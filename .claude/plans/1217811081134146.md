# PART 1 — In simple words

## What the system does today
When a staff member raises a support ticket or replies to one, the server sends their browser "back to the page you came from". It finds out where that was by trusting a note the browser attaches to the request (the "Referer", a record of the previous page).

## What is wrong with it
That note is written by whoever sends the request, and can be faked. A criminal can build a link or form that makes the note say "https://fake-bank-site.example". After the staff member submits, the server obediently sends them to that fake site, which can look just like our login page and steal their password. Because the staff member started on our real site, they have no reason to be suspicious. This is possible on five lines of the ticket code.

## What we are going to change
Before sending anyone "back", the server will check that the previous page is on our own website. If it is, nothing changes for staff. If it is missing or points anywhere else, the server sends them to the ticket list instead.

## What could go wrong
- If staff open the ticket page from a different address for our site (for example a second domain or a test address that differs from the configured base address), the "back" will land on the ticket list instead of the page they left. Nothing is lost, it is just a less convenient landing page.
- A browser that hides the Referer will now land on the ticket list; today it lands on the home page, because the empty value falls through to the site root.

| Word | What it means, simply |
|---|---|
| Referer | A note the browser sends saying which page you were on before. It can be forged. |

| Host | The website name part of an address, e.g. `admin.onestack.in`. |

# PART 3 — The technical version

## Root cause
Production `origin/onestackcbs` @ `10fa147eb8`, `application/modules/mobile_app/controllers/communication/ClientTicketMaster.php`. The task title says "echoed into href in 5 client-ticket views"; that is not what the code does. No view reads `HTTP_REFERER` (see Evidence). The 5 hits are server-side redirects in two methods:

```php
// raisedClientTicket()          :385, :390
redirect($_SERVER['HTTP_REFERER']);
// replyToClientTicket()         :700, :703, :707
redirect($_SERVER['HTTP_REFERER'], $this->data);
```

CI's `redirect()` (`system/helpers/url_helper.php:532`) sends the `Location` header to whatever string it is given, including absolute external URLs. The header value is attacker-controlled, so this is an open redirect. The class extends `Admin_Controller` (`:5`) so only logged-in admins reach it, but the victim IS such an admin. If the header is absent, an undefined-index read gives null (warning hidden by `error_reporting(E_ERROR)`), and `redirect('')` goes to the site root.

Routes: `raisedClientTicket` is reached via `application/config/routes.php:673`; `replyToClientTicket` via `:675`.

## How it will be fixed
Add one private method to the controller and use it at the 5 sites:

```php
private function safeReferer()
{
	$referer  = $this->input->server('HTTP_REFERER');
	$fallback = base_url('admin/bank_support_tickets-view');   // route routes.php:671 -> clientTicketIndex

	if (empty($referer)) {
		return $fallback;
	}
	$parts = parse_url($referer);
	$base  = parse_url(base_url());
	if (!isset($parts['scheme'], $parts['host'], $base['host'])
		|| !in_array(strtolower($parts['scheme']), ['http', 'https'], true)
		|| strcasecmp($parts['host'], $base['host']) !== 0) {
		return $fallback;
	}
	return $referer;
}
```

- Host comparison rejects `//evil.com` (host = evil.com), `https://evil.com`, `javascript:...` (no host) and `https://admin.onestack.in.evil.com` (different host string).
- Each site becomes `redirect($this->safeReferer());` / `redirect($this->safeReferer(), $this->data);`. The odd second argument `$this->data` on the three reply sites is existing behaviour and is left untouched (consistency rule).
- No new library or helper file; no codebase-wide change. Matches the style of the file (tabs, `public function` blocks).
