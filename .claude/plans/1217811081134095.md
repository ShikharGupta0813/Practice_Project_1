# PART 1 — In simple words

## What the system does today

Bank staff can upload a spreadsheet of a bank's customers and accounts, or of
their cards. The upload is not processed straight away. It goes into a waiting
line. Every few minutes a timed background job picks the next file from the
line and creates the customers, accounts and cards. There is no person behind
this job; the server runs it by itself.

The upload screens and the background job live in the same two code files. For
normal and card imports that is `CustomerAccountImport`; for "CBS" imports it is
`CbsCustomerAccountImport`.

## What is wrong with it

Almost every admin page first asks "are you logged in, and are you allowed to
do this?" These two files never ask. Anyone on the internet who knows the web
address can:
- upload a spreadsheet and have fake customers and accounts created inside a
  real bank,
- delete a bank's pending imports,
- see a bank's list of imports.

It is like a bank back office where every room is locked except the one where
new customers are entered, and that room opens onto the street.

The obvious fix is to put the normal admin lock on both files. On its own,
that would break the background job: the job cannot log in, so it would be
turned away every time and imports would silently stop.

## What we are going to change

1. Move the background-job part into its own new file. That file stays open, the
   same way every other background-job file in the system is today.
2. Point the job's web address at the new file. The address itself does not
   change, so nothing on the server's schedule needs touching.
3. Put the normal admin lock on the two original files. Uploading, deleting and
   listing imports then need a logged-in admin who has permission for the bank
   pages.

The moved code is copied exactly, with no changes inside it.

## What could go wrong

- **Staff with partial permissions.** Someone who can open the bank page but
  lacks its "add" permission can no longer upload. Someone without "delete" can
  no longer delete imports. This is intended and matches every other admin page
  (the user chose this).
- **The move itself.** If anything the background job needs is left behind,
  imports stop being processed. The plan checks this line by line, and the new
  file loads exactly what the old one did.
- **What stays open.** Anyone who knows the job's address can still make it run
  early, the same as every other background job today. That only processes files
  already in the line; it cannot add or delete anything.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Cron / background job | A task the server runs by itself on a timer, with no person logged in. |
| Import queue | The waiting line of uploaded spreadsheets. |
| Controller | A code file that answers a set of web addresses. |
| Route | The rule that says which web address goes to which code. |
| `Admin_Controller` | The standard "admin lock": it requires a logged-in admin and, for `admin/...` addresses, checks page permissions. |
| `CI_Controller` | The bare base with no lock at all. |
| Permission slug / action | The page name and verb (view/add/edit/delete) the permission check reads from the address, e.g. `bank-list` + `add`. |

# PART 3 — The technical version

## Root cause

Both classes extend the bare framework base, so neither `Auth_Controller`'s
ion_auth check nor `PermissionService` runs:

```php
// application/modules/cbs/controllers/CustomerAccountImport.php:10
class CustomerAccountImport extends CI_Controller
// application/modules/cbs/controllers/CbsCustomerAccountImport.php:9
class CbsCustomerAccountImport extends CI_Controller
```

Line numbers match the task. The constructors (`:12-32` and `:11-30`) only load
models and helpers. Neither file contains an `ion_auth` call.

simply switching the parent class would break the two cron routes shown in bold.

## How it will be fixed

**1. New controller `application/modules/cbs/controllers/CustomerAccountImportCron.php`**
(`extends CI_Controller`, like `CbsCron.php`, `CbsCronFinance.php` and `LoanCron.php`,
which all extend `CI_Controller`):
- The same file header as `CustomerAccountImport.php:1-8`: `set_time_limit(0)`,
  `require_once('vendor/autoload.php')`, and the four `use PhpOffice\...`
  lines. The moved code uses `IOFactory`, `Spreadsheet`, `Xlsx` and `Coordinate`
  (`:347, :457, :645, :1467, :1507, :1818, :2220, :2249, :2411, :2426`).
- The same constructor body as `CustomerAccountImport.php:12-32`.
- These methods moved **verbatim**:

| Method | Current lines | Why it moves |
|---|---|---|
| `new_process_customer_account_import_queue` | 297-679 | processing (unrouted, no callers); depends on the validators below |
| `validateCustomerFields` | 680-1110 | used only by the process methods |
| `validateAccountFields` | 1111-1299 | used only by the process methods |
| `validateDate` | 1300-1322 | used only by the two validators above |
| `process_customer_account_import_queue` | 1419-1874 | cron target (route :836) |
| `process_customer_account_card_import_queue` | 2182-2474 | cron target (route :1455) |
| `validateCustomerAccountCardFields` | 2475-end | used only by card processing |

Dependency check: the moved methods use `$this->db`, `CustomerAccountImport_model`,
`CustomerAccountCardImport_model`, `commonfunctions`, `encrypt_model`,
`CommonModel` (autoloaded, `autoload.php:131`) and each other. All of these come
from the copied constructor or from autoload. The methods that stay use none of
the moved methods: the only `$this->` method calls among them are
`insert_spreadsheet_data` and `insert_spreadsheet_card_data`, which both stay.

**2. Repoint the two live cron routes** (the keys stay the same, so the crontab
is untouched however it is invoked):
- `cbs-routes.php:836` → `"cbs/CustomerAccountImportCron/process_customer_account_import_queue"`
- `cbs-routes.php:1455` → `"cbs/CustomerAccountImportCron/process_customer_account_card_import_queue"`

**3. `CustomerAccountImport.php:10`** changes from `extends CI_Controller` to
`extends Admin_Controller`, and the moved methods are deleted from this file.

**4. `CbsCustomerAccountImport.php:9`** changes from `extends CI_Controller` to
`extends Admin_Controller`. Nothing moves here. Its cron route is already
commented out as UNUSED (`:1308`), so its `process_customer_account_import_queue`
simply becomes login-protected.

Effect on the admin routes after the change. `PermissionService` derives the
slug and action from segment 2:
- `bank-list-add` → `bank-list` / `add` (routes 833, 1305, 1452)
- `bank-list-view` → `bank-list` / `view` (routes 835, 1307, 1451)
- `bank-list-delete` → `bank-list` / `delete` (routes 1306, 1557, 1558)
- `all_customers-delete` → `all_customers` / `delete` (routes 834, 1453). The views
  do not use these; they call the 1557/1558 `bank-list-delete` equivalents.

User decision: the full `Admin_Controller` lock, with the permission check included.

Why the form upload keeps working: `MY_Controller.php:20` loads
`form_validation`, and `callback_validate_file_size` (`:43`, `:1966`, Cbs `:46`)
stays in the same class. `callback_` validators already work under
`Admin_Controller` in 23 module controllers (e.g. `AtmManagement.php`,
`BankManagement.php`, `CenterManagement.php`).

Non-browser callers: the git grep below finds no internal calls
(`Modules::run` or similar) to either class's methods. The only callers are the
routes and the three import views.
