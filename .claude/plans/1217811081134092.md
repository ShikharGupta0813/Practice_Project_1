# PART 1 — In simple words

## What the system does today
On the bank and partner pages in the console there is a list of **contact
people** (for example a bank's IT manager). Next to each contact is a dropdown:

- Pick a **role**: the system creates a console login for that person and
  emails them a password.
- Pick **"No Access"**: the system deletes that person's login.

The pages only show this dropdown to **OneStack staff**, meaning logins with no
bank and no partner attached. Bank staff never see it.

## What is wrong with it
Hiding the dropdown is like hiding a door behind a curtain but leaving it
unlocked. The server itself never checks who is asking. Anyone with any console
login can send the same request straight from their browser and:

- **create a login for any contact**, of any bank or partner;
- **delete anyone's login**. "No Access" deletes the login whose email matches
  the contact, and that could be a OneStack admin's email;
- **take over an existing login**. If a contact's email already has a login,
  the system overwrites that login's password and role.

There is also a fourth web address for this action that no page uses. It skips
the permission check completely.

## What we are going to change
1. The server now does the same check the page does. If your login has a bank
   or a partner, you get "Unauthorized access" and nothing happens.
2. If a contact's email already belongs to **another kind of login** (a
   superadmin, staff with a role group, or a login belonging to a different
   bank or partner), the system refuses and changes nothing. That applies to
   both giving and removing access. This check now runs **before** any email
   is sent.
3. The unused web address is removed.

Changing the role of a contact who already has a dashboard login made by this
same dropdown keeps working exactly as today.

## What could go wrong
- **A OneStack user tries to give access to a contact whose email is already a
  staff login.** They now get a refusal where it used to "work" by overwriting
  the staff login. That is the intended change.
- **Someone was using the removed web address.** Production logs show nobody
  has.
- **Main superadmin only, on partner pages.** The partner-contact dropdown works
  only for the main superadmin today, because the "partners" menu is switched
  off. That does not change.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Login | A console account (a row in `tbl_users`) that someone signs in with. |
| Contact | A person listed on a bank's or partner's page. Not a login until access is given. |
| Session | What the server remembers about who is signed in, including their bank and partner. The browser cannot change it. |
| Route / web address | The address the page calls to perform an action. |
| Role group | The modern role system (`role_grp_id`) used for staff logins. Dashboard-access logins do not have one. |
| Fails open | When a check cannot decide, it lets you through instead of stopping you. |

# PART 3 — The technical version

## Root cause
Two near-identical controller actions, neither with a server-side access check.

**1. `PartnerMaster::giveDashboardAccess()`**, `mobile_app/controllers/bank_onboarding_form/PartnerMaster.php:1222-1383`.

```php
$roleId = $this->input->post('role_id');
$userId = $this->input->post('user_id');   // any tbl_partner_contact id
...
$this->db->where('id', $userId);          // no ownership check
```

Every other page action in this class starts with `checkIfMainSuperadminOrOnestack()`
(`:25`, `:106`, `:242`, `:315`, `:472`, `:655`, `:688`, `:803`, `:920`, `:1043`,
`:1104`, `:1162`). This one does not.

**2. `CompanyMaster::giveDashboardAccess()`**, `CompanyMaster.php:4229-4382`. The
same shape, plus `company_id` taken from POST (`:4235`) and used to look up the
partner (`:4263-4265`).

**Who the UI shows the dropdown to.** Every view wraps it in the same condition,
e.g. `mobile_app/views/bank_onboarding_form/company-master/view.php:1973`:

```php
if (empty($this->session->userdata('partner_id')) && empty($this->session->userdata('company_id'))) {
```

The same condition is at `company-master/view-company-details.php:375`, and the
`application/views/admin/company-master/` copies are at `:365` and `:1744`. So the
intended users are logins with no bank and no partner. The server never
enforces it.

**Existing login is overwritten.** `PartnerMaster.php:1300` and `CompanyMaster.php:4316`
look the email up in `tbl_users`. If found:

```php
$userId = $userInfo[0]['id'];
if($this->ion_auth->update($userId, $additional_data))   // new password, role_id, company_id/partner_id
```

(`PartnerMaster.php:1339-1340`, `CompanyMaster.php:4343-4344`). `send_mail()` with the
new password has already run before this lookup (`PartnerMaster.php:1292`,
`CompanyMaster.php:4308`).

**"No Access" deletes by email.** `PartnerMaster.php:1371-1381` and `CompanyMaster.php:4367-4379`:

```php
$deleteStatus = $this->CommonModel->delete(DbTable::USERS, array('email' => $email));
```

**Fail-open route.** The task's `routes.php:2607` has moved to **`:2702`**:

```php
$route['admin/give-dashboard-access'] = 'mobile_app/bank_onboarding_form/PartnerMaster/giveDashboardAccess';
```

Its segment 2 has no action suffix, so the slug is `give-dashboard-access` and
the action is `view` (`MY_Controller.php:340-356`). There is no menu row, so
`PermissionService.php:127-152` returns `true`.

**Production evidence** (Shikhar, 2026-09-24):

```

                              (no row for give-dashboard-access)
access log grep "/admin/give-dashboard-access": no hits
```

- **`admin/give-dashboard-access`**: no menu row, so it fails open. It is unused,

- **`partners` is inactive.** `PermissionService.php:153-155` denies everyone except

- **The 62 NULL-group logins** match exactly what `CompanyMaster::giveDashboardAccess`
  creates: `role_id` set, no `role_grp_id`, `company_id` = the contact's bank. That
  is the shape of login this action may legitimately update or remove.

## How it will be fixed
In **both** functions:

1. **Access gate**, first thing inside the POST branch. It mirrors the views' own
   condition:
   ```php
   if(!empty($this->session->userdata('partner_id')) || !empty($this->session->userdata('company_id'))){
       $response['msg'] = 'Unauthorized access';
       $response['status'] = '0';
       echo json_encode($response);exit;
   }
   ```
   It returns JSON because the JS parses JSON (`view.php:3104-3111` shows `obj.msg`
   via `handleErrorResponse`). The page-action pattern `setAlert` + `redirect` would
   break the AJAX caller.
2. **Existing-login guard**, placed right after the contact lookup and before any
   password is generated or email is sent. It applies to both the grant branch and
   the "No Access" branch:
   ```php
   $userInfo = $this->CommonModel->select(DbTable::USERS, 'id, email, is_main, role_grp_id, company_id, partner_id', array('email' => $email));
   if(!empty($userInfo) && ($userInfo[0]['is_main'] == '1' || !empty($userInfo[0]['role_grp_id']) || <scope mismatch>)){
       $response['msg'] = 'A login already exists for this email';
       $response['status'] = '0';
       echo json_encode($response);exit;
   }
   ```
   - `<scope mismatch>` for CompanyMaster: `$userInfo[0]['company_id'] != $companyUsersInfo[0]['company_id']`
   - `<scope mismatch>` for PartnerMaster: `$userInfo[0]['partner_id'] != $partnerUsersInfo[0]['partner_id']`

   The later `$userInfo` lookup (`:1300` / `:4316`) is then reused, not repeated.
3. **CompanyMaster only:** stop trusting POST `company_id`. Look up the partner
   from the contact's own `company_id` (`$companyUsersInfo[0]['company_id']`)
   instead of `$this->input->post('company_id')`.

Then delete `routes.php:2702`.

**Why "refuse" is narrowed to *other kinds of* login.** Shikhar chose "refuse"
when the email already has a login. But the dropdown also shows each contact's
**current** role, loaded by joining `tbl_users` on email
(`CompanyMaster.php:2486-2488`), and is used to change it. A contact who already
has a dashboard login therefore *always* hits the "login exists" branch.
Refusing every time would break changing a role (7↔8) and break "No Access".
The guard refuses only logins this action did not create: main superadmin,
anyone with a role group, or a login belonging to a different bank or partner.
**Flagged for Shikhar's confirmation.**
