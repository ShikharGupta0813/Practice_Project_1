# PART 1 — In simple words

## What the system does today

This is the sandbox version of the partner-onboarding intake. Sandbox means the
practice environment — where a new partner's integration is tested before it is
allowed to handle real money. It receives the same kind of bundle as the live
intake: partner details with scanned documents inside, each document arriving with
its own name and the folder it should be filed into.

## What is wrong with it

The same defect as the two live intake files. The sender chooses the folder and
the file name, and the system obeys both without checking. A program can be sent
in place of a document and filed anywhere on the server.

Being "only the sandbox" does not make this safe. The sandbox usually runs on the
same servers as everything else, so a program placed here can still reach live
data. It is also typically the easiest of the three to reach, because sandbox
access is handed out more freely during partner testing.

## What we are going to change

The same change as the other two, using the same shared piece of code: one fixed
folder we control, a cleaned-up name, only real document types, and no
"anyone can change this" permission.

## What could go wrong

Sandbox is where partners experiment, so the range of file names and types
arriving here is probably wider and messier than on the live intake. An allowlist
tuned to live traffic may reject things sandbox users send routinely, and they
will read that as "the sandbox is broken".

If we are going to loosen the rules anywhere, this is the one place it might be
justified — but loosening should be a deliberate decision, not an accident.

# PART 3 — The technical version

## Root cause

Same defect class as tasks 34 and 35, in
`application/modules/mobile_app/controllers/apiv2/FetchSandboxDetails.php`.
First site at :51, identical shape — caller-supplied `$folderpath` and `$filename`
concatenated onto `FCPATH`, no `basename()`, no extension allowlist, no
`realpath()` containment, followed by `chmod(..., 0777)`.

`class FetchSandboxDetails extends REST_Controller` at line 5, so the same
`rest_auth = FALSE` exposure applies.

**The task title's "10/12" matches the file's 12 write sites**, but as with task
35 I could not identify a basis on which only 10 are vulnerable — all 12 build the
path from request values. **Plan targets all 12.**

## How it will be fixed

Use the shared `secure_store_document()` helper from task 34. Replace each of the
12 write + chmod pairs.
