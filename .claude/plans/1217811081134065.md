# PART 1 — In simple words

## What the system does today

When a new partner is set up on the system, an outside computer sends us their
details in one bundle. Inside that bundle are scanned documents — an agreement,
identity papers, and so on. Each document arrives with three things: the picture
of the document itself, the name it should be saved under, and the folder it
should be filed into.

Our system takes all three at face value. It uses the name it was given, files it
into the folder it was told to use, and saves it. It then marks the saved file as
readable and writable by anyone on the server.

## What is wrong with it

The sender chooses the folder. Nothing checks that the folder is a sensible place
to put a document.

Think of it as a mailroom that files whatever it is handed into whatever cabinet
the sender writes on the envelope — including the cabinet holding the building's
own operating instructions. Because the sender also chooses the file name and its
type, they can send something that is not a document at all, but a small program,
and have it filed somewhere the server will later run.

There is no check on the file type, so a program can be sent in place of a scan.
There is no check on the folder, so it can be aimed anywhere on the server. And
the permission the file is given afterwards lets anything on the server change it
again later.

This endpoint is part of the API surface, which is currently not requiring a
password (a separate task covers that). So today this can be reached without
signing in.

For a real person this means: an outsider could place their own program on the
bank's server and get it to run. From there, customer records, transaction data
and stored keys are all reachable. Nothing needs to have gone wrong yet for this
to be worth fixing immediately — the door is open.

## What we are going to change

We will stop trusting the sender about where a file goes and what it is. Every
uploaded document will be filed into one fixed folder that we choose, under a name
we clean up first, and only if it is a genuine document type (PDF or image). The
"anyone can change this" permission will be removed. All sixteen places in this
file that save an uploaded document will go through one shared piece of code, so
there is one rule instead of sixteen.

## What could go wrong

If the outside system that sends us these bundles is genuinely relying on choosing
its own folders — because different partners file into different places — then
forcing one fixed folder would break their uploads. We need to confirm this before
shipping. The safe version is to accept the folder name but only allow it to be
one of a known list, rather than any folder at all.

The other risk is documents that are legitimately an unusual type. If a partner
sends, say, a spreadsheet as part of the bundle and we only allow PDFs and images,
their upload will start failing. The allowed list needs to match what really
arrives.

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/api/FetchProductionDetails.php:45-53`
takes the file name, the destination folder and the file body straight from the
request JSON and writes it:

```php
$filename = $basicInfo['agreement_details']['name'];
$folderpath = $basicInfo['agreement_details']['folder_path'];
$base_64_encode_agreement = $basicInfo['agreement_details']['base_64_encode'];

$data = base64_decode($base_64_encode_agreement);
$folder_path = FCPATH.$folderpath.$filename;
file_put_contents($folder_path, $data);
chmod($folder_path, 0777);
```

Three separate defects in these four lines:

1. **`$folderpath` is caller-controlled and concatenated onto `FCPATH`.** No
   `realpath()` check, no allowlist. `../` sequences resolve upward out of the
   web root.
2. **`$filename` is caller-controlled with no `basename()` and no extension
   check.** A `.php` name is accepted, so the written file is executable by the
   web server if it lands anywhere served.
3. **`chmod($folder_path, 0777)`** makes the result world-writable, so even a
   file written to a safe location can be replaced afterwards by any other
   process on the host.

The class is `class FetchProductionDetails extends REST_Controller` (line 5).
Per `.claude/CLAUDE.md`, `rest_auth = FALSE` is live in
`application/config/rest.php`, so this is currently reachable unauthenticated.
That is tracked separately as task 27; this plan does not depend on it, but it is
why the severity is CRITICAL rather than HIGH.

**Line numbers confirmed against production.** The task title gives no line
number; the first write site is at :52.

## How it will be fixed

Add one private helper to the controller that performs every document write, and
route all sixteen call sites through it:

```php
private function storeUploadedDocument($base64, $requestedName, $subDir = '')
```

The helper will:
- `basename()` the requested name, then `preg_replace('/[^A-Za-z0-9._-]/', '_', …)`.
- Reject any extension not on the allowlist (`pdf, jpg, jpeg, png`), returning
  `false` rather than throwing.
- Resolve the destination under a single fixed base directory constant; if a
  sub-directory is supplied, validate it against a known list rather than using
  it as a raw path segment.
- Verify with `realpath()` that the resolved target is still inside the base
  directory before writing.
- Write with `file_put_contents()`, then `chmod(…, 0644)` — not 0777.

The same helper is needed by the three sibling controllers (tasks 35, 36 and the
untracked `api/FetchSandboxDetails.php`), so it should live in a shared location
rather than being copied. Suggested: a new
`application/helpers/secure_upload_helper.php`, loaded by each controller. This
matches the existing convention of plain function helpers in `application/helpers/`.

## Plan

1. Create `application/helpers/secure_upload_helper.php` with
   `secure_store_document($base64, $requestedName, $subDir = '')`, returning the
   written path on success or `false` on rejection.
2. Define the allowed extensions and the fixed base directory as constants at the
   top of the helper.
3. In `api/FetchProductionDetails.php`, load the helper in the constructor.
4. Replace each of the 16 `file_put_contents(...)` + `chmod(...)` pairs with a
   call to the helper, preserving the surrounding success/failure handling.
5. Where the existing code used the return of `file_put_contents` implicitly,
   add an explicit `false` check and return the existing JSON error shape — do
   not invent a new error format.
6. Leave the `$folderpath` request field being read, but pass it as `$subDir` so
   the helper validates it. Do not silently ignore it.
7. Commit. Do not touch the sibling controllers on this commit — separate tasks,
   same branch.

Regression: run one full partner-onboarding bundle end to end and confirm the
partner record is still created and the agreement is retrievable through whatever
screen normally displays it.

**Production evidence needed before shipping** — to size the risk in step 6, we
need to know what `folder_path` values real callers actually send. Run on
production, read-only:

```bash
grep -rho '"folder_path"[^,]*' /path/to/application/logs/bank-onboarding/ | sort | uniq -c | sort -rn | head -20
```

If this returns a small fixed set, the allowlist is that set and the change is
safe. If it returns many distinct values, the sub-directory rule needs rethinking
before this ships — raise it rather than guessing.
