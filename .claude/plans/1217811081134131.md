# PART 1 — In simple words

## What the system does today
Staff build an RBI report (a regulatory return the bank files with the Reserve Bank) on an admin screen. When they press Save, Excel or PDF, the page sends five details to the server: which bank, which bank category, which report type, which report, and the report's data. The server is meant to check each one is filled in before it saves anything.

## What is wrong with it
The checks are written like a guest list that says "turn the person away if they are not on the list AND their name is blank". Someone who is on the list with a blank name is let in, and someone who is not on the list at all is turned away only by accident. In practice: if a field arrives **present but empty**, the check does not catch it, and the server saves a report row and builds the return from empty inputs. Nobody gets an error telling them a field was missing. The result is an RBI return with blanks in it that looks like it was generated normally.

## What we are going to change
Change each of the five checks so it says "turn them away if the field is missing OR blank". Empty fields will then stop with the existing message ("Bank is required!" and so on) instead of producing a report.

## What could go wrong
Any screen that today sends an empty field and "works" will start getting an error. The four admin pages that send this data fill the fields from hidden boxes on the page; if any report type leaves one of those boxes blank, saving that report would now be refused. The data itself (`jsonString`) is never blank from those pages, so that one is safe. A production check for this is listed in the test section.

# PART 3 — The technical version

## Root cause
`application/modules/mobile_app/controllers/mis/ReportController.php:448-476`. Task line numbers still match (448-472 plus a sixth block at 472). Five checks, plus a sixth identical one for `jsonString` the task did not list:

```php
if (!isset($_POST['bank_id']) && $_POST['bank_id'] == '') {   // :448
```
Same shape at `:454` (`bank_category_id`), `:460` (`report_type`), `:466` (`report_id`), `:472` (`jsonString`).

With `&&`:
- field absent: `!isset` true, `$_POST[..] == ''` true (null == '') -> error set (works, but raises an undefined-index notice, hidden by `error_reporting(E_ERROR)`, see known-patterns).
- field present and `''`: `!isset` false -> short-circuit -> **no error**. This is the bug.
- field present and non-empty: no error (correct).

`$hasError` stays 0, so `:478` runs: a row is written to `rbi_report_details` (`:498` update or `:513` create) and the Excel/PDF path continues.

The same function is also called internally at `:1305` with `$_POST = $savePostData` where `jsonString` is `json_decode(...)` output, i.e. possibly an object or null, never a string. A fix using `trim()` / string functions on it would throw a TypeError on PHP 8. So the fix must use a plain comparison, not string functions.

## How it will be fixed
Replace `&&` with `||` and compare strictly, for all six blocks:

```php
if (!isset($_POST['bank_id']) || $_POST['bank_id'] === '') {
```
Strict `=== ''` is used so an object/null/array `jsonString` from the internal caller at `:1305` is never passed to a string function. Null is already caught by `!isset`. Whitespace-only values are deliberately NOT treated as empty (not in the task; avoids changing behaviour further). Messages and `$hasError`/`$data` handling unchanged. The existing typo "Reprot name" is left alone.
