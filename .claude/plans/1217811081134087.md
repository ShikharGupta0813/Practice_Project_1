# CRITICAL - Deduplicate the four independent copies of the import-queue delete query once fixed — fixing one leaves three vulnerable

Asana: https://app.asana.com/0/0/1217811081134087/f  |  ID: 1217811081134087  |  Due: no due date

---
# PART 1 — In simple words

## What the system does today

The same twelve-word piece of code exists in four different files. Each one removes
a queued bulk-upload job from the database. They were copied from one another over
time and have never been brought back together.

Three of the four are word-for-word identical apart from which table they point at.

## What is wrong with it

Duplication is not itself a security hole, but here it is what turns one flaw into
four. When the same flaw is copied four times, fixing the copy someone happened to
report leaves the other three exactly as they were. That is not hypothetical — of
these four, **only two have their own task**. Someone working the task list would
fix two and reasonably believe the job was done, while two remained open.

It also means the next person to need this behaviour will copy whichever version
they find first, and the count becomes five.

The everyday comparison: four doors into the same room, and a maintenance list that
mentions two of them.

## What we are going to change

After all four copies have been individually fixed, replace them with a single
shared piece of code that all four call. One place to read, one place to change,
and no way to fix it in one caller but not another.

## What could go wrong

The four copies are not perfectly identical — they point at three different tables,
and the surrounding code around each differs. Merging them carelessly could send a
delete to the wrong table, which would remove the wrong jobs.

This is also a change with no visible benefit to a user, which makes it the kind of
change that gets reviewed less carefully than it should be. The testing below
deliberately checks each of the four callers separately rather than assuming that
one working means all four work.

# PART 3 — The technical version

## Root cause

Four independent copies of the same unparameterised `DELETE`:

```
application/modules/cbs/controllers/CbsCustomerAccountImport.php:219
    "Delete from tbl_cbs_cron_import_data where queue_id = " . $_POST['id']

application/modules/cbs/controllers/CustomerAccountImport.php:234
    "Delete from tbl_cron_import_data where queue_id = " . $_POST['id']

application/modules/cbs/controllers/CustomerAccountImport.php:2165
    "Delete from tbl_cron_card_import_data where queue_id = " . $_POST['id']

application/modules/mobile_app/controllers/Users.php:1747
    "Delete from tbl_cron_import_data where queue_id = " . $_POST['id']
```

**Three distinct tables** across the four sites:
`tbl_cbs_cron_import_data`, `tbl_cron_import_data` (×2), `tbl_cron_card_import_data`.
Any shared implementation must take the table as a parameter — it cannot hardcode
one.

**The task's count of four is correct.** My first search found only three; widening
the pattern to catch the `$this->input` form as well as `$_POST` found the fourth
at `CustomerAccountImport.php:2165`.

**Coverage gap:** only `CbsCustomerAccountImport.php:219` (task 44) and
`Users.php:1747` (task 45) have Asana tasks. The two sites in
`CustomerAccountImport.php` have none.

## How it will be fixed

This task runs **last** on the shared branch, after all four sites are individually
parameterised.

Add one method to the existing import model rather than inventing a new layer —
`CustomerAccountImport_model` is already loaded by the cbs controllers:

```php
public function deleteImportQueueData($table, $queueId)
{
    $allowed = [
        'tbl_cron_import_data',
        'tbl_cbs_cron_import_data',
        'tbl_cron_card_import_data',
    ];
    if (!in_array($table, $allowed, true)) {
        return false;
    }
    return $this->db->delete($table, ['queue_id' => (int) $queueId]);
}
```

The table allowlist matters: passing a table name through as a variable is itself an
injection surface, so it must be constrained to the three known values rather than
accepted freely.

`$this->db->delete()` is the CI3 query-builder form and binds the value itself, so
the shared version has no raw SQL at all.

`Users.php` sits in `mobile_app`, not `cbs`, so it will need to load the model
explicitly. That is normal for this HMVC setup.

Behavioural — **each of the four callers must be exercised separately**, on
staging, signed in with the relevant permission:

1. cbs customer-account import queue → delete a job → confirm gone from
   `tbl_cbs_cron_import_data`.
2. The non-cbs customer-account import queue → delete → confirm gone from
   `tbl_cron_import_data`.
3. The **card** import queue → delete → confirm gone from
   `tbl_cron_card_import_data`, and confirm the other two tables are untouched.
   This is the site most likely to be wired to the wrong table by mistake.
4. The user-management queue delete → confirm gone from `tbl_cron_import_data`.

Then confirm the allowlist holds: call the model with a table name not on the list
and expect `false` with nothing deleted.

## Needs human review

`yes` — touches four call sites across two modules and three tables, deleting
customer import data. The wrong-table risk is real and only a reviewer exercising
all four screens will catch it.
