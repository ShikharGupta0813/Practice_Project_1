# CRITICAL - mobile_app/controllers/Payment.php:1304-1311 — interpolates transactionreferencenumber from an unauthenticated callback into $this->db->query()

Asana: https://app.asana.com/0/0/1217811081134086/f  |  ID: 1217811081134086  |  Due: no due date

---
# PART 1 — In simple words

## What the system does today

When a customer pays by UPI, the payment network tells us the result by calling
back to an address on our server. That callback carries a reference number for the
transaction.

Our system takes that reference number and asks the database for the full details
of the matching payment — the amount, the date, who sent it, who received it, the
customer's email and mobile number, their account number, and the bank's details.
It then uses those details to send the customer a confirmation text message and
email.

It builds that database question by gluing the reference number into a sentence.

## What is wrong with it

The address the payment network calls is, necessarily, open to the internet. It has
to be — the network is an outside system and cannot sign in. So the reference number
in that callback is a value from outside that anyone can send.

And that value is glued straight into a database question without being checked.

This is the same flaw as the other database ones in this batch, but with the worst
possible starting position: every other one needs a stolen or legitimate staff login
first. This one needs nothing. Anyone who can reach the callback address can send a
crafted reference number, and the database will carry out whatever extra
instructions it contains.

The particular question being asked here already reaches across customer records,
account numbers and bank configuration, so an attacker attaching their own question
onto the end of it is well placed to read the rest.

## What we are going to change

Hand the reference number to the database as a value rather than gluing it into the
sentence, so it can only ever be treated as a reference number and never as an
instruction.

## What could go wrong

This sits directly in the live payment confirmation path. If the change is wrong,
the symptom is not an error message — it is customers silently not receiving
confirmation of payments they made. That is worse than a visible failure because
nobody notices immediately.

So the fix itself is trivial, but it must be tested against a real transaction
rather than only checked for correct syntax.

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/Payment.php:1304-1311`, inside
`upi_callback()` (declared at **:1122**):

```php
$query = $this->db->query('select utm.upi_transaction_date, utm.upi_transaction_utr_no, utm.amount,
        utm.sender_upi_id, utm.receiver_upi_id, cust.email, cust.mobile_no, cust.name_on_pan,
        ... cm.company_name, cm.company_logo, cm.address, cm.city, cm.pincode, stm.state_name, cm.bank_url
    from tbl_upi_transaction_master utm
    inner join tbl_customers cust on cust.id = utm.customer_id
    inner join tbl_company_master cm on cm.id = utm.company_id
    inner join tbl_state_master stm on stm.id = cm.state_id
    left join tbl_customer_accounts acnt on utm.receiver_upi_id = acnt.upi_id
    where utm.upi_transaction_utr_no = "' . $apiRequest['transactionreferencenumber'] . '" group by utm.id');
```

`$apiRequest['transactionreferencenumber']` is interpolated inside double quotes in
the `WHERE`. Unlike the numeric-context injections elsewhere in this batch, this one
is **string context** — the attacker breaks out with a `"` first, but the payload
space after that is unrestricted, and the query already joins five tables including
`tbl_customers` and `tbl_company_master`.

**Exposure is unauthenticated by design.** Line 4:

```php
class Payment extends Public_Controller
```

`Public_Controller` (`application/core/MY_Controller.php`) exists precisely so
these payment-network callbacks can arrive without a session. So there is no login
in front of this — correctly so for the callback's purpose, which is exactly why the
injection matters.

**Line numbers confirmed** — the task's 1304-1311 still matches.

The result feeds `sendUpiConfirmationSms($result, $apiRequest)` at :1315.

## How it will be fixed

Bind the value:

```php
$sql = 'select ... where utm.upi_transaction_utr_no = ? group by utm.id';
$query = $this->db->query($sql, [$apiRequest['transactionreferencenumber']]);
```

No cast — UTR numbers are alphanumeric strings, not integers. Binding alone is the
correct and sufficient fix.

Do not restructure the query, rename columns or change the joins. The result array
is consumed downstream by `sendUpiConfirmationSms()` and any change to its shape
breaks confirmations.

## Plan

1. Read the other two `db->query(` sites in this file. If either has the same
   defect, raise it with the user before deciding whether to widen scope.
2. Extract the query at :1304 to a `$sql` variable with a `?` in place of the
   interpolated UTR.
3. Pass `[$apiRequest['transactionreferencenumber']]` as the second argument to
   `$this->db->query()`.
4. Leave the select list, joins, `group by` and the downstream
   `sendUpiConfirmationSms()` call untouched.
5. Commit.

## How to test

```bash
php -l application/modules/mobile_app/controllers/Payment.php
```

```bash
grep -n "transactionreferencenumber'\] *\." application/modules/mobile_app/controllers/Payment.php
```
Expected: no match — the value is no longer concatenated.

Behavioural, on staging with a real sandbox UPI transaction:

1. Complete a sandbox UPI payment end to end and let the network call back
   normally. **Expect the confirmation SMS and email to arrive**, with the correct
   amount, account number and bank name. This is the test that matters — a
   syntax-only check will not catch a broken binding.
2. Replay the same callback with a UTR that does not exist. Expect the existing
   `if (!empty($result))` branch to skip the SMS quietly, with no PHP error.
3. Replay with `transactionreferencenumber` set to `x" OR "1"="1`. Expect no rows
   returned and no confirmation sent — today this would match every transaction.

**Production evidence needed** — to confirm the UTR format assumption before
deciding whether any additional validation is warranted:

```sql
SELECT upi_transaction_utr_no FROM tbl_upi_transaction_master ORDER BY id DESC LIMIT 20;
```

If these are uniformly alphanumeric of a fixed length, an additional format check
would be a cheap second layer. If they vary, binding alone is the right and only
fix — do not add a format check that rejects real UTRs.
