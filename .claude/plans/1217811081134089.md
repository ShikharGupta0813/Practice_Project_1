# CRITICAL - Fix the 10 delete/remove/destroy routes whose derived action is not delete

Asana: https://app.asana.com/0/0/1217811081134089/f  |  ID: 1217811081134089  |  Due: no due date

---
# PART 1 — In simple words

## What the system does today

Every admin screen has a web address, and the system works out from that address
what the user is trying to do. It does this by looking at the end of the address:
if it ends in `-view` the user is looking, `-add` means creating, `-edit` means
changing, `-delete` means removing.

Once it knows which of those four it is, it checks the user's permissions for that
particular thing. Someone might be allowed to look at customers but not delete
them, and this is how that gets enforced.

## What is wrong with it

If the address does not end in one of those four words, the system does not stop
and ask. It assumes the user is just looking.

Twelve addresses that delete things do not end in `-delete`. Some end in nothing
recognisable at all, like `admin/delete-bank-user`. Some end in the wrong word
entirely, like `admin/homepage-add/homepage/remove_shortcut`, which the system
reads as an "add".

So for those twelve, the system checks the wrong permission. It asks "is this
person allowed to look at this screen?" and, if they are, lets them delete.

In practice that means a member of staff given read-only access to, for example,
support tickets can delete support tickets. Someone with read-only access to bank
users can delete bank users. The permission system is doing exactly what it was
told; it was told the wrong thing.

## What we are going to change

Correct those twelve addresses so the system can tell they are deletions. The
cleanest way is to give each one the `-delete` ending the system already
understands, matching how the other delete addresses in the system are already
written.

## What could go wrong

This is the important part. Today these twelve deletions are permitted to anyone
with read access. After the fix they will be permitted only to people with delete
access.

If the people currently doing these deletions have never been granted delete
permission — because they never needed it, since read access was enough — then the
moment this ships, they stop being able to do their job. Support staff would find
they can no longer close out tickets, and it would not be obvious why.

So before this ships someone has to check who currently holds delete permission on
these areas, and grant it where it is genuinely intended. That check is written out
in the testing section as a production query. **This change should not go live
until that has been looked at.**

Changing an address also breaks any bookmark or saved link pointing at the old one.
Where that matters, the old address can be kept as a redirect.

# PART 3 — The technical version

## Root cause

`application/core/MY_Controller.php:341-356`:

```php
$parts = explode('-', $segment2);
$possibleAction = end($parts);
$validActions = ['view', 'add', 'edit', 'delete'];

if (in_array($possibleAction, $validActions)) {
    $this->url_action = $possibleAction;
    array_pop($parts);
    $this->url_slug = implode('-', $parts);
} else {
    $this->url_slug   = $segment2;
    $this->url_action = 'view';        // <- silent default
}
```

Only `uri->segment(2)` is inspected. `PermissionService::checkPermission()` then
maps `'view'` to the `display_action` column
(`application/libraries/PermissionService.php:19-24`), so a delete is authorised
against read permission.

**I enumerated the affected routes rather than trusting the count.** Parsing all
non-commented `$route[...]` entries in `routes.php` and `cbs-routes.php`,

`homepage` short-circuit at `MY_Controller.php:343`:

Routes 5 and 8-11 are the clearest cases: `admin/delete-bank-user` splits to
`['delete','bank','user']`, `end()` is `user`, so the action is `view`. The word
"delete" being at the *front* of the slug is invisible to this logic.

**Not affected, despite matching a naive search:** eight routes of the form
`admin/(partner-delete|users_list-delete|partners-delete)/delete-partner`. These
are regex alternations — at runtime `segment(2)` is literally `partner-delete`,
which derives `delete` correctly. A search that treats the route key as the
segment reports these as broken; they are not.

## How it will be fixed

For each of the 12, add an explicit action suffix to `segment(2)`, matching the
existing convention seen at `routes.php:90`:

```php
// before
$route['admin/delete-bank-user'] = 'mobile_app/bank_onboarding_form/CompanyUsers/deleteCompanyUser';
// after
$route['admin/bank_user-delete/delete-bank-user'] = 'mobile_app/bank_onboarding_form/CompanyUsers/deleteCompanyUser';
```

The slug chosen must match an existing `menu_link` in the sidebar-navigation
table, or `PermissionService.php:127` will not find the menu row and will
**fail open** — granting access rather than denying it. **Step 1 establishes the
correct slug for each of the 12 from production data. Do not guess them.**

Routes 3 and 4 derive `add` and route 1 derives `add`; those need the suffix
changed, not added.

Where an address is likely bookmarked (5, 8-11 are bare top-level addresses),
keep the old key as a redirect to the new one rather than removing it.

## Plan

1. Get the slug list from production (query below). For each of the 12, choose a
   slug that **already exists** as a `menu_link`. Do not invent slugs.
2. Change the 11 keys in `routes.php`, one line each.
3. Change the 1 key in `cbs-routes.php` (route 1, `-add` → `-delete`).
4. For routes 5, 8, 9, 10 and 11, add a redirect entry preserving the old address.
5. Check the per-environment route files for overriding entries of the same keys:
   `grep -rn "delete-bank-user" application/config/` across every env dir. A later
   file silently overwrites an earlier one, so an override would undo the fix.
6. Commit.

Behavioural, on staging. **For each of the 12, two accounts are needed** — one with

1. As the delete-permission account, perform the deletion. Expect it to succeed

2. As the view-only account, attempt the same deletion. Expect it to be **denied**.
   Before this change it would have succeeded — that is the whole point of the fix.
3. Confirm the screen the deletion is launched from still loads for the view-only
   account (they should still be able to look).
4. For routes 5 and 8-11, request the **old** address and confirm the redirect
   lands on the new one.
5. Specifically re-test support tickets (routes 6 and 12) — it has two routes to
   the same delete and both must behave the same.

**Production evidence needed BEFORE step 1 — blocking:**

```sql
SELECT id, menu_link, sidebar_id, parent_id, is_active
FROM tbl_sidebar_navigation_menus ORDER BY menu_link;
```

This is the authoritative slug list. A slug not in here fails open at
`PermissionService.php:127`, so picking a non-existent slug would make things worse
rather than better.

```sql
SELECT rg.role_group_name, r.role_name, a.parent_menu, a.child_menu, a.delete_action, a.display_action
FROM tbl_user_management_access a
JOIN tbl_role_group_master rg ON rg.id = a.role_group_id
JOIN tbl_subrole_master r ON r.id = a.role_id
WHERE a.display_action = 1 AND a.delete_action = 0;
```

This is the lockout check. Every row is a role that can currently perform these 12
deletions via the read permission and **will lose that ability**. If the list
includes roles that legitimately do these deletions day to day, their
`delete_action` must be granted in the same release — otherwise this change breaks
their work. **Bring the result back before shipping.**
