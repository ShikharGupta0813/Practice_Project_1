# PART 1 — In simple words

## What the system does today
When a customer wants to verify their Aadhaar in the mobile app, they type in
their Aadhaar number. The app asks our server for a verification link. Our
server asks Digitap (the outside company that does the Aadhaar check) to create
one. Our server should then do three things:

1. Write a note in a record book saying "customer X started verifying,
   reference number Y".
2. Save the Aadhaar number on the customer.
3. Send the link back to the app, where the customer finishes the check.

Digitap sends the result back later. Our server uses the reference number in
that note to work out which customer it belongs to.

## What is wrong with it
Digitap is working fine. It returned a good link every time today. The problem
is in step 1, the note. One of the note's boxes, "vendor" (which company did
the check), is always left empty. The database refuses notes with that box
empty. The server stops right there and the app gets an error (500).

So on production **no customer can verify their Aadhaar from the app at the
moment**. Production logs show this happening today for two banks
(Ganga Stellar and Sirohi CCB). The bank's own staff screen (admin console)
still works, because it fills that box in correctly.

## What we are going to change
Fill in the "vendor" box with the right name ("kyc_digitap"). That is the same
value the older (v2) version of the app and the result-handling code in this
same file already use. It's a one-line change.

## What could go wrong
Very little. The only change is what gets written into that one box. If the
customer then completes the check on Digitap's page, the rest of the flow
(receiving the result and updating the customer) starts running on production
for the first time. That part has never actually run there, because every
attempt failed earlier. It should get a real end-to-end test on rbank and
production.

# PART 3 — The technical version

## Root cause
The line references are for `origin/onestackcbs`, in
`application/modules/mobile_app/controllers/apiv6/Profile.php`.

`send_aadhar_card_otp_post()` (line 2914) resolves the vendor at line 2954 with
`getVendorModuleConfig()`:
```php
$fetchModule = getVendorModuleConfig($this->currentBankId, KYC);
if($fetchModule['vendor_name'] == "digitap")
```
It then builds the audit row at lines 2979-2993:
```php
$authReqRespCon = array(
    'company_id'           => $this->currentBankId,
    'vendor'               => $fetchModule['module_key'],   // line 2981
```
`getVendorModuleConfig()` (`application/helpers/common_helper.php:2588-2652`)
returns `status, child_module_id, vendor_module_id, vendor_name, vendor_code,
vendor_slug, priority, is_configured, config`. It has **no `module_key` key**,
so `vendor` is always NULL. That key only exists on
`getVendorModuleWithConfig()` (`common_helper.php:255`, sets `module_key` at
~286).

Production schema (`SHOW CREATE TABLE`, supplied by the user):
`` `vendor` varchar(50) NOT NULL DEFAULT 'authbridge' ``. An explicit NULL is
rejected even in non-strict mode.

Production evidence (the user ran these read-only on 2026-09-28):
- `application/logs/log-2026-09-28.php:465-466`:
  `Query error: Column 'vendor' cannot be null - Invalid query: INSERT INTO
  tbl_authbridge_request_response (company_id, vendor, ...) VALUES ('334', NULL,
  'aadhar_no', ...)`. This was at 14:12:13 and 14:12:37, customer 752101
  (gangastellar).
- `logs/otp/digitap-send-aadhar-card-otp-2026-09-28.txt`: 5 app requests
  (customer 634685 on sirohiccb ×3, customer 752101 on gangastellar ×2). Digitap
  returned `code 200` with a valid URL on every one.
- `logs/otp/send-aadhar-card-otp-2026-09-28.txt`: no final `Response` line. The
  request died at the insert (line 2994) and never reached line ~3072.
- `SELECT … WHERE transactionId = '04045efb-…'` returned nothing. The row was
  never written.
- The admin console's inserts into the same table succeed
  (`logs/testing/query-create-2026-09-28.php`, `vendor = 'digitap'`), because
  `CustomerProfileManagement.php:13955` uses `$fetchModule['vendor_name']`.

Why v2 is not affected: `apiv2/Profile.php:2467` uses
`getVendorModuleWithConfig()`, which does set `module_key`, so line 2494 gets
`'kyc_digitap'`. The v2 send path is out of scope. Its `module_key` usage is
correct.

Knock-on effect: `unified_kyc_callback_get()` (`apiv6/Profile.php:16388`) finds
the customer by `transactionId` in this table. Because the row is never written,
the callback could never have matched on production either.

Side note, not verified and not in scope: `production/database.php:85` sets
`db_debug => (ENVIRONMENT !== 'production')`. A failed insert returning HTTP 500
suggests production's `ENVIRONMENT` is not exactly `production`. Worth
checking separately.

## How it will be fixed
Change line 2981 to the literal `'kyc_digitap'`. This matches:
- the same file's callback insert (`apiv6/Profile.php` in
  `unified_kyc_callback_get`, `'vendor' => 'kyc_digitap'`)
- what v2 writes on the same flow (`module_key` = `kyc_digitap`)

I chose this over `$fetchModule['vendor_name']` (`'digitap'`, the admin
console's value) because the mobile flow's rows should match each other
(send row plus callback row).

I'm not switching v6 to `getVendorModuleWithConfig()`. That would change the
`vendor_name == "digitap"` branch condition at 2955 and risk the authbridge
branch.
