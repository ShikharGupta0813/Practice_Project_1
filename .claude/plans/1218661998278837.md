# PART 1 — In simple words

## What the system does today
OneStack's support team uses Freshdesk, an online helpdesk, for support
tickets. In the admin panel, the "OneStack support tickets" page shows those
tickets by asking Freshdesk for them.

To talk to Freshdesk, our server needs three things: the Freshdesk address, an
API key and a password. Today the address is typed straight into the code, and
the key and password sit in a hidden file on the server (`.env`). None of them
are in the vendor settings book.

## What is wrong with it
Nothing is broken. But OneStack is moving every outside service into one new
settings book, so that settings can be seen and changed on the admin
configuration screens instead of by editing code or server files. KYC has
already moved. Customer Support hasn't.

## What we are going to change
Freshdesk's address, key and password will live in the new settings book, and
the support-ticket page will read them from there. Freshdesk is shared by the
whole of OneStack and doesn't belong to any one bank, so it uses the book's
global (all-banks) values.

If the settings haven't been entered yet, the page quietly falls back to
today's values, so nothing breaks while the data is being set up.

## What could go wrong
- If the settings are entered with a typo, the support page can't load tickets
  until they're corrected. The fallback only applies when the settings are
  missing, not when they're wrong.
- The service has to be created on the admin screens with exactly the names
  below. Otherwise the code won't find it and will keep using the fallback.

# PART 3 — The technical version

## Root cause / current state (onestackcbs)
- `application/modules/mobile_app/controllers/communication/Freshdesk.php:18-20`
  and `CommunicationFreshdesk.php:19-21`:
  ```php
  $this->api_key = $_ENV['FRESHDESK_API_KEY'];
  $this->password = $_ENV['FRESHDESK_PASSWORD'];
  $this->yourdomain = "https://onestack.freshdesk.com";
  ```
- Hardcoded domain in views: `mobile_app/views/communication/freshdesk/view-ticket.php:6`
  and `views/admin/freshdesk/view-ticket.php:19`.
- The old vendor tables are not read for Freshdesk anywhere.
- Production new tables (checked 2026-09-29) have no Customer Support row. The
  existing rows are kyc_aadhar, kyc_pan, insurance, investment, payment gateway,
  banl, upi 1.0 and upi 2.0.
- Admin users here are OneStack users. The session company_id is always null or
  0 (confirmed by the user), so `getVendorModuleConfig($companyId, …)` can't be
  used: it returns nothing for an empty company.

## How it will be fixed (Priyanka's KYC pattern, commits b99f29f795 / 56e46af0b3)
1. **Constant** in `application/config/constants.php`, next to `KYC_PAN` etc.:
   `define('CUSTOMER_SUPPORT_MODULE', 'customer_support_customer_support');`
   This is the slug the config screen generates
   (`ConfigProductMaster::addUpdateSubModule`, `url_title(group . '_' . child, 'underscore', TRUE)`)
   for Module Group **"Customer Support"** plus Sub Module **"Customer Support"**.
   That's the same shape as `insurance_insurance` and `banl_banl`.
2. **Helper** in `application/helpers/common_helper.php`, directly after
   `getVendorModuleConfig()`: `getGlobalVendorModuleConfig($childModuleSlug)`.
   - It returns the same array shape as `getVendorModuleConfig()`.
   - It resolves the active `tbl_vendor_module_mapping` row for the slug, with no
     company join, and loads its master values through her
     `getCompanyVendorConfiguration(0, 0, $vmmId)`. That function decrypts SECRET
     fields, and a company id of 0 means no bank override.
   - SQL is parameterised.
3. **Controllers** (`Freshdesk.php`, `CommunicationFreshdesk.php` constructors):
   read `DOMAIN`, `API_KEY` and `PASSWORD` from
   `getGlobalVendorModuleConfig(CUSTOMER_SUPPORT_MODULE)['config']`. If a value is
   empty, fall back to today's `$_ENV` value or the hardcoded domain. This is the
   same fallback pattern as her Authbridge constructor.
4. **Views**: replace the hardcoded domain with the controller's domain, passed
   in `$this->data`. First confirm which of the two `view-ticket.php` files is
   actually rendered, and change only the live one.

**Data setup** (done on the admin screens, not in code; rbank first, then production):

| Screen | Enter |
|---|---|
| Product Configuration → Vendor Master | Vendor **Freshdesk** |
| → Module Group Master | **Customer Support** |

| → Module – Vendor Mapping → Add Config | `DOMAIN` (TEXT), `API_KEY` (SECRET), `PASSWORD` (SECRET) with the global values. **Production DB holds production values, rbank DB holds rbank values.** |
