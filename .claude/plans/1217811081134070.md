# PART 1 — In simple words

## What the system does today

There is a page in the admin system where staff can upload a QR code file for
a bank. Behind the scenes, a small piece of program code (`upload_qr`) accepts
whatever file was sent, saves it into a folder on the server, and — if the file
looks like a PDF — converts it into an image. Anything that is not a PDF is
just treated as "a normal image" and left as-is.

## What is wrong with it

Two separate problems, in the same function:

1. **No check on what kind of file it actually is.** The code does work out the
   file's extension (the letters after the last dot, like `.png` or `.exe`),
   but only AFTER it has already saved the file to disk, and only to decide
   whether to run PDF-to-image conversion. It never uses that check to refuse
   a file it does not recognise. So today, someone could upload a file with any
   extension at all — including a program file — and it would be saved,
   unchanged, into a folder that is directly reachable from the internet by
   its web address. That is the same as leaving a door open for anyone who can
   reach this feature to plant a file on the server that could later be run as
   code.

2. **The everyday "can this person actually do this" check is skipped.** Most
   admin pages are protected by two layers: (a) you must be logged in, and (b)
   the system checks whether your specific staff role is allowed to perform
   this specific action. For this feature, only layer (a) is active — a person
   must still log in — but layer (b), the check on whether their role is
   actually permitted to upload QR files, silently does nothing. In practice
   this means any logged-in staff account, regardless of what they are
   supposed to be allowed to do, can call this feature. We could not find any
   button or page in the admin system that actually calls this feature today
   — so nobody is being asked to use it right now — but the door is still open
   for anyone who knows (or guesses) the web address to call it directly.

## What we are going to change

- Check the file type against a short allowed list (image and PDF types only,
  matching what the code already knows how to handle) BEFORE saving the file,
  and reject anything else with a clear error.
- Add the same everyday "is this staff member actually allowed to do this"
  check that this screen's sibling pages already use, so this stops being the
  one exception.

## What could go wrong

Very little, because nothing in the live admin system currently calls this
feature (verified by searching the whole codebase). The two changes are:
narrowing what file types are accepted (so a legitimate PDF/PNG/JPG upload
still works exactly as before), and adding a permission check that mirrors
what every sibling page on this same screen already requires. The only way
this could visibly change something is if some staff role that is currently
NOT granted "customer account management" edit access was relying on this
undocumented, unchecked route — which is the exact behaviour this task exists
to close.

# PART 3 — The technical version

## Root cause

`application/modules/cbs/controllers/CustomerAccountManagement.php:7111`,
`upload_qr()`:

```php
$fileName = time() . '_' . basename($file['name']);
$targetPath = $uploadDir . $fileName;
...
$ext  = strtolower(pathinfo($file['name'], PATHINFO_EXTENSION));
if (move_uploaded_file($file['tmp_name'], $targetPath)) {   // <- saved to disk first
    if ($ext === 'pdf') {
        ... convert to PNG ...
    } else {
        // Normal image upload — no check that it IS an image
        echo json_encode(['status' => 'success', 'path' => base_url('uploads/' . $fileName)]);
    }
}
```

`$targetPath` is under `FCPATH . 'uploads/'` (`:7117`), i.e. the web-root
`uploads/` folder — anything saved there is directly downloadable/executable
by URL. `$ext` is computed at `:7140` but is used only to branch between "PDF"
and "not PDF" — never to reject a file. There is no MIME check and no
allowlist anywhere in the function.

Second issue — routing/permissions. The route is defined at
`application/config/cbs-routes.php:1005`:

```php
$route['upload-qr'] = 'cbs/CustomerAccountManagement/upload_qr';
```

This has no `admin/` first segment. `Auth_Controller::__construct()`
(`application/core/MY_Controller.php:341-360`) derives the permission slug
from the URI's first two segments; when segment 1 is not `admin` it falls into
the `else` branch:

```php
} else {
    $this->url_slug   = '';
    $this->url_action = '';
    ...
}
$this->permissionservice->checkPermission(['slug' => $this->url_slug, 'action' => $this->url_action]);
```

With `action` empty, `PermissionService::checkPermission()`
(`application/libraries/PermissionService.php:24-29`) never sets
`$params['column']` and returns `false` immediately — but the call site above
never inspects that return value, so the result is a no-op either way. Login
IS still enforced (`CustomerAccountManagement` extends `Admin_Controller`
extends `Auth_Controller`, both of which check `ion_auth->logged_in()` /
`is_admin()`), but the granular "is this role allowed to edit customer
accounts" check never runs for this one route.

This exact mechanism (empty slug/action silently bypassing the permission
check, and the return value being ignored) is the same class of issue as the
broader Asana task on `PermissionService`/`MY_Controller` (gid
1217811081134060). This plan does **not** touch `PermissionService.php` or
`MY_Controller.php` — it adds a self-contained, explicit permission check
inside `upload_qr()` itself, the same way sibling actions on this exact
controller already do it, so the fix does not depend on or collide with that
broader (separately tracked) change.

**Confirmed no live caller.** Searched the whole repo:

```
grep -rn "upload-qr" .          -> only the route definition itself (cbs-routes.php:1005)
grep -rn "qr_file" .            -> 26 hits, all either language-file JSON strings or an
                                    unrelated same-named form field in
                                    application/modules/cbs/views/bank-management/customer-and-business-imports.php
                                    that posts to a DIFFERENT endpoint
                                    (admin/bank-list-add/cbs/add-qr-onboard-import-queue)
```

So this is a reachable-but-uncalled endpoint today — real risk to close, no
UI regression risk from fixing it.

**Existing convention on this exact controller** —
`CustomerAccountManagement.php:43` already gates `index()` with:

```php
if (checkControllerAccess('customers', 'customer_account_management', 'display_action')) {
```

`checkControllerAccess()` (`application/helpers/permission_helper.php:187-197`)
calls `redirect('admin/homepage')` on failure, which is wrong for a JSON/AJAX
endpoint like `upload_qr()`. The underlying bare check,
`checkMgmtPermissionAccess()` (`permission_helper.php:144`), has no redirect
side effect and just returns `true`/`false` — that is the right primitive to
call here so a denial can be returned as JSON instead of an HTML redirect.

## How it will be fixed

In `upload_qr()`, before anything else runs:

```php
if (!checkMgmtPermissionAccess('customers', 'customer_account_management', 'edit_action')) {
    echo json_encode(['status' => 'error', 'message' => 'Unauthorized access']);
    return;
}
```

(`edit_action` matches the `actionMap['edit']` column used everywhere else in
`PermissionService`/`permission_helper` for a data-modifying action, and
mirrors the `customers` / `customer_account_management` slug already used by
`index()` on this same controller.)

Then, right after `$ext` is computed and before `move_uploaded_file()` is
called:

```php
$allowedExt = ['jpg', 'jpeg', 'png', 'pdf'];
if (!in_array($ext, $allowedExt, true)) {
    echo json_encode(['status' => 'error', 'message' => 'Unsupported file type']);
    return;
}
```

This must run before the existing `move_uploaded_file($file['tmp_name'],
$targetPath)` call, not after — the current code moves the file first, then
looks at the extension.

Scope is held to these two additions. No change to routing, no change to
`PermissionService.php`/`MY_Controller.php`, no change to the PDF-conversion
or "normal image" success-path logic beyond gating what is allowed to reach
them.
