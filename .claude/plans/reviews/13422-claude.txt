[MEDIUM] application/modules/mobile_app/controllers/communication/Freshdesk.php:22 - Configured Freshdesk domain is used without validation for credentialed API calls
    category=Security confidence=0.82
    DOMAIN is now read from an admin-editable DB row and used, with only trimming, as the base URL for requests that send the API key and password. It is also written unescaped into an href in view-ticket.php. Each field falls back separately, so a DOMAIN that is mistyped or maliciously set while API_KEY/PASSWORD are still empty will send the production .env credentials to that host. It also allows a non-http(s) scheme in the rendered link. Before use, check that DOMAIN is https and that its host is on a Freshdesk allowlist, and consider falling back as a group (all three from the DB or all three from the old source) instead of per field. The same code is in CommunicationFreshdesk.php.

[LOW] application/helpers/common_helper.php:2673 - Helper returns priority and is_configured as constant 0 even when config is found
    category=Maintainability confidence=0.80
    getGlobalVendorModuleConfig() claims to return the same shape as getVendorModuleConfig(), but it never fills in 'priority' or 'is_configured'. A successful resolution therefore returns status=true with is_configured=0. Any future caller that checks is_configured, as the company-level resolver's callers may do, will wrongly treat the module as unconfigured. Either fill in these fields, for example is_configured = !empty($response['config']), or remove them from this helper's response.

[SUGGESTION] application/modules/mobile_app/controllers/communication/CommunicationFreshdesk.php:18 - Credential-resolution and fallback logic is duplicated across two controllers
    category=Maintainability confidence=0.80

Any later change, such as domain validation or dropping the .env fallback, must be made in both places and could drift. Consider one small shared helper, such as getFreshdeskCredentials(), that both constructors call.

PR Assessment
-------------

Problem Complexity
Level: MEDIUM
Summary: The code change itself is small. Moving API credentials to a new config source adds concerns about backward-compatible fallback, secret decryption, slug matching against admin-generated data, and a global (company 0) resolution path that the existing resolver does not support.
Factors:
  - Credentials move from environment/hardcoded values to admin-managed, encrypted DB configuration
  - A new global (non-company) resolution path is needed because OneStack users have a null/0 company_id
  - Correctness depends on the admin-entered data producing the exact slug the code expects
  - Backward-compatible fallback is required until rows exist in each environment (rbank, production)
  - Two controllers and a view share the credential and domain values

Fix Quality
Level: GOOD
Summary: The implementation follows the existing vendor-config pattern, uses a parameterized query, and keeps current behavior through fallbacks. It lacks domain validation, repeats the controller logic, and has no automated tests.
Strengths:
  - The new helper uses a parameterized query and reuses getCompanyVendorConfiguration() for secret decryption instead of reimplementing it
  - Fallbacks keep today's .env and hardcoded values until the config rows exist, which makes deployment low-risk
  - The ticket view's hardcoded domain is replaced with the configured domain, keeping links consistent with API calls
  - Trailing slashes are trimmed from the domain, which prevents double-slash URLs
Areas for Improvement:
  - Validate the scheme and host of the configured DOMAIN before sending credentials to it or rendering it in an href
  - Fall back as a group, not per field, so DB and .env values are never mixed
  - Move the repeated constructor logic into one shared helper
  - Fill in or remove the placeholder is_configured/priority fields in the helper response
  - Add at least a unit test for getGlobalVendorModuleConfig() covering the found, not-found and empty-slug cases
