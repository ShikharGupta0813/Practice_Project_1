[HIGH] application/modules/cbs/controllers/CbsCron.php:2554 - KYC-expiry cron destroys verified PAN name data
    category=Correctness confidence=0.85
    updateExpiredKycStatus overwrites verify_panname with 'NA' and clears is_pan_no_verified and is_aadhar_no_verified whenever a risk profile has expired, so the verified PAN name is permanently lost. If the risk profile is later renewed, the customer stays 'Not Verified' and must be fully re-verified, and there is no audit trail of the old value. The profile view already derives expiry from risk_expiry_date. Consider not mutating the verification data, or at least keep the original value (for example in a history or audit column) and document the reset as intended business behaviour.

[MEDIUM] application/config/cbs-routes.php:1492 - PR diff contains unrelated, undescribed functional changes
    category=General confidence=0.90
    Besides the import auth fix, the diff adds a new KYC-reset cron and route, changes KYC status logic in two places, changes NPCI table and column lookups, and filters the YES Bank error export. None of this is mentioned in the description or verification notes. It appears to come from merged onestackcbs commits while the PR targets onestackcbs-dev. Reviewers approving a security fix would also approve unreviewed data-mutating logic, so rebase the branch or split the PR so that only the intended changes are merged.

[MEDIUM] application/modules/cbs/controllers/CbsCron.php:2552 - Per-row UPDATE loop in KYC-expiry cron
    category=Performance confidence=0.85
    The cron loads every expired customer ID into memory and then runs one UPDATE per customer, with no batching or transaction. On the first run against production this could mean many thousands of individual writes on tbl_customers, and a failure partway through leaves the data partly updated. Use a single set-based UPDATE ... JOIN, or chunked where_in updates inside a transaction.

[MEDIUM] application/modules/cbs/controllers/CbsCron.php:2542 - Aadhaar-only verified customers never reset on expiry
    category=Correctness confidence=0.80
    The cron only selects customers whose verify_panname is non-empty and not 'NA'. Customers verified only through Aadhaar (is_aadhar_no_verified = 1 with no verified PAN name) keep their flag after the risk profile expires. CustomersListModel reports KYC as 'Not Done' only when both flags are 0, so these customers still appear as KYC done in the list, which is inconsistent with the profile page. Base the filter on the verification flags rather than on verify_panname.

[LOW] application/modules/cbs/views/customer-profile-management/kyc-information.php:266 - Database query and business rule placed in view
    category=Architecture confidence=0.85
    The view now calls $this->CommonModel->select on tbl_customer_risk_profile and decides the KYC-expiry rule inline, handling both result shapes defensively. This puts data access and a KYC business rule in the presentation layer, and the same rule is implemented differently in the cron and in CustomersListModel. Compute kycStatus in the controller or a shared service so all three stay consistent.
