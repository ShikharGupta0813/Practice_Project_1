[MEDIUM] application/modules/cbs/controllers/CbsCron.php:2542 - Expiry cron skips customers who are verified only by Aadhaar

So a customer verified only by Aadhaar whose risk profile has expired keeps is_aadhar_no_verified = 1, and the customer list keeps showing their KYC as done. Select on the verification flags (is_pan_no_verified = 1 OR is_aadhar_no_verified = 1) so all three places use the same definition of verified.

[MEDIUM] application/modules/cbs/views/customer-profile-management/kyc-information.php:266 - Database query and KYC-expiry business rule placed in a view
    category=Architecture confidence=0.85
    The view now calls CommonModel->select on tbl_customer_risk_profile and decides KYC validity itself. That puts data access and a compliance rule in the presentation layer and duplicates the expiry logic in the cron. The rules can drift apart, and this one can't be unit-tested. Compute the KYC status in the controller or model (kycInformation/contactAndKyc) and pass it to the view.

[LOW] application/modules/cbs/controllers/CbsCron.php:2553 - One UPDATE per customer, with no batching or transaction
    category=Performance confidence=0.85
    The cron loads every expired customer ID into memory and runs one UPDATE per row. On large tenants this means thousands of round trips, and a failure partway through leaves a partial update. It also increments updated_count without checking whether the update succeeded. A single set-based UPDATE (or where_in in chunks) would be faster and atomic, and would give an accurate affected-row count.

PR Assessment
-------------

Problem Complexity
Level: MEDIUM
Summary: The headline fix is a single-endpoint tenant-isolation check, but the diff also bundles KYC-expiry rules, NPCI lookup changes and an export filter fix. Together these touch several modules and regulatory-sensitive data.
Factors:
  - The endpoint returns CBS credentials and settlement account data, so an authorization mistake has a high impact
  - Distinguishing tenants relies on session state (company_id) rather than an explicit role
  - The access check depends on tbl_company_master.company_gstn matching tbl_bank_onboarding.gst_number in production
  - The bundled KYC-expiry change spans a cron, a view and a list query, and they must stay consistent
  - The bundled NPCI changes switch which tables and key columns the XML request/response lookups use

Fix Quality
Level: NEEDS_IMPROVEMENT
Summary: For bank users, the fetchBankDetails guard is fail-closed and correctly normalised, which fixes the reported cross-bank leak. But it grants unrestricted access based on the absence of company_id, and the PR carries unrelated changes, one of which does not achieve its stated goal.
Strengths:
  - The guard is fail-closed for bank users: a missing company row, an empty company GSTIN or a mismatch all return the existing generic error
  - GSTINs are compared case-insensitively and whitespace-trimmed, which avoids false denials
  - The denial response matches the 'not found' response, so it does not reveal which GSTINs exist
  - The fix is applied to both copies of the controller, and the PR description gives a production SQL check for data consistency
Areas for Improvement:
  - Grant cross-tenant access only to an explicitly identified OneStack user, not to any session without company_id
  - Add automated tests for the allow/deny cases instead of relying only on an isolated manual check
  - Split the unrelated merged changes (KYC expiry cron, NPCI table switch, YES Bank export, PAN bankid) out of this security PR so they are reviewed on their own
  - Fix the YES Bank export subquery so it actually correlates on the attempt type
  - Move the risk-expiry query out of the view and use one KYC-verified definition across the cron, the view and the customer list
