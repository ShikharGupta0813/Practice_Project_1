[MEDIUM] application/core/MY_Security.php:51 - Stale body token takes precedence over the fresh header token
    category=Correctness confidence=0.82
    The header is only used when $_POST[csrf_test_name] is absent. Once protection is on, form_open() prints a hidden csrf_test_name field at render time, and csrf_regenerate=TRUE rotates the token after every POST. So an AJAX call that sends serialize() or FormData(form) without a submit event sends the stale field, and the request gets a 403 even though csrf.js attached the current token as a header. The header is read from the cookie at send time and is always current, so prefer it whenever it is present.

PR Assessment
-------------

Problem Complexity
Level: HIGH
Summary: Turning on CSRF safely in a large CI3 codebase means covering about 2,500 AJAX calls and hundreds of forms with a rotating token. It also needs the stock token check extended and every machine-to-machine caller (NPCI, bank, mobile, cron) correctly exempted, because a missed exemption breaks payments.
Factors:
  - csrf_regenerate=TRUE rotates the token after every POST, so tokens must be read at send time
  - Stock CI3 accepts the token only from $_POST, so JSON-body and header-based requests need a server extension
  - The exempt list for payment, NPCI and bank callbacks is safety-critical and must be derived from route files and production traffic
  - Global monkey-patching of XHR, fetch and form submit affects every page on every surface
  - Behaviour must not change while protection stays off

Fix Quality
Level: NEEDS_IMPROVEMENT
Summary: The core design is sound and matches the agreed plan: the token is read from the cookie at send time, it is only sent to the same origin, a header fallback is added on the server, and the exempt list is deployed with the code. However, the mechanical </head> insertion broke a production page, and the token-precedence logic in MY_Security undermines the header approach for serialized forms.
Strengths:
  - Reads the token from the cookie at send time, which avoids staleness from csrf_regenerate
  - Same-origin checks on XHR, fetch and forms, so the token is never sent to NPCI or other external origins
  - Covers scripted form.submit() and submitter formaction/formmethod, and uses getAttribute to avoid shadowing by named inputs
  - An idempotent guard (window.__csrfTokenSupport) makes double inclusion safe
  - MY_Security delegates to parent::csrf_verify(), keeps honouring config csrf_exclude_uris, and has no effect while protection is off
  - The exempt list is commented by caller type
Areas for Improvement:
  - Remove the csrf.js injection from recon-dashboard.php, and audit the other replaced </head> occurrences to confirm each is real document markup
  - Prefer the X-CSRF-Token header over a $_POST token when both are present
  - Reconcile exemptions such as home/.* (listed as keep-protected in the plan) and add a comment for each uncommented exemption
  - No automated tests or a documented local verification for the header path and the exempt-URI matching
