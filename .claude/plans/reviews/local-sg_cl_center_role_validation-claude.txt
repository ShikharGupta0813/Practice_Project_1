Problem Complexity
Level: LOW
Summary: This is a single-endpoint input-validation fix: restrict one form field to a fixed set of four global role IDs and use the validated value everywhere it is written. Tenant scoping is already enforced by the existing bank_id session check.
Factors:
  - Only one controller method is affected, and it has a single AJAX caller
  - The allowed roles are a small, global, fixed set with no per-tenant rules
  - The field feeds a security-sensitive privilege assignment (console user cbs_role_id)
  - One edge case matters: legacy contacts holding roles outside the allowlist

Fix Quality
Level: GOOD
Summary: The change fixes the root cause with the framework's built-in in_list rule and replaces every raw $_POST['role'] use in the method. Invalid input goes down the existing error path, and nothing is written. It is minimal and follows the business plan, but no automated regression coverage is added.
Strengths:
  - A server-side allowlist (in_list[5,7,8,9]) replaces a character-set check that allowed any role ID
  - All five raw $_POST['role'] usages are replaced with a single $role_id read through the input layer after validation
  - Rejections reuse the existing form_validation failure path, so no partial contact or user rows are written
  - The per-field custom error message gives the user a clear 'Please select a valid Role' prompt
Areas for Improvement:
  - The allowed role IDs are now hardcoded in both the controller and the view. A shared constant or config entry would stop the server allowlist and the dropdown from drifting apart.
  - No automated regression test checks that disallowed roles (e.g. 2, 999999, non-numeric) are rejected and write no rows.
