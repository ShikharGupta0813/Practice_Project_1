PR Assessment
-------------

Problem Complexity
Level: LOW
Summary: This is a single authorization check that ties a request parameter to the tenant in the session, placed at the start of one endpoint that is duplicated in two controllers. There is one business rule and no state changes or integrations.
Factors:
  - Single business rule: bank users may only read their own bank's record
  - Two user classes, told apart by whether company_id is in the session
  - Same endpoint duplicated in two controller files
  - Sensitive data involved (CBS API keys, contact PII) raises the stakes but not the complexity

Fix Quality
Level: GOOD
Summary: The check is correct and small, and it runs before any sensitive data is queried. It denies access when the company record or its GSTN is missing, and it is applied the same way to both copies of the endpoint.
Strengths:
  - Check runs before the sensitive select, so no data is read for requests that will be rejected
  - Denies access when the company row is missing or company_gstn is empty, instead of allowing it
  - Case- and whitespace-insensitive comparison avoids false rejections from formatting differences
  - Applied the same way in both duplicated controllers
  - Uses the existing CommonModel/DbTable query path, not raw SQL
Areas for Improvement:
  - Access is decided by whether company_id is present in the session, so a bank-user session that lacks company_id gets unrestricted access. Consider checking for an explicit OneStack role instead.
  - The rejection message 'Invalid user id' does not describe the actual failure (GSTN does not belong to the caller's bank). This makes client-side handling and support triage harder.
  - The same guard is copied into two files; a shared helper would stop them drifting apart in future fixes
  - No regression test or documented manual check covers the cross-tenant rejection case
