  What Changed: Every customer-data method in the mobile-app DashboardDefaultState controller (the apiv2 and apiv6 copies, plus the old api/DashboardDefaultSatet copy) now uses the customer ID from the verified login token ($this->customerId). The three write methods (updateName, updateMobileNoEmail, verifyOpt) now also refuse child logins (!$this->api_child_Id) before doing any work. The old api/ copy's updateMobileNoEmail and verifyOpt, which were gated on request fields, are now gated on the token customer.
  Files Modified: application/modules/mobile_app/controllers/api/DashboardDefaultSatet.php, application/modules/mobile_app/controllers/apiv2/DashboardDefaultState.php, application/modules/mobile_app/controllers/apiv6/DashboardDefaultState.php
  High-Level Impact: Closes a broken-access-control / IDOR path. Before this change, any logged-in customer could put another customer's ID in the request and read that customer's profile, transactions and tickets, rename them, or change their mobile/email via an OTP sent to the attacker's own phone. Because login is by mobile OTP, the last one meant account takeover. The server now always acts on the customer named in the token. Child logins can no longer write to the parent's record, because they are rejected before the write instead of receiving 'No Access' after it. Any app build that sends a customer_id different from the token will now silently act on the token's customer. No query shapes, schema or response formats change.
  Potential Review Focus: 1) Check that no remaining line in the three files uses $apiRequest['customer_id'] to choose a record; only log lines should still read it. 2) In verifyOpt, both $targetCustomerId assignments (the pre-check and the final update) should use the token customer, and the child gate should run before the OTP_LOG update. 3) For child logins, the trailing 'No Access' block should still overwrite the response on the read endpoints, which still run their queries for the parent's ID. 4) apiv2 and apiv6 should stay identical apart from decrypt_api_request vs decrypt_api_request_gcm. 5) Staging tests: send A's token with customer_id = B and confirm only A is affected, on both /api/v2 and /api/v6.

PR Assessment
-------------

Problem Complexity
Level: MEDIUM
Summary: The fix is mechanically simple, but it is a security-critical authorization change: an account-takeover path across nine methods in three copies of the same controller, plus the child-login rules. Getting any one call site wrong keeps the vulnerability open.
Factors:
  - Broken access control that leads to account takeover through the mobile-number change and OTP verify flow
  - Nine methods and about 45 call sites, duplicated across three near-identical controller copies (api, apiv2, apiv6)
  - Child-login semantics: the JWT for a child carries the parent's customer_id, so switching to the token ID alone would have let child logins write to the parent
  - Backward-compatibility risk for app builds that send a customer_id different from the token
  - Interaction with an earlier partial fix (affaa8a262) that introduced the request-over-token fallback in verifyOpt

Fix Quality
Level: GOOD
Summary: The fix consistently takes the customer from the verified token at every identified call site in all three copies. It also adds a child-login gate on the write paths, which prevents a new regression the change would otherwise have caused. There are no automated tests; verification relies on php -l, a grep, and manual staging steps.
Strengths:
  - Uses $this->customerId (from jwt->authorizeToken) at every call site listed in the business context, including both $targetCustomerId assignments in verifyOpt and both company lookups in updateMobileNoEmail
  - Adds !$this->api_child_Id to the write-method gates, so a child login can no longer write to the parent's record now that the request ID is ignored
  - The old api/ copy's request-field gates (isset($apiRequest['customer_id']) and isset($apiRequest['otp']) alone) are now tied to the authenticated customer
  - The apiv2 and apiv6 edits are identical, so the two copies do not drift apart
  - Log lines that record the client-sent customer_id are kept, which helps spot abuse attempts
  - Minimal, targeted diff with no unrelated changes
Areas for Improvement:
  - No automated regression test proves that a request with customer_id = B and A's token acts only on A; that is the key security property of this change
  - Read endpoints (myTransactions, getRecentTickets, getAllTickets, transactionDetails) still run their queries for the parent when a child logs in and rely on the trailing 'No Access' overwrite; gating these on !$this->api_child_Id too would avoid the wasted queries and make the rule explicit
  - The logic is still triplicated across api/, apiv2/ and apiv6/, so future security fixes must be applied three times; this PR does not worsen that
