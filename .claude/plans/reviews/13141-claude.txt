[HIGH] application/modules/mobile_app/controllers/npci-ibmb/NpciIBMB.php:510 - Lockout is fully bypassed when mobile number cannot be resolved
    category=Security confidence=0.87
    The new attempt-limiting check only runs `if (!empty($mobileNo) && ...)`, so when both the custDetails lookup and the CUSTOMERS fallback fail to return a mobile_no, PIN verification proceeds with no cap on attempts at all — reintroducing the exact unlimited-guess vulnerability this PR is meant to fix. Since this is a payment-authorization credential, any code path that leaves mobile_no empty (deleted/malformed customer record, lookup failure) becomes an unprotected brute-force vector. Recommend failing closed (deny or use a fallback key such as customer_id/account_no) when mobile_no cannot be determined, rather than skipping the check.

[MEDIUM] application/modules/mobile_app/controllers/npci-ibmb/NpciIBMB.php:505 - Client-spoofable X-Forwarded-For trusted for stored IP
    category=Security confidence=0.85
    `$ip_address` is taken directly from `HTTP_X_FORWARDED_FOR` when present, which is fully attacker-controlled unless the app sits behind a trusted proxy that strips/overwrites it. Since this value is only persisted for logging and is not used in the lockout decision itself, the impact is limited to corrupting the audit trail used to investigate brute-force attempts against this payment credential, but that undermines the value of the new logging for incident response. Prefer taking the first trusted proxy hop (e.g., REMOTE_ADDR, or a validated proxy chain) rather than the raw header value.

[MEDIUM] application/modules/mobile_app/controllers/npci-ibmb/NpciIBMB.php:510 - Check-then-log attempt counting is not atomic
    category=Concurrency confidence=0.80
    The attempt count is read via `is_max_otp_attempts_exceeded` and only written after verification fails via `mobile_otp_sent_logs`, with no locking or atomic increment between the two. An attacker sending several concurrent M-PIN guesses can have all of them pass the count check before any failure is logged, allowing a burst of guesses beyond `max_attempts` per window. For a control specifically meant to stop automated/brute-force guessing of a payment PIN, this gap materially weakens the protection under concurrent requests.

[LOW] application/modules/mobile_app/controllers/npci-ibmb/NpciIBMB.php:1219 - No automated tests for new lockout logic
    category=Testing confidence=0.82
    The PR adds new security-critical branching (mobile number resolution, attempt counting, threshold comparison, lockout short-circuit) with no accompanying unit or integration tests. Given this replaces the previous 'no counter, lockout, or delay' gap for a payment-authorization credential, untested edge cases (empty mobile number, exact threshold boundary, window expiry) risk silently regressing the fix in future changes.
