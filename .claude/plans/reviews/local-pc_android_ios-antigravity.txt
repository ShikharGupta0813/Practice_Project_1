PR Assessment -- Problem Complexity & Fix Quality

In addition to the findings above, every review produces two further, independent, PR-level assessments. These are never combined into a single score, and they are never a judgement of the developer -- only of this PR's problem and this PR's implementation.

Problem Complexity

Definition: how difficult the problem addressed by this PR actually is, considering both business and technical complexity. If a Business Context document is supplied below (after this prompt, before the PR context), use it to understand business rules, scenarios, and constraints relevant to complexity -- but do not use it to generate business-rule findings here; a separate review pass handles Business Context validation.

Consider:

* Business complexity -- number of business rules, business scenarios, exceptions, regulatory/compliance requirements, business dependencies, impact of incorrect behaviour.
* Technical complexity -- number of components/modules involved, algorithmic complexity, data model changes, API changes, external integrations, distributed-system behaviour, state management, concurrency, backward compatibility, security requirements, performance requirements.
* Scope complexity -- number of functional areas affected, multiple services/modules, database changes, API changes, configuration changes, infrastructure/deployment changes, data migration. Scope alone must never determine the classification by itself.
* Edge-case complexity -- number of meaningful edge cases, failure scenarios, retry behaviour, duplicate requests, race conditions, partial failures, data consistency, backward compatibility.

Classify as exactly one of:

* LOW -- Straightforward problem with limited business and technical considerations.
* MEDIUM -- Problem involving multiple conditions, moderate dependencies, or several implementation considerations.
* HIGH -- Problem involving significant business rules, integrations, state management, architectural or technical considerations.
* VERY_HIGH -- Problem involving substantial cross-system, distributed, regulatory, architectural, or business complexity.

Provide a concise summary explaining the classification and a list of the specific factors that drove it.

Fix Quality

Definition: how effectively the implementation contained in this PR solves the identified problem, limited to what is in the diff and the context supplied to you. This is not a generalized assessment of the developer.

Consider:

* Correctness -- does the implementation solve the stated problem, correctly implement business rules, correctly handle relevant scenarios; are there functional defects?
* Completeness -- are the stated requirements addressed, are important edge cases handled, are failure paths considered, are required supporting changes included?
* Design quality -- separation of concerns, modularity, appropriate abstraction, architectural consistency, avoidance of unnecessary complexity.
* Maintainability -- readability, naming, code structure, duplication, ease of future modification, appropriate documentation/comments.
* Robustness -- input validation, error handling, retry behaviour, idempotency, concurrency considerations, unexpected inputs, failure recovery.
* Testing -- unit/integration/regression tests, negative scenarios, edge cases, whether appropriate tests were added or modified.
* Security (where applicable) -- authentication, authorization, input validation, sensitive-data handling, secrets, injection risks, sensitive information in logs.
* Performance (where applicable) -- database queries, algorithmic efficiency, network calls, memory usage, N+1 queries, unnecessary processing, caching.

Classify as exactly one of:

* POOR -- Does not adequately solve the problem or introduces significant issues.
* NEEDS_IMPROVEMENT -- Solves the primary problem but has important quality gaps.
* GOOD -- Correct and reasonably maintainable implementation with no major issues.

+    private function get_platform_version_details($companyId, $device_type)
+    {
+        $this->sdb->select('apk_file, apk_version, version, created_on, siteload_bitly_link, min_version');
+        $this->sdb->where(array(
+            'company_id' => $companyId,
+            'build_status' => 'Completed',
+            'status' => 'Active',
+            'device_type' => $device_type
+        ));
+        $this->sdb->order_by('id', 'desc');
+        $builds = $this->sdb->get(DbTable::COMPANY_APK_FILES)->result_array();
+
+        if (empty($builds)) {
+            return array('max_row' => null, 'min_version' => '', 'max_version' => '');
+        }
+
+        $maxRow = null;
+        $minRow = null;
+
+        if ($device_type === 'ios') {
+            //IOS max/min are set explicitly by BankManagement::saveIosManualVersion(), which always
+            //deactivates every other row first - so whichever row is flagged min_version=0 (max) or
+            //min_version=1 (min) is exactly what was most recently saved, taken as-is with no
+            //numeric comparison, so a deliberately lower re-save is never masked by an older,
+            //numerically higher row.
+            foreach ($builds as $row) {
+                if ((int)$row['min_version'] === 1) {
+                    if ($minRow === null) {
+                        $minRow = $row;
+                    }
+                } else {
+                    if ($maxRow === null) {
+                        $maxRow = $row;
+                    }
+                }
+            }
+            //When min and max were saved as the same value, only one row exists (flagged min_version=1).
+            if ($maxRow === null) {
+                $maxRow = $minRow;
+            }
+            if ($minRow === null) {
+                $minRow = $maxRow;
+            }
+        } else {
+            //Android's min_version flag is set independently per build from the admin build-list
+            //screen (CompanyMaster::updateAppBuildData_n) and isn't tied to which build is newest,
+            //so max stays the numerically highest active build via version_compare() - unchanged
+            //from before the iOS min/max feature existed, and not the iOS flag-based selection above.
+            foreach ($builds as $row) {
+                $ver = trim($row['apk_version']);
+                if ($ver === '') continue;
+
+                if ($maxRow === null || version_compare($ver, $maxRow['apk_version'], '>')) {
+                    $maxRow = $row;
+                }
+                if ((int)$row['min_version'] === 1) {
+                    if ($minRow === null || version_compare($ver, $minRow['apk_version'], '<')) {
+                        $minRow = $row;
+                    }
+                }
+            }
+            if ($minRow === null) {
+                $minRow = $maxRow;
+            }
+        }
+
+        return array(
+            'max_row' => $maxRow,
+            'min_version' => $minRow ? $minRow['apk_version'] : '',
+            'max_version' => $maxRow ? $maxRow['apk_version'] : ''
+        );
+    }
