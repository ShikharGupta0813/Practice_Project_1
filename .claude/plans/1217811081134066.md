# PART 1 — In simple words

## What the system does today

This is the version 2 copy of the partner-onboarding intake. It does the same job
as the version 1 one: an outside computer sends a bundle of partner details with
scanned documents inside, and this file saves those documents to the server.

As before, the sender supplies three things per document — the document itself,
the name to save it under, and the folder to file it into — and the system uses
all three exactly as given.

## What is wrong with it

The same problem as the version 1 file, in more places. The sender picks the
folder, so files can be aimed at places they should never reach. The sender picks
the name and the type, so a small program can be sent instead of a scan. And the
saved file is then marked so anything on the server can change it.

The reason this is a separate task rather than the same one is simply that it is a
separate file. The two were copied from each other and have drifted apart, so
fixing one does nothing for the other.

Same real-world consequence: an outsider could get their own program onto the
bank's server.

## What we are going to change

Exactly the same change as the version 1 file, using the same shared piece of code.
Every saved document goes into one folder we control, under a name we clean, only
if it is a real document type, without the "anyone can change this" permission.

## What could go wrong

Same two risks as the version 1 file: if real senders genuinely need to choose
their own folders, forcing one folder breaks them; and if they legitimately send
document types outside our allowed list, those uploads start failing. Both are
settled by looking at what production actually receives before shipping.

One extra risk specific to this file: it has 18 save points rather than 16, and
they are not all identical. Each one needs converting individually rather than by
find-and-replace.

# PART 3 — The technical version

## Root cause

Same defect class as task 34, in
`application/modules/mobile_app/controllers/apiv2/FetchProductionDetails.php`.
First site at :52 has the identical shape:

```php
$data = base64_decode($base_64_encode_agreement);
$folder_path = FCPATH.$folderpath.$filename;
file_put_contents($folder_path, $data);
chmod($folder_path, 0777);
```

Caller-controlled `$folderpath` and `$filename` concatenated onto `FCPATH`, no
`basename()`, no extension allowlist, no `realpath()` containment, then
world-writable permissions.

`class FetchProductionDetails extends REST_Controller` at line 5 — same
unauthenticated exposure as task 34 while `rest_auth = FALSE`.

**Line count discrepancy with the task title.** The title says "12/18 write
sites". The file has **18** `file_put_contents` calls. Reading them, all 18 build
their path from request-supplied values; I could not reproduce a split that makes
only 12 of them vulnerable. **Plan targets all 18.** If the reviewer knows why 6
were excluded, that should be raised before merge.

## How it will be fixed

Use the shared `secure_store_document()` helper created in task 34
(`application/helpers/secure_upload_helper.php`). Do not write a second copy.

Replace each of the 18 `file_put_contents` + `chmod` pairs with a helper call,
preserving each site's existing success/failure handling.
