# PART 1 — In simple words

## What the system does today

Before the bank pulls a company's commercial credit report, it checks that
whoever is asking really controls the registered mobile number. It does this the
usual way: it makes up a six-digit code, texts it to that number, and asks for
the code back.

The code is stored, along with the mobile number it was sent to and a time ten
minutes in the future when it stops being valid. When someone types a code in,
the system looks for a stored code that matches that mobile number, is still
marked unused, and matches what was typed. If it finds one, the check passes.

## What is wrong with it

Nobody counts the wrong guesses.

There is no limit on how many times a code can be tried. Get it wrong, and the
system says "Invalid OTP. Please enter the correct OTP." and waits for the next
attempt. Wrong guesses do not use the code up, do not lock anything, and are not
recorded anywhere.

A six-digit code has nine hundred thousand possible values, and the code stays
valid for ten minutes. A person guessing by hand would never get there. A
computer program sending guesses as fast as the server will answer will — a few
hundred guesses a second gets through a large part of that range inside the
window, and it only has to be lucky once.

What that means for a real person: someone who knows a company's registered
mobile number, but does not have the phone, can trigger the code and then guess
until they get in. They do not need to intercept the text message. At the end of
it they get the company's commercial credit report — its borrowing, its
repayment history, its outstanding debts.

Nothing suggests this has happened. But the door is standing open, and the only
reason it has not been walked through is that nobody has tried.

## What we are going to change

Count the failed attempts, and stop accepting new ones once there have been too
many from that mobile number in a short window. This is not a new invention: the
mobile app already does exactly this for its own login codes, using a table that
already exists and settings that are already configured. We will use the same
table, the same settings and the same style of check.

## What could go wrong

The real risk is locking out a genuine user. Someone who mistypes the code a few
times will be told to wait rather than being allowed to keep trying. That is the
intended trade-off — it is what makes guessing impractical — but it does mean a
frustrated user where previously there was none.

The limit and the window are not new numbers invented here. They are the ones the
mobile app already uses for its login codes, already set on the live system, and
already judged acceptable for real customers. If they turn out to be too strict
for this screen, they can be changed without touching the code.

A second, smaller risk: an attacker could deliberately trigger the lockout on
somebody else's mobile number to block them. That is a real downside of every
limit of this kind, and it is much less bad than leaving the guessing open.

| Word | What it means, simply |
|---|---|
| OTP | One-Time Password — a short code sent by text, used once to prove you hold the phone. |
| Brute force | Trying every possible value until one works, using a program rather than a person. |
| CBR | Commercial Bureau Report — the credit report for a business rather than a person. |
| Rate limit | A cap on how many times something may be tried in a period of time. |
| Controller | A file of program code that handles one screen or one kind of request. |
| Constant | A setting fixed once at start-up and used by name throughout the code. |
| Lockout window | The stretch of time the cap is measured over — for example, five failures in fifteen minutes. |

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/mis/EquifaxController.php`,
`verifyCommercialCbrOtp()` at lines 271-336.

The verification is a single unbounded lookup:

```php
$otpRow = $writeDb
    ->select('id, expiry_on')
    ->from(DbTable::OTP_LOG)
    ->where(array(
        'company_id'  => $companyId,
        'mobile_no'   => $mobileNo,
        'otp'         => $otp,
        'is_verified' => '0'
    ))
    ->order_by('id', 'DESC')->limit(1)->get()->row_array();

if (empty($otpRow)) {
    return $this->response([
        'status'  => false,
        'message' => 'Invalid OTP. Please enter the correct OTP.'
    ], 400);
}
```

On a miss it returns 400 and nothing else happens. Specifically:

- No counter is incremented and no row is written anywhere.
- The candidate OTP row keeps `is_verified = '0'`, so it stays matchable.
- There is no delay, no captcha, no IP or mobile-number throttle.
- The route is reached through `index_post('verify-commercial-cbr-otp')`
  (`EquifaxController.php:93-96`), so each guess is one plain POST.

The OTP itself is `rand(100000, 999999)` (line ~199 of the send path) — a 6-digit
space of 900,000 — with `expiry_on` set to `+10 minutes` (line 212). Unlimited
guesses against a 900,000-value space inside a 10-minute window is a practical
attack, not a theoretical one.

`rand()` rather than `random_int()` is a second, weaker issue (predictable PRNG).
Out of scope here; worth its own task.

## How it will be fixed

Reuse the throttle the mobile app already uses for login OTPs. Verified present
on `onestackcbs`:

- Table `DbTable::MOBILE_LOGIN_ATTEMPT` = `tbl_mobile_login_attempts`, columns
  `ip_address`, `mobile_no`, `time`, `event` (`DbTable.php:176`).
- Constants `MOBILE_OTP_MAX_ATTEMPTS` and `MOBILE_OTP_ATTEMPTS_IN_SECONDS`, both
  read from `$_ENV` at `application/config/constants.php:196-197` — already
  defined on production, or `constants.php` would fatal on every request.
- The pattern in `apiv7/Profile.php`: check with
  `is_max_otp_attempts_exceeded($mobileNo, 'login_otp_verify', $time, $max)`
  (line 144), and record a row on each **failed** verification via
  `mobile_otp_sent_logs($ip, $mobileNo, 'login_otp_verify')` (line 1223, in the
  `else` branch where the OTP did not match).

Two small helpers get local copies in `EquifaxController`, mirroring
`apiv7/Profile.php:1978-1989` and `2028-2032`. This deliberately duplicates rather
than extracts: the same method already exists in four controllers
(`apiv2`/`apiv3`/`apiv6`/`apiv7` `Profile.php`) plus `CommonFunctions.php`, so a
fifth local copy is the established house style, and `.claude/CLAUDE.md` says to
match surrounding style rather than introduce a new pattern mid-file.

The autoloaded `CommonFunctions::is_max_otp_attempts_exceeded()` is deliberately
**not** reused: it queries `DbTable::CONSOLE_OTP_ATTEMPT`
(`tbl_console_otp_attempts`, `CommonFunctions.php:5012`), which is the admin
console's table, not the mobile one. Calling it would count the wrong rows.

New event name: `equifax_cbr_otp_verify`, so this throttle is independent of the
mobile login throttle and one cannot lock out the other.

Resulting shape of `verifyCommercialCbrOtp()`:

1. Existing `$companyId` / `$mobileNo` / `$otp` resolution and the two existing
   400 guards, unchanged.
2. **New** — before the lookup:
   ```php
   if ($this->is_max_otp_attempts_exceeded($mobileNo, 'equifax_cbr_otp_verify', MOBILE_OTP_ATTEMPTS_IN_SECONDS, MOBILE_OTP_MAX_ATTEMPTS)) {
       return $this->response([
           'status'  => false,
           'message' => 'Maximum attempts reached. Please try again after some time.'
       ], 429);
   }
   ```
3. Existing lookup, unchanged.
4. **New** — inside the existing `if (empty($otpRow))` branch, before the 400:
   ```php
   $this->equifax_otp_attempt_log($this->input->ip_address(), $mobileNo, 'equifax_cbr_otp_verify');
   ```
5. Existing expiry check and success path, unchanged.

`$this->input->ip_address()` is used rather than reading `X-Forwarded-For`
directly as `apiv7/Profile.php:133` does, because CI's accessor validates the
value; a raw header is attacker-controlled and would let each guess present a
different IP. The throttle keys on `mobile_no` regardless, so the IP is recorded
for forensics only.

Status `429` is used for the throttle response; the existing failure paths keep
`400`.
