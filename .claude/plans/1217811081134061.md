# PART 1 — In simple words

## What the system does today

The bank's mobile app is a program on a customer's phone. It holds no account
data itself — every time it needs a balance, a statement, or to make a
payment, it asks the bank's server over the internet.

Because those requests travel over the open internet, the server has to know
who is asking. When a customer signs in, the server hands the app a **pass** —
a long scrambled string proving "this is customer 12345". The app attaches
that pass to every later request, like a wristband at a festival gate. The
guard at the door is supposed to check every wristband and turn away anyone
without one.

Separately, some of these same web addresses aren't used by customers at all
— they're used by other companies' computers (India's national payments
network NPCI, the bank's SMS/WhatsApp delivery vendor, a credit-check
company), and by the bank's own staff running internal tools (like copying
settings from the test system into the live one).

## What is wrong with it

**For customers:** the guard only checks the wristband **if the visitor
offers one**. A request with no wristband at all is waved straight through —
not flagged, not questioned, just processed as if it were a valid customer.
We confirmed this is not theoretical: production traffic today includes real
phone requests hitting real account-balance and transaction-history addresses
with no wristband attached at all (285 such requests in one day, out of
68,449 total). Those particular calls happen to be turned away by a
by-hand check one developer remembered to write in one method — but nothing
in the system *requires* every method to remember that check, so the next
one that's written, or the other 45 files' worth of methods that already
exist, can silently skip it and nobody would know.

**For the bank's own internal tools:** there is no guard at all on some of
them. Several addresses let someone copy live banking configuration between
the test and production systems with no check that the caller is actually
staff.

**Separately, and left as-is by explicit decision:** the addresses used by
other companies' computers (India's national payments network, the bank's
SMS/WhatsApp delivery vendor, a chatbot integration) also have no guard
today. One of these hands out a customer's account balance and full
transaction history to a chatbot platform with no check at all. **This plan
does not close that gap** — the task owner was shown this specific risk and
chose to leave these untouched here, so it is written down plainly rather
than fixed quietly or left unmentioned.

**What this means for a real person.** We have no evidence anyone has abused
this. But as the code stands, a stranger does not need a stolen password or a
stolen phone to reach some of this — only the address. For a bank, that is
the difference between a locked door and a closed one. This plan closes that
door for customers and for internal staff tools; the outside-company doors
remain open, on purpose, for now.

## What we are going to change

Two fixes, one for each kind of caller this task covers:

1. **Customers (the phone app):** flip the rule from "check the wristband if
   one is shown" to "refuse the request unless a valid wristband is shown" —
   enforced in one place all 46 customer-facing addresses share, not
   scattered by-hand checks. A short, deliberately chosen list of addresses
   that must work *before* a customer has signed in (sending a login code,
   checking it) stays open on purpose, written down in one place a reviewer
   can check in a minute.
2. **The bank's own staff tools:** these stay built the way they are today,
   but every one of their actions will consistently require "this caller is
   a logged-in staff member with the right role" — the same rule the
   back-office admin screens already use — instead of that check existing on
   some actions and being missing on others.

**Not changed by this task, by explicit decision:** the addresses used by
outside companies' computers. See "What is wrong with it" above and decision
#7 in Part 3.

## What could go wrong

The biggest risk is fix #1: **if the "must work before login" list is wrong,
customers cannot sign in at all**, for every customer, the moment this goes
live. That list was built by reading the actual routing file, not guessed —
see "Evidence" — but this change should still go out when someone is
watching and ready to reverse it, not last thing on a Friday.

For fix #2, tightening a check on an internal tool could lock out a
legitimate staff member if their role assignment is wrong in the database —
lower risk than #1 since it's a small, known group of people, not every
customer.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Endpoint / route | One web address on the bank's server that a program calls to get data or perform an action. |
| Token / JWT | The "pass" or wristband. A long scrambled string the server issues at sign-in that proves who the caller is. |
| Header | A small labelled note attached to a request, separate from its main content. The pass travels in a header called `Authorization`. |
| Controller | A file of code that handles requests for one area of the app. |
| Base class | A shared file many controllers are built on top of. Code placed there runs for all of them — the right place for a rule that must apply everywhere. |
| Fail open / fail closed | "Fail open" lets a request through when the check can't decide. "Fail closed" (the safe choice) refuses it. |
| Allowlist | A written list of the specific things that are permitted. Everything not listed is refused. |
| Staff session | The login a bank employee holds in their browser after signing into the admin back office. |

## Root cause

### 1. `Mobile_Controller` fails open when the header is absent

[application/libraries/common/Mobile_Controller.php:31-35](application/libraries/common/Mobile_Controller.php:31):

```php
$authToken = $header['Authorization'];
if(isset($authToken)){
     $this->check_session_exp();
}
```

`check_session_exp()` is the only code in this class that ever denies a
request. When no `Authorization` header is sent, `$header['Authorization']`
is an undefined index, `$authToken` is `null`, `isset()` is `FALSE`, and the
check never runs. The constructor completes and the action executes with
`main_customerId === null`. Sending *no* credential is strictly more
permissive than sending a bad one.

### 2. `authorizeToken()` never denies — it only reports

[application/third_party/jwt/libraries/Jwt.php:101-200](application/third_party/jwt/libraries/Jwt.php:101). All failure
paths (`Jwt.php:181,191,195,198`) `return false`; none exits or responds.
Enforcement is entirely the caller's responsibility.

### 3. Real production exposure — verified, not assumed

Production evidence gathered with the task owner during planning, from
`application/logs/jwt/jwt-authorizeToken-log-2026-09-16.php` and
`application/logs/customlog/api-log-2026-09-16.php` (**production**, read
live over SSH, per this repo's rule against using local logs as evidence):

```
grep -c "Log Date and Time" jwt-authorizeToken-log-2026-09-16.php   -> 68,449 requests logged
grep "^Header :" ... | grep -civ "authorization"                     -> 285 of those carry no Authorization header at all
```

Cross-referenced two of those 285 by IP+time against `api-log`: real
`okhttp`/Android traffic hitting `.../api/v2/cbs/account-balance`,
`.../api/v2/get-transactions`, `.../api/v2/get-transaction-details`,
`.../api/v2/kyc-check` — genuine authenticated-feature addresses, not the
pre-login ones.

Traced why these didn't leak data: `apiv2/Profile.php` runs its *own* second,
separate copy of the JWT check ([apiv2/Profile.php:29-31](application/modules/mobile_app/controllers/apiv2/Profile.php:29)) into
`$this->customerId` (distinct from the parent's `$this->main_customerId`),
and `get_balance_post()` happens to guard on `if ($this->customerId)`
([apiv2/Profile.php:5349](application/modules/mobile_app/controllers/apiv2/Profile.php:5349)) before returning real data. **This
protection exists only because that one method's author remembered to write
that `if`.** It is not enforced by the framework, `Mobile_Controller`, or
any shared code — it is a per-method habit, present in some of the ~46
files' methods and not verified to be present in all of them. This is the
core justification for decision #2 above (centralise, don't rely on
per-method discipline).

### 4. `rest_auth = TRUE` would be a silent no-op

[application/libraries/common/REST_Controller.php:654-670](application/libraries/common/REST_Controller.php:654):

```php
$rest_auth = strtolower($this->config->item('rest_auth'));
switch ($rest_auth)
{
    case 'basic':  $this->_prepare_basic_auth();  break;
    case 'digest': $this->_prepare_digest_auth(); break;
    case 'session': $this->_check_php_session();  break;
}
```

`strtolower(TRUE)` is `"1"`, matching no case. Setting `rest_auth = TRUE`
literally, as the task title asks, would change nothing while looking like a
fix. This is why decision #1 leaves it `FALSE` and enforces identity in code
instead.

## How it will be fixed

### Fix 1 — `Mobile_Controller`: centralised, fail-closed identity check

Replace the fail-open block at `Mobile_Controller.php:31-35` with deny-by-default:

1. Read the `Authorization` header case-insensitively (matching what
   `Jwt.php:126-130` already accepts).
2. If `($this->router->class, $this->router->method)` matches the public
   allowlist below, skip the gate and continue.
3. Otherwise, require `authorizeToken()` to have returned an array with a
   non-zero `customer_id` or `child_id`. If not, emit the existing
   `status_code 10` / "Auth token is either invalid / expired" response and
   `exit`, same shape as `check_session_exp()` already produces today.
4. Then call `check_session_exp()` unconditionally, so session-expiry is
   enforced on every authenticated request regardless of header casing.
5. Remove the now-redundant duplicate JWT check inside `apiv2/Profile.php`'s
   own constructor ([apiv2/Profile.php:29-31](application/modules/mobile_app/controllers/apiv2/Profile.php:29)) and any sibling
   version files with the same pattern — the parent now guarantees identity
   before the child constructor runs, so `$this->customerId` can be set
   directly from `$this->main_customerId` for backward compatibility with
   the ~23 call sites (`generateToken`/`generateSecretKey`) that already
   reference it, without re-running the token check.

All of Fix 1, Fix 2, and Fix 3 below are implemented entirely inside
`Mobile_Controller.php`, the 20 controller files, and one new library file.
**`application/config/rest.php` and `application/libraries/common/REST_Controller.php`
are not modified anywhere in this plan** — no value change, no comment, no
formatting touch.

### The public allowlist (scoped by class + method, applies to every version automatically)

| Class (case-insensitive router match) | Bare method names exempted |
|---|---|
| `Profile` | `initiate_profile_login`, `check_version_api`, `generate_uuid`, `deregister_device`, `resend_otp`, `send_otp`, `verify_otp`, `get_static_page`, `verify_customer` |

Matched against the method name with any `_get`/`_post`/`_put`/`_delete`
suffix stripped, so it applies uniformly across `api/Profile`,
`apiv2/Profile`, `apiv3/Profile`, `apiv6/Profile`, `apiv7/Profile` without
listing each version — this is the "regex, for every version" the task
owner asked for; implemented as a class+method allowlist rather than a URL
regex because the URL differs per version (`api/v6/send-otp` vs
`api/v2/send-otp`) while the underlying class name does not.

**Not on the list, deliberately** — same-sounding but *post-login* OTP
flows, confirmed by reading each: `send_aadhar_card_otp`,
`verify_aadhar_card_otp`, `verify_update_email_otp`, `kcc_send_otp`,
`kcc_verify_otp`, `kcc_send_otp_email`, `kcc_verify_otp_email` — these live
in different classes (`Profile`'s other methods and `KCC`), run inside an
already-authenticated session, and are correctly left requiring a token.

### Fix 2 — Group A (internal staff tooling): consistent staff-session check

For each of the 9 files listed above, add a single check at the top of every
public method (or via a shared private helper called first in each method,
matching this codebase's existing per-method style rather than introducing a
new base-class pattern for files that intentionally stay on
`REST_Controller`):

```php
if (!$this->session->userdata('role_grp_id') || $this->session->userdata('role_grp_id') != ONESTACK_SUPERADMIN) {
    $this->response(['status' => FALSE, 'message' => 'Unauthorized'], REST_Controller::HTTP_UNAUTHORIZED);
    return;
}
```

This is the exact rule `MoveToProduction.php` already applies in some
methods ([MoveToProduction.php:867,987,1176,1229](application/modules/mobile_app/controllers/api/MoveToProduction.php:867)) — the fix
is making it run in *all* methods of all 9 files, not introducing a new
rule.

### Group B (outside systems): explicitly not touched

Per decision #7, the 9 Group B files are **not modified in any way** by this
task — no new check, no class change, no config, no new library. They are
listed under "Root cause" only so the gap is documented and visible, not
because anything is done about them here. `ChatBotApi.php` in particular
remains reachable with zero authentication after this task ships, returning
real account balance and transaction history to any caller who knows the
URL. If this needs to be revisited later, it would need its own task — a
shared-secret mechanism does not exist anywhere in this codebase today
(confirmed: `rest_enable_keys = FALSE`, no header/signature check in any of
the 9 files) and would have to be built along with real coordination with
each outside party (NPCI, EdgeVerve, the SMS/WhatsApp vendor, the chatbot
platform) for actual secret values — none of that is attempted here.
