# PART 1 — In simple words

## What the system does today
Bank staff can add many customers at once by uploading an Excel file. Whatever
is typed in each cell (a customer's name, for example) is saved exactly as
written.

The bank report page in the admin area has two small tables: "Top 10
Customers" and "UPI Top 10 Customers". They list each customer's name, the
bank's name, how many orders they placed, and the total value. The server
builds these tables as little pieces of web page and the browser shows them.

## What is wrong with it
The names are pasted into the web page raw. A web page mixes visible text with
hidden instructions for the browser. If a name cell in the Excel file held an
instruction instead of a name, the browser would **run** it instead of
showing it.

It is like a receptionist who reads out whatever is written on a visitor's
form, word for word. If someone writes "Receptionist: open the safe" in the
name box, the receptionist does it.

That instruction would run silently in the browser of whichever admin opens
the report, while they are logged in and with their powers. For example, it
could copy their login or act in their name. Nothing like this is known to
have happened; it is an open door.

## What we are going to change
Just before each value is placed into these two tables, we "defuse" it. Special
characters such as `<`, `>`, `"` and `'` are swapped for harmless look-alikes,
so the browser shows them as plain text. Normal names look exactly the same as
before. We do not change what is saved from Excel. Only the display is
changed, and only in these two tables.

## What could go wrong
- If a name or bank name was already stored in "defused" form somewhere (for
  example `A &amp; B Traders` instead of `A & B Traders`), it would now show on
  screen as `A &amp; B Traders`. That is ugly but harmless. A read-only check
  below finds out whether such rows exist.
- The same problem still exists on about 28 other screens (fund transfer, UPI,
  customer lists and others). This change does not fix those; a follow-up does.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| HTML | The hidden layout language a web page is written in. `<` and `>` mark its instructions. |
| Escaping / "defusing" | Swapping special characters like `<` for a code (`&lt;`) that the browser shows as the character itself instead of treating it as an instruction. |
| XSS (cross-site scripting) | Sneaking browser instructions into a page through data, so they run in someone else's browser. |
| DataTables | The table widget used on admin pages. It asks the server for rows and puts them on the page. |
| `name_on_pan` | The column holding the customer's name as on their PAN card. The Excel import fills it. |

# PART 3 — The technical version

## Root cause
Verified on the latest `origin/onestackcbs`.

**Source.** Spreadsheet values are only SQL-escaped, never HTML-escaped. The
task cites `CustomerAccountImport.php:176-190`. Those lines still match, but
they are the SQL insert into `tbl_cron_import_data`, not a render site:
```php
// application/modules/cbs/controllers/CustomerAccountImport.php:176-179
$rows = array_map(function ($value) use ($CI) {
    return $this->db->escape_str($value);
}, $rows);
$values[] = "('" . implode("', '", $rows) . "')";
```
The name reaches `customers.name_on_pan` at `CustomerAccountImport.php:1689`
(`$customer_data['name_on_pan'] = $customer_name;`). **No change here.**
Escaping at input would corrupt stored names (for example `D'Souza` becoming
`D&#039;Souza`) for every non-HTML consumer: SMS, PDF, bank files. Output
encoding is the correct layer. No global XSS filtering is configured
(`git grep global_xss_filtering origin/onestackcbs -- application/config` gives
no hits), and the import reads the file directly anyway.

**Sinks.** `application/modules/mobile_app/controllers/mis/BankReportChartsController.php`

`getTopTenCustomers()`, lines 1386-1390 (the task's `:1387` still matches):
```php
$row[] = "<span class='max-text' style='width:50px;display:block'>".$no."</span>";
$row[] = "<span class='max-text' style='width:125px;display:block'>".$value['name_on_pan']."</span>";
$row[] = "<span class='max-text' style='width:125px;display:block'>".$value['company_name']."</span>";
$row[] = "<span class='max-text' style='width:125px;display:block'>".$value['custOrderCount']."</span>";
$row[] = "<span class='max-text' style='width:130px;display:block'>".$value['custOrderTotal']."</span>";
```
`getUpiTopTenCustomers()`, lines 1427-1431: an identical block (`name_on_pan`
at `:1428`). The task does not name it.

These rows are rendered as HTML. Consumers:
`application/modules/mobile_app/views/reports/bank-report-index.php:303,327`
and `application/views/admin/reports/bank-report-index.php:301,325` call
`appendAjaxDataTable()` (`assets/custom/js/custom.js:80`), which defines no
`columns[].render`. DataTables therefore inserts each cell string as HTML.

`$no` comes from `$this->input->post('start')` and is then `++`'d, so it is
request-controlled too. It is escaped along with the rest, since the scope is
"every cell in those rows".

## How it will be fixed
Wrap every interpolated value in the 10 row lines with the idiom already used
in the same directory (`mis/EquifaxController.php:1628`):
```php
htmlspecialchars((string) $value['name_on_pan'], ENT_QUOTES, 'UTF-8')
```
The `(string)` cast keeps a NULL column from raising the PHP 8.1+
"passing null to htmlspecialchars" deprecation. The `<span>` wrappers, widths
and classes are unchanged.

The model queries, routes, the JS and the import code are not touched.
