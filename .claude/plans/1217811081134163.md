# PART 1 — In simple words

## What the system does today
When someone clicks a button or a link in the admin website, the browser sends a request to a web address (a URL). A file called `routes.php` is like a switchboard operator: it looks at the address and decides which piece of code should answer it. Most addresses are wired correctly, so the right code answers and the button works.

## What is wrong with it
A handful of these switchboard wires are wrong or missing a piece:

- **A stray placeholder.** One wire has a leftover marker (`$1`) that was meant to carry a piece of the address through to the code, but the address it's attached to doesn't actually have that piece to carry. It doesn't break anything today because the code on the other end ignores it, but it's confusing leftover wiring.
- **Two forms that quietly fail.** Two "turn this FAQ on/off" buttons in the admin panel build a web address that includes an ID number at the end. The switchboard wire for that address was written *without* a slot for that ID number — it only matches the address without anything after the last slash. Since the real click always includes the ID, the switchboard never finds a match, the request goes nowhere, and the toggle silently does nothing. No error is shown to the person clicking it — it just doesn't work.
- **A duplicate, unused wire.** One wire for "post a comment on a UPI transaction" was set up correctly elsewhere with a typo carried through consistently, and an old copy of the wire (without the typo) is left behind, unused by any page. It's dead weight.
- **Two wires that go to a dead end.** Two addresses about a Riskcovry insurance page are wired to a piece of code named `processRiskcovry`, but the code library that runs this section of the website has a rule: for that code to be reachable, its name must end in `_get` or `_post`. Because it doesn't, the switchboard actually redirects the request somewhere else entirely (a generic "info" page) instead of where the wire claims. Nothing in today's admin panel or app ever calls this address, so nobody notices, but the wiring is misleading and dead.

Two other suspects from the task title turned out, after checking, not to be real problems: the UPI-2 "post comment" wire is correctly connected, and the newer "NpciMobileAPIV6" address checked out fine — its wire and its code agree on how many pieces of information pass between them.

A separate group of three "support ticket" wires point to code that was never written (the code the wire names does not exist). That is a different, bigger problem — the buttons that use them are actively broken today, and fixing it means writing new code, not just rewiring an address. **That part is explicitly out of scope for this task and is left untouched**, per instruction.

## What we are going to change
Only `application/config/routes.php` — no controller code, no new features. Four wiring fixes:
1. Remove the stray, meaningless placeholder from the SMS-callback wire.
2. Give the two "FAQ sub-category toggle" wires a slot for the ID number the buttons already send, so those buttons start working.
3. Delete the one leftover, unused duplicate UPI comment wire.
4. Delete the two dead-end Riskcovry wires, since they don't reach the code they claim to and nothing calls them.

## What could go wrong
- If anything, anywhere, silently depended on the exact old (broken) URL of the two FAQ toggle wires returning a 404 instead of succeeding, that behaviour changes — but a 404 today already means the feature is broken, so this is a pure improvement.
- Deleting the two Riskcovry wires removes those specific URLs entirely (404 instead of a misdirected response). If some undiscovered external caller (outside this repo, e.g. a Riskcovry webhook) hits either URL, it would now get a 404 instead of the current wrong page. No such caller was found in the codebase.
- Deleting the duplicate UPI wire removes one specific unused URL; the working one is untouched.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Route | An entry in `routes.php` that maps a URL to the code that should run for it |
| Capture group | A placeholder (like `(:any)`) in a route's URL pattern that grabs part of the real URL and hands it to the code as a piece of data |
| REST controller | A type of controller (code file) used for the app's API, which requires method names to end in `_get`/`_post`/etc. to be reachable |
| `_remap` | The internal traffic-cop function that REST controllers use to decide which method actually runs for a given request |

# PART 3 — The technical version

## Root cause

**1. Stray `$1` with no capture group — [application/config/routes.php:2023](application/config/routes.php:2023)**
```php
$route['api/gupshup-sms-callback'] = 'mobile_app/npci-upi/NpciUPI/smsCallbackDeviceBinding/$1';
```
The source pattern `api/gupshup-sms-callback` has no `(:any)` or regex group, so `$1` is a dangling backreference. The target method takes zero parameters and reads everything via `$this->input->get()` ([NpciUPI.php:538-546](application/modules/mobile_app/controllers/npci-upi/NpciUPI.php:538)), so the extra call-time argument is silently ignored by PHP today. Confirmed as titled — cosmetic/leftover, not a live bug.

**2. FaqManagment x2, trailing slash with no capture — [routes.php:2863-2864](application/config/routes.php:2863)**
```php
$route['admin/risk_profile-edit/change-faqs-sub-category-status/'] = 'mobile_app/products/FaqManagment/changeFaqsSubcatStatus';
$route['admin/communication_FAQs-edit/change-faqs-sub-category-status/'] = 'mobile_app/products/FaqManagment/changeFaqsSubcatStatus';
```
Both admin views that use these paths append a category ID after the final slash:
```php
// application/modules/mobile_app/views/products/faqs/index-subcat.php:54
url : "<?php echo base_url("admin/risk_profile-edit/change-faqs-sub-category-status/".$reqData["category_id"]); ?>",
// application/views/admin/faqs/index-subcat.php:54
url : "<?php echo base_url("admin/communication_FAQs-edit/change-faqs-sub-category-status/".$reqData["category_id"]); ?>",
```
Both are POST requests carrying `list_id`/`new_status` in the POST body ([index-subcat.php:53-56](application/modules/mobile_app/views/products/faqs/index-subcat.php:53)); `changeFaqsSubcatStatus()` itself takes no parameters and reads only `$this->input->post(...)` ([FaqManagment.php:608-645](application/modules/mobile_app/controllers/products/FaqManagment.php:608)) — the trailing ID in the URL is not read by the controller at all, it just needs to be *matched* for CI's router to route the request there. Because the route pattern has no wildcard after the trailing slash, a URL with an ID appended does not match this route at all, so the request 404s and the AJAX `error` callback fires silently (it's empty — [index-subcat.php:71-72](application/modules/mobile_app/views/products/faqs/index-subcat.php:71)). This is a live, currently-broken toggle on both FAQ sub-category admin pages.

The two working sibling routes at [routes.php:745-747](application/config/routes.php:745) use a different URL shape (no ID segment at all) and work fine — they are not affected.

**3. Duplicate dead UPI comment route — [routes.php:1024](application/config/routes.php:1024)**
```php
$route['admin/upi_1-all_transactions-view/cbs/post-comment'] = 'mobile_app/transactions/UpiMaster/postUpiComment';
```
Both UPI-1 admin views that submit this form post to `.../post-commentt` (double "t", a typo carried consistently into the live code) — [upi-master/upi-transactions/view.php:520](application/modules/mobile_app/views/admin/upi-master/upi-transactions/view.php:520) and [transactions/upi-master/upi-transactions/view.php:452](application/modules/mobile_app/views/transactions/upi-master/upi-transactions/view.php:452) — which is served by the separate route at [routes.php:2628](application/config/routes.php:2628). No page anywhere in the repo posts to the single-"t" path. Confirmed dead by exhaustive grep for `post-comment` (12 files, none use the single-t UPI-1 path) and for `postUpiComment` (all call sites checked above).

The task title named `Upi2Master/postUpiComment` as the dead one, but that route ([routes.php:2629](application/config/routes.php:2629)) exactly matches what [upi2-master/view.php:541](application/modules/mobile_app/views/admin/upi2-master/view.php:541) submits to — it is live and correct, and is left untouched.

**4. Dead-end Riskcovry routes — [routes.php:1646](application/config/routes.php:1646) and [routes.php:2298](application/config/routes.php:2298)**
```php
$route['api/v2/process-riskcovry'] = 'mobile_app/api/Insurancev2/processRiskcovry';
$route['api/v6/process-riskcovry'] = 'mobile_app/apiv6/Insurance/processRiskcovry';
```
Both target controllers extend `Mobile_Controller`, which extends `REST_Controller` ([Insurancev2.php:6](application/modules/mobile_app/controllers/api/Insurancev2.php:6), [apiv6/Insurance.php:6](application/modules/mobile_app/controllers/apiv6/Insurance.php:6)). `REST_Controller::_remap()` always dispatches to `{method}_{http_verb}` and falls back to `index_{http_verb}` (prepending the originally-requested method name as an argument) when that suffixed method doesn't exist:
```php
// application/libraries/common/REST_Controller.php:742-747
$controller_method = $object_called.'_'.$this->request->method;
if (!method_exists($this, $controller_method)) {
    $controller_method = "index_" . $this->request->method;
    array_unshift($arguments, $object_called);
}
```
Both `processRiskcovry($data)` methods ([Insurancev2.php:1044](application/modules/mobile_app/controllers/api/Insurancev2.php:1044), [apiv6/Insurance.php:1044](application/modules/mobile_app/controllers/apiv6/Insurance.php:1044)) are plain names with no `_get`/`_post` suffix, and both classes define `index_get()` ([Insurancev2.php:18](application/modules/mobile_app/controllers/api/Insurancev2.php:18), [apiv6/Insurance.php:18](application/modules/mobile_app/controllers/apiv6/Insurance.php:18)). So hitting either route never actually runs `processRiskcovry()` — it silently runs `index_get()` instead, which returns a generic API response, not the Riskcovry view. This is a genuinely misdirected route. Exhaustive grep for `process-riskcovry` and `processRiskcovry` across `application/` (`*.php`, `*.js`) found no caller anywhere in this repo.

The task title attributed an "argument-count mismatch" to `NpciMobileAPIV6` — checked and not reproducible: its route ([routes.php:2393](application/config/routes.php:2393)) has 2 capture groups and its target method ([NpciMobileAPIV6.php:128](application/modules/mobile_app/controllers/npci-upi/NpciMobileAPIV6.php:128)) takes exactly 2 parameters; they agree. The genuine argument/dispatch mismatch was in Insurancev2/apiv6-Insurance instead (this item).

**Out of scope, left untouched (per explicit instruction to skip missing-method fixes):**
`ClientTicketMaster x3` — routes at [routes.php:2624-2627](application/config/routes.php:2624) and [routes.php:2872-2875](application/config/routes.php:2872) point to `deleteClientTicket`, `getCustomersByCompanyId`, `getVendorsByVendorGrpId` on `ClientTicketMaster`, none of which exist anywhere in the codebase (confirmed via `grep -rn "function deleteClientTicket\|function getVendorsByVendorGrpId\|function getCustomersByCompanyId" application/` — zero matches). These are actively called by [support-ticket/create.php:136,151](application/views/admin/customer-service/support-ticket/create.php:136) and [support-ticket/index.php:51](application/views/admin/customer-service/support-ticket/index.php:51), so this is live broken functionality, not dead code — but fixing it means writing the missing methods, which is out of scope here.
