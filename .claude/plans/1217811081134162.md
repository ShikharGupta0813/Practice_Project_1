# PART 1 — In simple words

## What the system does today
Admin screens have on/off switches and status drop-downs: switch a product, a tool, a customer or a bank biller on or off, mark a payment's settlement as pending or completed, set a support ticket to open or closed. When you flip one, the browser sends the new value to the server and the server writes it into the database exactly as received.

## What is wrong with it
The server never checks that the value makes sense. It trusts the drop-down. Anyone who can reach these pages (a logged-in admin, or someone who tricks one into sending a request) can send any text, such as "banana" or "2", and it gets stored. A customer's "active" flag could end up as something other than on or off; a payment settlement could be marked with a made-up status that no report understands; a ticket could get a status that makes it vanish from every list. Nothing is stopped today, and the bad value is saved silently.

## What we are going to change
In each of these places the server will keep a short list of the values that are allowed (for example, only 0 or 1 for an on/off switch) and refuse anything else with an "Invalid status" message. The allowed lists come from what production really contains today, so nothing used now is blocked.

## What could go wrong
- If some screen sends a value that is valid in real life but not in the list, that switch will start showing an error instead of saving. The lists were built from real production data and the screen code, but four of the on/off tables (modules, FAQ categories, BBPS billers, Orowealth AMCs) were not checked in production; see "How to test" for the read-only check to run first.
- Production has a blank `settlement_status` on some rows (the empty value in the data). Blank is deliberately NOT allowed as a new value; existing blank rows are untouched.

## How it will be fixed
In each method, immediately after the POST/method check and before the existence lookup, add an inline allowlist check using the file's own style (tabs vs spaces, `$response` array, same `echo json_encode($response); exit;` ending):

```php
$new_status = $this->input->post('new_status');
if (!in_array((string) $new_status, array('0', '1'), true)) {
	$response['msg'] = 'Invalid status';
	echo json_encode($response);
	exit;
}
```

Notes: strict `in_array` on the string form avoids PHP's loose `'abc' == 0` equality. `$response['status']` is already initialised to 0 at the top of each method. No shared helper is added (consistency rule: neighbouring controllers are copy-paste, and a helper would touch an autoloaded file with project-wide blast radius). Settlement and ticket methods use their own string lists; ticket values are trimmed before comparing.
