# PART 1 — In simple words

## What the system does today

This is the third of four copies of the same piece of code. It does the same job as
the one in the customer-account import screen: staff remove a queued bulk-upload
job, the screen sends the job's identity number, and the system builds a database
instruction by gluing that number onto the end of a sentence.

This copy lives in the user-management area rather than the account-import area,
but the line itself is word for word the same.

## What is wrong with it

The same flaw. The number is glued in without being checked, so a value that is not
a number becomes part of the database instruction and the database obeys it.

The reason there are four separate tasks rather than one is that the same faulty
line was copied into four files over time and the four have never been reconciled.
Each copy is independently exploitable; fixing three of them changes nothing about
the fourth.

## What we are going to change

The same fix: hand the sentence and the value to the database separately so the
value can only ever be read as a number.

## What could go wrong

Nothing beyond what applies to the sibling copies. The behaviour for a genuine
numeric value is unchanged.

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/Users.php:1747`
— **the task says :1773; the actual line is :1747. The code has moved 26 lines up.**

```php
$sql = "Delete from tbl_cron_import_data where queue_id = " . $_POST['id'];
```

Identical to the `CbsCustomerAccountImport.php` copy: raw `$_POST['id']`
concatenated into a `DELETE` in numeric context. No cast, no escaping, no binding.

The task's subtitle — "gated only on the routed path" — refers to the fact that
whatever protection exists comes from the route this method sits behind rather than
from any check inside the method. That is the same fail-open route problem tracked
in tasks 54 and 56, which are separate and flagged NEEDS DISCUSSION. **This plan
does not attempt to fix the routing.** It fixes the injection only. The two are
independent: binding the parameter is correct regardless of how the route resolves.

## How it will be fixed

```php
$id = (int) $this->input->post('id');
$sql = "Delete from tbl_cron_import_data where queue_id = ?";
$qry_result = $this->db->query($sql, [$id]);
```

Same shape as the other three copies, so the four read identically afterwards and
task 53's dedupe becomes a mechanical extraction.
