# PART 1 — In simple words

## What the system does today

Three kinds of screen are involved.

**The upload screens.** Staff upload a spreadsheet of customers, users or cards.
Each upload gets a number. Next to each one is a delete button. When you press it,
the screen sends that number back to the server, and the server deletes that upload.

**The branch setup screens.** Staff pick a branch and a centre, and the screen shows
how many products and services that branch offers. The screen sends the branch number
and the centre number to the server, and the server counts them up.

**The payment confirmation step.** When a UPI payment completes, the payment provider
sends us a message containing the transaction's reference code. We look that transaction
up so we can text and email the customer their confirmation.

In all three cases the server does the same thing: it builds a written instruction for
the database, and it glues the number it received into the middle of that sentence.

## What is wrong with it

Think of a clerk with a form that says "Delete upload number ______".

The clerk's job is to read the sentence and do what it says. Normally someone writes
`7`, so the clerk deletes upload 7. But this clerk never checks that the blank actually
contains a number. They just read the finished sentence aloud and obey it.

So if somebody writes into that blank:

> `7 and also delete everything else`

the clerk reads the whole sentence and does all of it. The clerk had no way to tell
which part of the sentence was the real instruction and which part was smuggled in.

That is exactly what happens here. The value arrives from the browser, gets glued into
the middle of a database instruction, and the database carries out whatever the finished
sentence says.

**Two defences that people assume are protecting this, and neither one does:**

*"There is a check above it."* There is. Before deleting, the code looks up the upload
to confirm it exists. But that lookup is done the safe way, so it succeeds: someone
typing `1 OR 1=1` is read by the safe lookup as simply `1`, upload 1 does exist, and
the check waves them through. Then the unsafe line runs the full sentence. The guard
does not merely fail to stop the attack — it confirms it.

*"We strip out dangerous punctuation."* The app does filter some characters. But this
attack needs none of them. `1 OR 1=1` is only letters, digits, spaces and an equals
sign. Every one of those passes the filter untouched.

**What this means for a real person:**

- On the four upload screens, someone could delete rows they were never meant to touch.
- On the six branch screens, someone could ask the database yes-or-no questions about
  *any* table in the system — customer records, accounts, transactions — and read the
  answers off the count shown on screen. It is slow, one question at a time, but there
  is no limit to what can be asked.
- The payment confirmation step is the most serious. It sits on a public web address
  with **no login at all**, because it has to accept messages from the payment provider.
  Anyone on the internet who can reach that address gets the same power.

Nothing here says an attack has already happened. It says that if someone tried, nothing
in the code would stop them.

## What we are going to change

We stop gluing. At every one of these spots, the value is handed to the database as a
separate item rather than pasted into the sentence. The database then treats it as a
value only, never as an instruction. Someone typing a whole page of commands into the
box just means the database goes looking for a record with that ridiculous name, finds
none, and does nothing.

For the spots that hold ID numbers, we also force the value to be a whole number before
it is used, which throws the attack text away entirely. For the payment reference — which
contains letters, not just digits — we use the hand-it-over-separately method instead,
because forcing it to a number would destroy a real reference code.

Every screen behaves exactly as it does today.

## What could go wrong

**Honest risks:**

- **Nothing visible should change, and that is the thing to check.** Nineteen small edits
  across five files. The danger is not a clever failure, it is a typo — a missing bracket,
  a value passed in the wrong order. Every screen touched needs to be opened once and
  clicked through.
- **We cannot properly test this from a developer machine.** Nine of these spots sit on
  screens driven by real import queues and real branch data, and the local database does
  not match production. The code can be verified by reading it; "I clicked it and it
  worked" is not something this plan can honestly promise.
- **The payment callback cannot be tested safely at all.** It is a live payment path.
  It should be watched after release rather than triggered on purpose.
- **If a value is forced to a number where it should not have been, lookups quietly
  return nothing** instead of failing loudly. This is why the payment reference is
  deliberately handled differently, and why one already-safe value in the branch screens
  is being left exactly as it is.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| SQL | The language used to give instructions to the database — "find this", "delete that". |
| SQL injection | When someone types database instructions into an ordinary form field, and the system carries them out because it glued the text into its own instruction. |
| Parameterise / bind | The safe method: send the instruction and the value as two separate things, so the database never reads the value as an instruction. |
| Cast to integer | Force a value to be a whole number. `1 OR 1=1` becomes just `1`; the rest is discarded. |
| Query builder | CodeIgniter's helper for building database instructions safely. It parameterises for you. |
| Raw SQL | A database instruction written out by hand as text, bypassing the query builder. This is where the bug lives. |
| Callback | A web address our system exposes so an outside company (here, the payment provider) can send us updates. It has no login, by design. |
| UTR | Unique Transaction Reference — a bank's code for a payment. Contains letters as well as digits. |
| Controller | A file holding the code that runs when a particular screen or address is opened. |
| Blind injection | An attack where the stolen data is not printed on screen, but can still be worked out one yes/no question at a time. |

# PART 3 — The technical version

## Root cause

Nineteen raw-SQL statements across five files interpolate a request-derived value
directly into the statement text. All were read on `onestackcbs`.

## How it will be fixed

Three mechanical transformations. No control flow changes, no signature changes, no
refactoring, no deduplication of the four copies.

**1. Group A (4 sites) — cast to int, keep raw SQL shape.**

```php
// before
$sql = "Delete from tbl_cron_import_data where queue_id = " . $_POST['id'];
$qry_result = $this->db->query($sql);

// after
$queue_id = (int) $_POST['id'];
$qry_result = $this->db->query("Delete from tbl_cron_import_data where queue_id = ?", array($queue_id));
```

Both belt and braces: the cast makes the value structurally incapable of carrying SQL,
and the bound parameter means the statement text no longer varies with input. The
surrounding `$_POST['id']` uses that feed the query builder (`$condition = array('id' => $_POST['id'])`)
are already safe and are left alone.

**2. Group B (6 sites) — cast the two attacker-controlled values only.**

```php
// before
$sql = "select DISTINCT product_id from tbl_cbs_center_products where is_active ='1' and bank_id =" . $id . " and branch_id =" . $branch_id . " and center_id = " . $center_id . " and product_id NOT IN (...)";

// after
$branch_id_i = (int) $branch_id;
$center_id_i = (int) $center_id;
$sql = "select DISTINCT product_id from tbl_cbs_center_products where is_active ='1' and bank_id =" . $id . " and branch_id =" . $branch_id_i . " and center_id = " . $center_id_i . " and product_id NOT IN (...)";
```

`$id` is deliberately left interpolated as-is. It is not attacker-controlled (see Root
cause), and casting it would convert the `"Not Found"` sentinel from a loud SQL error
into a silent `bank_id = 0` returning a count of zero. That is a behaviour change on an
error path with no production evidence behind it, and it does not improve security. It
belongs in a separate task about the `"Not Found"` sentinel, not in a security fix.

`CommonModel::sql()` takes only a string, so binding is not available here without
changing that shared model's signature — out of scope. The `(int)` cast is complete
protection for these two values regardless.

**3. Group C (1 site) — bind, do not cast.**

```php
// after
$query = $this->db->query('select ... where utm.upi_transaction_utr_no = ? group by utm.id',
    array($apiRequest['transactionreferencenumber']));
```

The `"` quoting around the placeholder is removed — CI's binder quotes and escapes it.
No cast: a UTR contains letters, and `(int)` would reduce a real reference to `0`,
silently breaking the confirmation SMS and email for every UPI payment.

**4. Group D (8 sites) — cast at the top of each function.**

One cast per function, at the point `$queue_id` enters, covering both the `Update` and
the `Delete` below it:

```php
public function insert_spreadsheet_data($file_path, $queue_id, $table_name)
{
    $CI = &get_instance();
    $queue_id = (int) $queue_id;
    // Validate table name and queue_id
    ...
```

This is 4 added lines covering 8 sites, and needs no edit at the statements themselves.
