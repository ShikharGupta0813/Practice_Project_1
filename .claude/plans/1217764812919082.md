# PART 1 — In simple words

## What the system does today
When an admin is logged in, the browser automatically proves who they are on every request. The website does not check *where* a request came from. A page on some other website can therefore make the admin's browser send a request to our admin panel (create a user, change a setting), and the server believes it.

CodeIgniter (our framework) has a protection for this built in. It is switched off: `csrf_protection = FALSE`.

## What is wrong with it
Nothing bad has to have happened yet; the door is simply unlocked. A bad link opened by a logged-in admin can quietly perform admin actions.

The lock cannot just be turned on. If we flipped it today, every save button, every table that loads by AJAX and every export would fail with "403 Forbidden", because none of them send the secret token. Machine callers (mobile app, NPCI/bank callbacks, cron jobs) could not send one at all, so payments and callbacks would stop. A first attempt on rbank did this and was reverted.

## What we are going to change
1. Add one shared JavaScript file that automatically attaches the *current* token to every form submit and every JavaScript request, so we do not edit hundreds of forms and about 2,500 calls by hand.
2. Teach the server to also accept the token from a request header (needed for JSON requests and used for all JS requests).
3. Write the list of URLs that machines call and exempt them.
4. Only after all that is live and checked, switch the lock on, as its own one-line change that can be undone in seconds.

## What could go wrong
- A screen or button we missed would show 403 once the lock is on.
- A machine URL missing from the exempt list would stop working (payments, callbacks, mobile app). This is the main danger, so the list is checked against real production traffic before the switch.
- Pages open for a long time can hold an old token (expires after 2 hours); the user would need to reload.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| CSRF | A trick where another website makes your logged-in browser send a request without you knowing |
| Token | A secret stamp the page must send back with each request to prove it is really our page |
| Cookie | A small note the browser keeps and sends back to the server on every request |
| AJAX | JavaScript sending or loading data without reloading the page |
| Exempt list (`csrf_exclude_uris`) | URLs the server does not stamp-check, because machines call them |
| Header | Extra information sent along with a request, separate from the form data |
| Regenerate | The server issues a new stamp after every request, so an old stamp stops working |

# PART 3 — The technical version

## Root cause
`application/config/config.php:468-473`
```php
$config['csrf_protection'] = FALSE;
$config['csrf_token_name'] = 'csrf_test_name';
$config['csrf_cookie_name'] = 'csrf_cookie_name';
$config['csrf_expire'] = 7200;
$config['csrf_regenerate'] = TRUE;
$config['csrf_exclude_uris'] = array();
```
CSRF checking is off; nothing in the code base sends a token.

Why a plain "turn it on" fails (verified in `system/core/Security.php`, stock CI 3.1.10):
- `:230-231` — the token is accepted ONLY from `$_POST[csrf_test_name]`, compared with the cookie. No header is read. So a header-based `$.ajaxSetup` alone does nothing, and JSON-body requests (empty `$_POST`) can never pass.
- `:236-244` — with `csrf_regenerate = TRUE` the cookie rotates after every POST. A token printed into the page (including the hidden field `form_open()` adds at `system/helpers/form_helper.php:102-130`) goes stale after the first AJAX POST on that page. Tokens must be read from the cookie at send time, and a form's hidden field must be overwritten with the live value at submit time (NOT "skip if already present").
- `:217-227` — the exclude list is regex (`preg_match('#^'.$excluded.'$#i', uri_string)`), no `#` allowed in patterns.
- `config.php:420-424` — `cookie_prefix` is `''`, `cookie_path` `/`, `cookie_httponly` FALSE, so JS can read the cookie `csrf_cookie_name`.

No `ajaxSetup` / `ajaxPrefilter` exists anywhere (grep over `application`, `assets`, `siteload`). The senior's rbank change (comments by Dheeraj/Pankaj) is not in this repo, so its exact failure is inferred, not confirmed.

## How it will be fixed
**Client** — new `assets/custom/js/csrf.js`, loaded straight after jQuery in each shared template:
1. Read the token from the cookie `csrf_cookie_name` at the moment of sending.
2. `$.ajaxPrefilter`: for same-origin POST requests set header `X-CSRF-Token`. Covers `$.ajax/$.post/.load`, DataTables, jQuery plugins.
3. Wrap `window.fetch` and `XMLHttpRequest.prototype.open/send`: same rule (covers the ~20 `fetch` calls, native XHR, CKEditor/Dropzone-style uploads).
4. Document-level capturing `submit` listener: for same-origin `<form method=post>` set/overwrite a hidden `csrf_test_name` input with the live cookie value. Skip forms whose `action` resolves to another origin (e.g. the NPCI form in `modules/cbs/views/aeps/webinterface.php:72`) so the token never leaks. Also hook `HTMLFormElement.prototype.submit` for scripted `form.submit()`.
5. Never send the token to another origin.

**Server** — new `application/core/MY_Security.php` (`subclass_prefix` is `MY_`, `config.php:144`): override `csrf_verify()`; if request is POST and `$_POST[csrf_token_name]` is absent but header `X-CSRF-Token` is present, copy it into `$_POST` then call `parent::csrf_verify()`. Parent then validates and unsets it as normal. Behaviour is unchanged while `csrf_protection` is FALSE (csrf_verify is not called).

**Exempt list** — held in `MY_Security::$_csrf_machine_uris` (config.php is untracked), filled with machine-called URL patterns. Draft from the route files (`routes.php` ~2,473 route lines, `cbs-routes.php` ~1,421; first segments: admin ≈2,738, api ≈736, cron 121, debugger 37, cbs 25, v1 20, ibmb 8, rest small):

Machine / external — EXEMPT (draft):
`api/.*`, `cron/.*`, `cbs/cron/.*`, `ibmb.*` (`ibmb/…`, `ibmb-test-cases/…`, `ibmb/netBanking/…`), `bbps/.*`, `aeps/.*`, `upi/.*`, `imps/.*`, `benenamelookup/.*`, `pay`, `payment/.*`, `external/.*`, `v1/.*`, `v2/.*`, `v6/.*`, `soundbox/.*`, `heartbeat`, `register-deregister-device/.*`, `deregister-data-update`, `npci-upi-listvae-cron/.*`, `single-login` (cross-console hand-off: production POSTs the operator email to rbank — see DUAL-03).

Browser pages — KEEP PROTECTED, token via csrf.js (must be reviewed individually in step 5 below): `auth/*` login, `otp-login`, `verify-otp-login`, `forgot-password`, `reset-password/*`, `change-password/*`, `admin/*`, `cbs/*` (non-cron: the `cbs/get-upi-by-mobile`, `cbs/generate-print-pdf`, export routes are AJAX from admin pages, covered by csrf.js), `bank_upload/*`, `bankposter/*`, `link_post/*`, `debugger/*`, `home/*`, `getstarted/*`, `edgeverve`, `*-report` routes.
Each of the "keep protected" non-admin routes must be classified by reading its controller (browser form vs machine caller) before PR 1 is finalised; unclassified ones default to EXEMPT-with-a-comment, never to blocked.

JSON-body calls (jQuery `contentType: application/json` in 16 files, e.g. `cbs/views/service-managment/card-controls.php`, `equifax/*.php`, `assets/custom/js/equifax_individual.js`, `transunion.js`; `fetch` JSON in `soundbox-standee-print-setup.php`, `aeps/webinterface.php`, `ibmb_views/*`, `add-customer-details-ekyc-setu.php`) need no per-call edit: the header from csrf.js plus MY_Security covers them. `ibmb/*` is exempt anyway.

## How to test
Local checks prove the CODE paths only, not production behaviour. Use a scratch copy of config (do NOT commit): set `csrf_protection` TRUE in a local-only edit and revert it after.

1. Syntax: `php -l application/core/MY_Security.php` and `php -l application/config/config.php`.
2. With protection TRUE locally:
   - `curl -i -c jar.txt http://localhost/oneStackLocal/auth/login` → note cookie `csrf_cookie_name`.
   - POST without token: `curl -i -b jar.txt -X POST http://localhost/oneStackLocal/auth/login -d identity=x` → expect `403`.
   - POST with header: `curl -i -b jar.txt -H "X-CSRF-Token: <cookie value>" -X POST …` → expect NOT 403.
   - POST with JSON body + header: `-H "Content-Type: application/json" -d '{}'` → expect NOT 403.
   - POST to an exempt URL (e.g. `api/v2/upi-callback`) with no token → expect NOT 403.
3. Browser (admin, protection TRUE locally): open Network tab; save a form, load a DataTables list, run an export, upload a file, make a JSON-body call (card-controls), do two rapid AJAX saves; confirm every POST carries the header/field and none returns 403; confirm the AEPS NPCI form post carries no token field.
4. Browser: leave a page open, do an AJAX save, then submit a `form_open()` form — expect success (proves submit-time refresh beats regenerate).
5. Protection FALSE (as shipped in PR 1): load admin, auth, public pages; confirm no JS errors and no behaviour change.
6. Nothing else broken: `.claude/bin/verify.ps1`.
7. GATE (production, read-only; adjust log path). List POST URLs outside `/admin/`:
```
grep -h '"POST ' /var/log/apache2/access.log* | awk '{print $7}' | sed -E 's/\?.*//' | grep -v '^/admin/' | sed -E 's#^/([^/]+).*#\1#' | sort | uniq -c | sort -rn | head -60
```
Conclusion: any first segment in the output that is not on the exempt list or a known browser page is a machine caller to add before PR 2. Also check `/admin/` POSTs from non-browser user agents:
```
grep -h '"POST /admin/' /var/log/apache2/access.log* | grep -viE 'mozilla|chrome|safari|firefox' | awk '{print $7}' | sed -E 's/\?.*//' | sort | uniq -c | sort -rn | head -30
```
Conclusion: any URL here is a machine call under `admin/` and must be exempted individually.
