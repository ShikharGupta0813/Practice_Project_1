Asana: https://app.asana.com/1/1139764983605995/task/1217811081134126  |  ID: 1217811081134126  |  Due: 2026-09-16

# PART 1 — In simple words

## What the system does today

There is a page in the admin panel (`admin/transunion-view`) where staff can pull a customer's credit report from TransUnion, a real credit-bureau company (like CIBIL). TransUnion's real connection is **not switched on yet** — this integration was built but is not live. So right now, every time someone uses this page, the system does not actually contact TransUnion at all. Instead it returns a canned, made-up ("dummy") sample report that is baked into the code — the same fake data every time, including a fake name ("JOHN WICK"), a fake credit score, and fake account numbers. This is expected and correct for now, since TransUnion isn't live.

## What is wrong with it

For one specific action on that page — "get customer's credit assets" — the system doesn't just show the fake report on screen. It also **saves that fake report into the customer's real record** in the database, in the same table where a genuine credit report would eventually be stored, tied to that customer's real account. There is nothing in the saved record marking it as fake. If anyone (a staff member, another part of the system, or a future report) later reads that table expecting real CIBIL data, they would see this fabricated report and have no way to tell it isn't genuine.

Separately, and unrelated to the above: the piece of code that builds the fake sample report has a typo — it uses the wrong symbol to join two pieces of text together. On the PHP version this project may run in the future (PHP 8), that typo does not just misbehave, it crashes the request outright. It is a straightforward bug worth fixing regardless of the TransUnion situation.

## What we are going to change

1. Stop saving the fabricated/dummy credit report into the customer's record. The dummy report can still be shown on screen (nothing else changes there), it just will no longer be written to the database. Saving will resume automatically, unchanged, once TransUnion is actually switched on in the future (the on/off logic itself is untouched).
2. Fix the typo in the dummy-report builder so it does not crash.

The "is the real connection on or off" logic itself is being **left exactly as-is** — that was a deliberate decision, not something being fixed here.

## What could go wrong

- If some other part of the system already expects a `tbl_customer_cibil_asset` row to exist after a "get customer assets" call, and it was silently relying on the dummy row being there, that dependent code could now see no row. Checked: nothing else in the codebase reads from this table for this flow (see evidence below), so this risk is not expected to materialise, but it is the one behaviour change worth watching.
- None of this touches authentication, money, or any other module.

# PART 3 — The technical version

## Root cause

**1. Fabricated data persisted as if real** — `hitAPI()` in `application/modules/mobile_app/controllers/mis/TransUnion.php`. For `$api_name == 'GetCustomerAssets'`, the response (currently always the dummy response, since `isPortalWorking` is never set to 1 anywhere in the codebase — confirmed by repo-wide grep, see Evidence) is unconditionally persisted:

```php
// TransUnion.php:616-625
if (ob_get_length()) {
        ob_clean();
}
echo $response;

if ($api_name == 'GetCustomerAssets') {
        $this->writeLog("hitAPI - Processing GetCustomerAssets", [...], 'INFO');
        $this->updateGetCustomerAssetResp($response, $customer_id, $company_id);
}
```

`updateGetCustomerAssetResp()` writes it into the real customer's row:

```php
// TransUnion.php:643-665
public function updateGetCustomerAssetResp($response, $customer_id, $company_id)
{
        ...
        $create_data = array(
                'customer_id' => $customer_id,
                'company_id' => $company_id,
                'encrypted_resp' => $response,
        );
        $generated_report_id = $this->encrypt_model->create(DbTable::TRANS_CUSTOMERS_CIBIL_ASSET, $create_data);
        ...
}
```

`DbTable::TRANS_CUSTOMERS_CIBIL_ASSET` resolves to `tbl_customer_cibil_asset` (`application/libraries/common/DbTable.php:366`).

Note the task's cited line numbers (42, 481, 654) have drifted slightly with code changes since August; current lines are 40 (flag reset), 470/476 (dummy branch), 618-625 and 643-665 (persistence).

**2. Fatal TypeError risk on PHP 8** — `dummyResponses()`:

```php
// TransUnion.php:861-863
echo($responseBody + "------");
return $responseBody;
```

`$responseBody` is a JSON string (non-numeric). PHP 8 raises `TypeError: Unsupported operand types: string + string` for the `+` operator on non-numeric strings — this line was clearly meant to be `.` (string concatenation), not `+`.

**Left unchanged (per explicit decision):** the `isPortalWorking` flag being reset to 0 inside `writeLog()` (`TransUnion.php:40`) and never set to 1 anywhere. This is intentional today — TransUnion is not live — and is out of scope for this task.

## How it will be fixed

1. In `hitAPI()`, only call `updateGetCustomerAssetResp()` when the response actually came from the real portal, i.e. guard the existing call with `$this->isPortalWorking == 1`. This requires no change anywhere else: today the guard is always false (matches "stop persisting now"), and if `isPortalWorking` is ever legitimately turned on in the future, persistence resumes automatically with genuine data — no follow-up change needed there.
2. In `dummyResponses()`, change the `+` to `.` so the debug echo does string concatenation instead of triggering PHP 8's TypeError.
