# PART 1 — In simple words

## What the system does today

Every page and button in the admin console goes through a guard before it
opens. The guard looks at the page's name in the web address, finds that page in
the list of menus, and checks whether your role is allowed to view, add, edit or
delete there.

## What is wrong with it

Whenever the guard **cannot find an answer**, it waves you through instead of
stopping you. That happens in four situations:

1. **The page is not in the menu list.** The guard writes a note and lets you in.
2. **Your role has no entry for that menu at all.** Note written, let in.
3. **The browser did not say which page you came from** (the "Referer"). This
   happens on every normal page load from the address bar and can be removed on
   purpose. The guard then skips looking up *which* page you asked for, and
   checks your role against **any** menu instead. If you are allowed anything
   anywhere, you get in.
4. **The address does not start with `admin/`.** The guard has nothing to check,
   answers "no", and nobody listens to that answer, so you get in.

So a staff member with a small role can open pages and use buttons their role
was never given.

## What we are going to change

**Now:** the guard keeps behaving exactly as today, but every time it would have
said "no" in one of those four situations, it writes a clear line in a new log
file, "would deny", saying which page, which user and which situation.

**Later (a separate, one-line change per situation):** once the log shows only
real misuse and the route-name fixes (tasks 2, 8, 25) are live, each situation is
switched from "warn" to "deny" one at a time.

## What could go wrong

- **Now:** very little. Nobody is blocked. The risk is one extra log file, and
  the extra database lookup in situation 3 (see technical part).
- **Later, when a situation is switched to deny:** anyone who has been getting in
  through that gap, including legitimate staff on pages whose menu setup is
  incomplete, will be blocked. That is why the log comes first: it shows exactly
  who would be affected before anyone is.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Slug | The page name inside the web address, e.g. `bank-list` in `admin/bank-list-view`. |
| Action | The last word: view, add, edit or delete. |
| Access row | The database line saying what one role may do on one menu. |
| Referer | A note the browser sends saying which page you came from. It is optional and can be removed. |
| Fail open | When a check can't decide, it lets you in. "Fail closed" means it keeps you out. |
| Warn mode | Log what would be blocked, but block nothing yet. |

# PART 3 — The technical version

## Root cause

The title's first half is **already done** on `onestackcbs`. The call now sits
after the `admin` conditional, so it runs for every `Auth_Controller` request
(`application/core/MY_Controller.php:347-375`):

```php
if ($segment1 === 'admin') { ... $this->url_slug / url_action from segment 2 ... }   // :347
else { $this->url_slug = ''; $this->url_action = ''; writeLog(["Skipping URL"=>...]); }  // :365-370
$this->permissionservice->checkPermission(['slug'=>$this->url_slug,'action'=>$this->url_action]);  // :372
```

The return value is ignored. Only `deny()` (redirect + `exit`) actually blocks.

`application/libraries/PermissionService.php` (218 lines) has four fail-open
paths:

1. **No action** (`:24-29`): `if (empty($params['column'])) { return false; }`.
   Every non-`admin/` URL arrives with an empty action. `false` is ignored by
   MY_Controller, so the request proceeds. (`ActionUIComponent.php:20` uses the
   return value with `$redirect = false` and does hide the button.)
2. **Slug not found** (`:127-152`): `if (empty($menu)) { writeLog(... 'PermissionService'); return true; }`.
3. **No access row** (`:173-199`): `if (empty($access)) { writeLog(...); return true; }`.
4. **Missing Referer** (`:71` and `:165`): the menu lookup and the
   `parent_menu`/`child_menu`/`sub_child_menu` conditions (`:119-164`) are
   **inside** `if (!empty($params['slug']) && !empty($referer)) {`. With no Referer,
   the access query at `:167-171` runs with only `role_group_id` + `role_id`, so it
   matches an arbitrary access row of that role. The Referer is optional and
   absent on address-bar navigation. This is still a live gap. (The
   `missing-referer` log at `:59-69` only logs.)

`is_main == 1` short-circuits to `true` (`:14-16`) and stays that way.

## How it will be fixed (warn mode)

All changes are in `PermissionService.php`; `MY_Controller.php` is untouched.

1. **Switch**, as a class constant, so enforcing is a reviewed code change and
   not an untracked config edit (`application/config/config.php` is not in git):

   ```php
   // Fail-open paths that now DENY. Empty = warn mode: log "would deny", allow as before.
   // Reasons: 'no-action', 'slug-not-found', 'no-access-row', 'missing-referer'
   const DENY_REASONS = [];
   ```

2. **One helper** used at every fail-open point:

   ```php
   private function failOpen($reason, $params, $redirect, $legacyResult = true)
   {
       writeLog([
           'reason'      => $reason,
           'enforced'    => in_array($reason, self::DENY_REASONS) ? 'yes' : 'no',
           'gate'        => $redirect ? 'page' : 'ui',
           'current_url' => current_url(),
           'slug'        => $params['slug'] ?? '',
           'action'      => $params['action'] ?? '',
           'user_id'     => $this->CI->session->userdata('user_id'),
           'role_grp_id' => $this->CI->session->userdata('role_grp_id'),
           'sub_role_id' => $this->CI->session->userdata('sub_role_id'),
       ], '', 'PermissionService-would-deny');

       if (in_array($reason, self::DENY_REASONS)) {
           return $this->deny($redirect);
       }
       return $legacyResult;
   }
   ```

   It logs `user_id`, not email (CLAUDE.md: no PII in logs), and writes to
   `application/logs/PermissionService-would-deny-YYYY-MM-DD.log` (`writeLog`,
   `common_helper.php:1807-1812`).

3. **Wire it in**, keeping today's result as `$legacyResult`:
   - `:27-29` no action: `return $this->failOpen('no-action', $params, $redirect, false);`
     (today's `false` is preserved for `ActionUIComponent`).
   - `:152` slug not found: `return $this->failOpen('slug-not-found', $params, $redirect);`
     after the existing log, which is left as is.
   - `:199` no access row: `return $this->failOpen('no-access-row', $params, $redirect);`
     after the existing log.
   - **Missing Referer**: restructure so the menu lookup runs whenever the slug is
     non-empty. Only the referer-mismatch *logging* (`:73-116`) stays behind
     `!empty($referer)`. That is the correct check.

     To keep warn mode behaviour-neutral, a no-Referer request with a slug is
     handled **before** the normal path, and today's answer is returned unless
     `'missing-referer'` is enforced:

     ```php
     if ($noReferer && !empty($params['slug']) && !in_array('missing-referer', self::DENY_REASONS)) {
         $legacy = $this->CI->CommonModel->select_row(DbTable::USER_MANAGEMENT_ACCESS, $params['column'], $roleOnlyCondition);
         $legacyAllowed = empty($legacy) || (int) $legacy[$params['column']] === 1;   // today's rule, :167-203
         if ($legacyAllowed && !$this->scopedAllowed($params, $roleOnlyCondition)) {
             $this->failOpen('missing-referer', $params, $redirect);   // logs only (not enforced here)
         }
         return $legacyAllowed ? true : $this->deny($redirect);
     }
     ```

     `scopedAllowed()` is a small private, side-effect-free helper that runs the
     menu lookup and scoped access query **strictly**: menu missing, inactive, or
     no row → `false`; `column == 1` → `true`. It is used only for this
     comparison. Once `'missing-referer'` is enforced, no-Referer requests skip
     this block and go through the normal menu-scoped path, where
     `slug-not-found` and `no-access-row` apply as for any request.

4. Nothing else changes. With `DENY_REASONS = []` every request gets the same
   answer as today. The only differences are the new log lines and one extra
   `select_row` on no-Referer requests with a slug.

Enforcement check, **local only, not committed**: set

Rollout dependency: while `'missing-referer'` is not enforced, requests **without**
a Referer always get today's role-only answer and never reach the
`slug-not-found` / `no-access-row` checks. So enforcing `no-access-row` alone only
affects requests that carry a Referer. To close pasted-URL access too, enforce
`missing-referer` in the same step or after.

Log files: `no-action` lines go to their own file,
`PermissionService-would-deny-no-action-<date>.log` (they fire on almost every
non-admin request). All other reasons go to `PermissionService-would-deny-<date>.log`.
Staging step 3 therefore checks the `-no-action` file. Each distinct line is
written once per request, not once per button. Once `missing-referer` is
enforced, the requests it blocks (`menu-inactive`, `not-granted`) are still logged,
with `enforced=yes`.
