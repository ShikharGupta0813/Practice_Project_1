# PART 1 — In simple words

## What the system does today

There is an internal tool called the "CBS Debugger" that OneStack staff use to test the connection between OneStack and a bank's core banking system (CBS) — the bank's own computer system that holds real customer accounts and balances. Through this tool, staff can look up a customer, refresh that customer's access token, and fire live test requests at the bank (check balance, list payees, start a fund transfer, pull a batch of customer records from the bank, and more).

The only thing that decides whether someone is allowed to open this tool is one line of code: "is this person logged in at all?" (technically: does their browser session have an `identity` value set). It does not check whether that logged-in person's role has actually been granted permission to use the CBS Debugger.

There is a second, separate check further down that only runs on the tool's front page (the `index()` method) — before it shows the page, it asks "does this role have permission to view the CBS Debugger menu item?" That second check is the real gatekeeper. But it only guards the front page. It does not guard the buttons on that page.

## What is wrong with it

Three specific actions behind those buttons — refreshing a customer's bank token (`updateCbsToken`), firing a live test request at the bank (`triggerCbs`), and bulk-pulling a batch of customer records from the bank into our own database (`pullMobileDataStore`) — have no permission check of their own. They only inherit the "is this person logged in" check from the constructor.

That means: any logged-in OneStack user — even one whose role was never given access to the CBS Debugger menu at all — can call these three actions directly (by URL, bypassing the page and its hidden buttons) and the system will still carry them out. In practice that means an employee with no CBS Debugger permission could still refresh a real customer's bank token, fire live transfer/account/payee requests at a bank's core system on a real customer's behalf, or trigger a bulk pull of a bank's customer records into our database — none of which should be possible for someone without that specific permission.

Note: the page that hosts the buttons for two of these actions (`update-token`, `trigger-cbs-call`) already hides those buttons unless the logged-in user's role has `add_action` or `edit_action` permission on `cbs_debugger` — see `cbs_debugger.php:103`. So the intended rule already exists and is enforced in the browser; it is simply missing from the server.

## What we are going to change

We will add that same permission check — the one already used to decide whether to show the buttons — directly inside the three actions themselves, on the server. If someone without that permission calls these actions directly, the server will now refuse and return an "Unauthorized" response, the same way several other admin tools in this codebase already do.

## What could go wrong

- If the permission data itself is missing or wrong for some legitimate CBS-debugging role, that role would suddenly be blocked from actions it currently (accidentally) has access to. This is a real risk for any role that has been using these buttons without formally holding `add_action`/`edit_action` on `cbs_debugger` — but since the buttons are already hidden from such a role today, no *intended* workflow should be affected.
- `pullMobileDataStore` is reached by a plain URL with the bank/company id, a limit, and a token as parts of the URL (not a page with buttons), so there is no existing UI gate to compare against for it — the same `add_action`/`edit_action` rule is applied by direct analogy with the other two.

# PART 3 — The technical version

## Root cause

`CbsDebugger` extends `Public_Controller` (application\modules\mobile_app\controllers\technology\CbsDebugger.php:3), so it gets none of `Admin_Controller`'s `ion_auth`/admin checks. Its own constructor only checks session presence:

```php
// CbsDebugger.php:15-36
if ($this->session->userdata('identity') != null) {
    $this->company_id = $this->session->userdata('company_id');
    ...
} else {
    redirect('auth/login', 'refresh');
}
```

`index()` (the page load) is separately gated:

```php
// CbsDebugger.php:42
if(checkSubChildControllerAccess('technology', 'onestack_technology', 'cbs_debugger', 'display_action')){
```

But the three named methods have no such call anywhere in their bodies (verified — only `index()` in this file calls `checkSubChildControllerAccess`/`checkSubChildMgmtPermissionAccess`):

- `updateCbsToken()` — CbsDebugger.php:170-208. Reads `customer_token`, `crn`, `cbs_bank_indentifier` from POST and calls the bank's tokenization API.
- `triggerCbs()` — CbsDebugger.php:211-1044. Reads `module`, `customer_token`, `cbs_bank_indentifier`, and a large `extra_params` array from POST, and fires the corresponding live CBS call (fund transfer variants, block/unblock fund, account status change, pull-card, pull-mobile, etc., via the `module` switch at CbsDebugger.php:219-242).
- `pullMobileDataStore($company_id, $limit, $customer_token)` — CbsDebugger.php:3519-3626. Takes `$company_id` directly as a URL segment, looks up that company's live `cbs_url`/`cbs_public_key`, calls the bank's `/cbs/pull-mobile` endpoint with `CURLOPT_SSL_VERIFYPEER => 0` (CbsDebugger.php:3572), and writes the results into `tbl_pull_mobile_records` plus updates `tbl_cbs_debugger_offset`.

Routing (application/config/routes.php):
- `updateCbsToken`: `routes.php:1325` — `admin/cbs_debugger-view/cdb/debugger/update-token`
- `triggerCbs`: `routes.php:1318` — `admin/cbs_debugger-view/cdb/debugger/trigger-cbs-call`
- `pullMobileDataStore`: `routes.php:2446` — `admin/store-pull-mobile/(:any)/(:any)/(:any)`, i.e. `admin/store-pull-mobile/<company_id>/<limit>/<customer_token>`

The `admin/...` prefix means `MY_Controller`'s own permission branch (`segment(1) === 'admin'`) technically also runs for all three — but that branch has its own separately-tracked fail-open bugs (write-verb routes resolving to `view`, no-access-row/slug-not-found/missing-Referer fail-open — Asana tasks for "eleven raw-SQL sites" batch's siblings, e.g. the 78 write-verb-routes task and the checkPermission-placement task). This task is scoped to the gap inside the controller itself, independent of that router-level mechanism, matching the task title exactly.

The intended permission is already established elsewhere in this same file's view — `views/debug/cbs_debugger.php:103` only shows the "update token" / "trigger CBS" buttons when:

```php
checkSubChildMgmtPermissionAccess('technology', 'onestack_technology', 'cbs_debugger', 'add_action')
|| checkSubChildMgmtPermissionAccess('technology', 'onestack_technology', 'cbs_debugger', 'edit_action')
```

`checkSubChildMgmtPermissionAccess()` (application\helpers\permission_helper.php:203-256) returns a plain boolean (`true` for `is_main == '1'`, otherwise a DB lookup that returns `false` when no matching access row exists — i.e. it fails **closed**, unlike `checkPermission()`'s known fail-open paths), so it is safe to call directly inside an AJAX method.

## How it will be fixed

Add the same permission check used by the view, at the top of each of the three methods, using the JSON-error convention already used elsewhere in this codebase for AJAX permission failures (e.g. `application\modules\mobile_app\controllers\configuration\ConfigSoundboxMaster.php:2943`: `echo json_encode(['status' => 0, 'message' => 'Unauthorized access']);`).

For `updateCbsToken()` and `triggerCbs()`:

```php
if (!checkSubChildMgmtPermissionAccess('technology', 'onestack_technology', 'cbs_debugger', 'add_action')
    && !checkSubChildMgmtPermissionAccess('technology', 'onestack_technology', 'cbs_debugger', 'edit_action')) {
    echo json_encode(['status' => 0, 'message' => 'Unauthorized access']);
    return;
}
```

placed as the first statement inside the method, before any POST data is read or used.

For `pullMobileDataStore($company_id, $limit, $customer_token)` — same check, same message, `return;` instead of falling through (this method has no JSON success envelope on every path, so a plain early return after echoing the JSON error is consistent with its existing style).
