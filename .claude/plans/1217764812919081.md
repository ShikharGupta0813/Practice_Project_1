# PART 1 — In simple words

## What the system does today

The admin screens that list customers, their orders, their UPI payments and their
support tickets are tables. For each row, the server takes values from the database
(a name, an email, a UPI address, a company name) and glues them straight into a
piece of web-page code, which the browser then displays.

## What is wrong with it

Most of those values are glued in exactly as stored. If a stored value contains
characters that mean something to a web page (like `<` or `"`), the browser treats
them as page code rather than text. Someone who can get such a value into the
database — a customer choosing a strange UPI address or name, an imported spreadsheet,
a partner's company name — could make the admin's screen run their script, while a
bank employee is logged in.

A comparison: a form where the "name" box is copied onto an official letter without
anyone checking whether the name is actually a forged signature.

Nothing tells us this has happened. It is a hole, not a known incident.

## What we are going to change

In this one file (the customer screens), every value that comes from the database is
passed through the project's standard "treat this as plain text" filter before it goes
into the table. The link-drawing helper used for most customer columns does this once,
centrally. Normal data looks exactly the same afterwards.

Other screens with the same problem (86 other files) are **not** part of this change.

## What could go wrong

- A column that deliberately contains page code (a coloured badge, a line break) could
  start showing that code as text if it is filtered in the wrong place. The plan
  handles each of those individually.
- A value filtered twice would show as `&amp;` instead of `&`. The two places that
  already filter before calling the helper have their old filter removed.

## How it will be fixed

1. `renderTableLink()` — escape the label once, with an opt-out for the one caller
   that passes pre-built HTML:
   ```php
   private function renderTableLink($href, $label, $attrs = [], $escapeLabel = true)
   {
   	if ($label === null || $label === '') {
           return '';
       }
   	if ($escapeLabel) {
   		$label = html_escape((string) $label);
   	}
   	...
   ```
2. Remove the now-redundant `htmlspecialchars((string) X, ENT_QUOTES, 'UTF-8')` wrapper
   at the 8 lines listed (pass `X` bare). Output is byte-identical.
3. `:2285` → `chunk_split(html_escape($value['upi_transaction_id']), 15, "<br/>")`,
   and `:2290` passes `false` as the 4th argument.
4. Wrap each raw DB value in the table above with `html_escape(...)` at the point of
   concatenation, matching `:6870-6893` style, e.g.
   `"<span ...>" . html_escape($value['company_name']) . "</span>"`.
   - chunk_split sites: `chunk_split(html_escape($value['sender_upi_id']), 12, "<br/>")`.
   - Wrapped in ucfirst/strtolower: escape the inner value, e.g.
     `ucfirst(strtolower(html_escape($value['upi_transaction_status'])))`.
   - `:1968` default badge only: `ucfirst(html_escape($value['payment_status']))`.
   - `?? 'N/A'` / `?? 'pending'` forms: `html_escape($value['company_name'] ?? 'N/A')`.
   - Derived vars: escape at assignment (`:1927 $category_name`, `:2248 $frm_status`,
     `:2269 $frm_score`, `:2484 $assignee`).

`html_escape` is CI's `common.php` helper (`htmlspecialchars(..., ENT_QUOTES, charset)`),
available everywhere; already used in this file.
