# Block unauthorized access

Asana: https://app.asana.com/1/1139764983605995/project/1201457139017812/task/1218054427929389  |  ID: 1218054427929389  |  Due: 2026-09-09

## What this task is

`PermissionService::checkPermission()` is the single gate that decides whether a
logged-in admin user may open an admin page or see an action button. Today, when
that gate cannot answer the question, it **lets the request through and writes a
line to `application/logs/PermissionService-<date>.log`**. Nobody reads that log,
so in practice the check does nothing in those cases.

There are three such cases in the function:

| # | Situation | Line | What happens now |
|---|---|---|---|
| 1 | URL has no `-action` suffix, so no permission column can be chosen | `PermissionService.php:28` | `return false` — no block, no log |
| 2 | The URL slug is not a row in `tbl_sidebar_accordion_menus` | `PermissionService.php:152` | logs, then `return true` (fail open) |
| 3 | The role has no access row at all for that menu | `PermissionService.php:199` | logs, then `return true` (fail open) |

Cases 2 and 3 are the fail-open holes: the code has actively concluded it has no
permission record for this user and this page, and then allows the page anyway.

This task closes cases **2 and 3**: deny the request and record it in a dedicated
`blocked-urls` log instead of the `PermissionService` log.

Case 1 is deliberately **left alone** — see "Decisions taken" below.

Referrer handling (`missing-referer` and `referer-parent-mismatch` logging, lines
52-117) is explicitly out of scope and is not touched.

## Why we are doing it

This is a live access-control failure, not a theoretical one. The existing logs
show real users passing through the holes:

```
PermissionService-2026-08-18.log   131x  admin/dashboard-view/exp/cbs/transacting-user-graph
PermissionService-2026-08-03.log   126x  admin/dashboard2-view/bank_mis/transacting-user-graph
```

`dashboard` is confirmed present and active in `tbl_sidebar_accordion_menus`, so
those hits are case 3 — roles with **no access row for the dashboard** reading
dashboard data anyway. `dashboard2` is not in the menu table at all, so those are
case 2.

Concretely, leaving this as-is means: any admin URL whose slug was never wired
into the sidebar menu table is readable by every logged-in staff user regardless
of role, and any role that was never granted a menu permission still gets the
page. In a core banking admin panel that is customer and transaction data being
served to roles that were never granted it. The permission system appears to be
enforcing and is not.

The cost of fixing it is that users currently relying on the hole lose access —
that is the point of the fix, but it is a visible change and is why this needs
human review before merge (see below).

## Decisions taken

Two readings of the Asana comment were possible; both were put to the user and
answered:

- **Case 1 (no `-action`): exempt, do not block.** 25 routes in
  `application/config/cbs-routes.php` start with `cbs/` rather than `admin/`,
  carry no action and no slug, yet resolve to `Admin_Controller` subclasses —
  Excel exports (`cbs/excel_export/write`), `cbs/generate-print-pdf`,
  `cbs/get-customer-qr-for-print`, `cbs/terms-and-condition-view`. Blocking on
  "no `-action`" would redirect all of them to `admin/homepage` and remove
  working features. Line 28 keeps returning `false` unchanged.
- **Case 3 (no access row): block.** Accepted that roles currently reaching
  dashboard graphs without an access row will be denied and must be granted the
  permission properly.

## How it will be fixed

In `PermissionService::checkPermission()`, replace the two `return true`
fail-open branches with `return $this->deny($redirect)`, and change their log
target from `PermissionService` to a new `blocked-urls` log with a `reason` field
naming which of the two rules fired.

Two supporting changes make that correct rather than merely different:

1. **The duplicated role lookups go away.** Lines 130-143 and 177-190 re-query
   `tbl_role_group_master` and `tbl_subrole_master` even though the same two rows
   were already fetched at lines 37-50 into `$roleGroup` and `$role`. The blocked
   branches reuse the existing variables. This removes 2 redundant DB queries per
   blocked request and collapses three near-identical log blocks into one private
   `logBlocked()` helper.
2. **`deny()` learns to answer AJAX properly.** The dashboard URLs in the log are
   XHR calls. `deny()` currently does `setAlert()` + `redirect('admin/homepage')`,
   which hands a JavaScript caller a `200` with a login-ish HTML body — the graph
   would fail silently and look like a bug rather than a denial. For
   `is_ajax_request()`, `deny()` will instead emit HTTP `403` with a small JSON
   body and stop. Non-AJAX behaviour (alert + redirect) is unchanged.

## Files and scope

| File | Lines | What changes |
|---|---|---|
| `application/libraries/PermissionService.php` | 127-153 | Case 2: `return true` becomes `return $this->deny($redirect)`; log to `blocked-urls` with `reason: slug_not_in_menu`; drop duplicate role lookups |
| `application/libraries/PermissionService.php` | 173-200 | Case 3: `return true` becomes `return $this->deny($redirect)`; log to `blocked-urls` with `reason: no_access_row`; drop duplicate role lookups |
| `application/libraries/PermissionService.php` | 209-217 | `deny()` returns 403 JSON for AJAX; unchanged for normal page loads |
| `application/libraries/PermissionService.php` | new private method | `logBlocked($reason)` — one writeLog call site |

Total: 1 file, roughly 60 lines changed (mostly deletions of duplicated code).
**Size: small in diff, medium-to-large in behavioural impact.** The line count is
modest but this changes who can open which page across the entire admin panel.

`application/core/MY_Controller.php` is **not** touched, because case 1 is exempt.
That is convenient: `MY_Controller.php` is the one nearby file that **differs
between `onestackcbs` and `onestackcbs-dev`** (5 insertions / 3 deletions, in the
`Admin_Controller` maker-checker notification block — unrelated to permissions).
`PermissionService.php` and `ActionUIComponent.php` are **identical on dev and
production**, so this fix applies cleanly to both branches.

### What else calls this code

Only two callers of `PermissionService::checkPermission()` exist (the global
`checkPermission()` in `application/helpers/permission_helper.php:84` is a
different, unrelated function taking controller/method names):

- `application/core/MY_Controller.php:368` — `Auth_Controller::__construct()`,
  with `$redirect = true`. This is the page-level gate; it runs for all 164
  `Admin_Controller` subclasses. This is where the denial becomes visible.
- `application/libraries/ActionUIComponent.php:20` — `renderButton()`, with
  `$redirect = false`. **Consequence to expect:** Edit/Add/Delete/View buttons on
  pages whose slug is absent from the menu table, or where the role has no access
  row, will stop rendering. That is the same fail-open being closed, surfacing in
  the UI rather than as a redirect. `renderButton()` already handles a `false`
  return by emitting an empty string, so no change is needed there — but
  reviewers should expect buttons to disappear on affected pages.

## Plan

1. `git checkout onestackcbs && git pull origin onestackcbs`, then
   `git checkout -b sg_cl_block_unauthorized_access`.
2. In `application/libraries/PermissionService.php`, add a private helper:

   ```php
   private function logBlocked($reason, $roleGroup, $role, $extra = [])
   ```

   It calls `writeLog([...], '', 'blocked-urls')` with `reason`, `current_url()`,
   the session `email`, and the already-resolved role-group / role names. Never
   log tokens or PII beyond the email already logged today.
3. Replace the case-2 block (lines 127-153). Keep the `empty($menu)` condition;
   delete the duplicated `$roleGroupId` / `$subRoleId` / `$roleGroup` / `$role`
   lookups; call `logBlocked('slug_not_in_menu', ...)` with the slug; then
   `return $this->deny($redirect);` in place of `return true;`.
4. Replace the case-3 block (lines 173-200) the same way, with reason
   `no_access_row`, additionally logging `$params['column']`.
5. Leave lines 27-29 (`empty($params['column']) => return false`) untouched, and
   leave the referrer logging at lines 52-117 untouched.
6. Update `deny()`:

   ```php
   private function deny($redirect)
   {
       if ($this->CI->input->is_ajax_request()) {
           $this->CI->output
                ->set_status_header(403)
                ->set_content_type('application/json')
                ->set_output(json_encode(['status' => false, 'message' => 'Unauthorized access']))
                ->_display();
           exit;
       }
       if ($redirect) { setAlert('Unauthorized access', 'error'); redirect('admin/homepage'); exit; }
       return false;
   }
   ```

   Note: the AJAX branch must run before the `$redirect` check so XHR callers get
   403 whether or not the caller asked for a redirect. Confirm `is_ajax_request()`
   is reachable — `MY_Controller.php:325` already uses it in the same request
   lifecycle, so it is.
7. Match surrounding style: this file is inconsistently indented CI3-era code.
   Fix indentation only inside the blocks being rewritten; do not reformat the
   file.
8. Commit with the `Asana: 1218054427929389` trailer.

## How to test

Run each of these from the repo root.

1. **Syntax check** — must exit 0:

   ```
   powershell -File .claude/bin/verify.ps1
   ```

2. **Confirm the new log target is the only new writeLog name** — expect the
   blocked-urls call site and no remaining `'PermissionService'` target in this
   file:

   ```
   grep -n "writeLog" application/libraries/PermissionService.php
   ```

3. **Confirm the fail-open returns are gone** — this must print nothing:

   ```
   sed -n '119,205p' application/libraries/PermissionService.php | grep -n "return true;"
   ```

   (The only legitimate `return true` remaining in the function are the `is_main`
   super-admin at line 15 and the granted-access check near the end.)

4. **Find a role that will now be blocked**, to test against a real case:

   ```
   "/c/xampp/mysql/bin/mysql.exe" -u root rbank_master_db -e "SELECT m.id, m.menu_link FROM tbl_sidebar_accordion_menus m WHERE m.is_active=1 AND m.id NOT IN (SELECT child_menu FROM tbl_user_management_access) LIMIT 5;"
   ```

5. **Manual check in the browser** (cannot be automated — the gate requires a
   logged-in admin session, so `curl` without a session cookie only ever reaches
   the login redirect):
   - Log in as a **non-main** admin user (`is_main != 1`).
   - Open `admin/dashboard-view`. Expected: if that role has no access row, the
     page redirects to `admin/homepage` with an "Unauthorized access" alert.
   - Open a page the role **does** have permission for. Expected: loads normally.
     This is the regression check — confirm the fix did not block granted access.
   - Open `admin/homepage`. Expected: always loads (short-circuited at
     `MY_Controller.php:344`).
   - Log in as a **main super-admin** (`is_main = 1`). Expected: everything loads;
     the check returns `true` at line 15 before any of this code runs.

6. **Confirm the exempted routes still work** — this is the regression that
   matters most, since it is the case we deliberately did not block. While logged
   in, open in the browser:
   - `cbs/terms-and-condition-view/1827/1/4/52` — expected: loads.
   - Trigger any Excel export (`cbs/excel_export/write`) from the UI — expected:
     the file downloads.

7. **Check the logs after the manual pass:**

   ```
   ls application/logs/ | grep blocked-urls
   ```

   Expected: a `blocked-urls-<today>.log` exists, with one line per blocked
   attempt, each carrying a `reason` of `slug_not_in_menu` or `no_access_row`,
   and **no** new lines in today's `PermissionService-<today>.log` for those same
   attempts.

8. **AJAX denial returns 403, not an HTML redirect** — with the browser devtools
   Network tab open, as the blocked role, trigger a dashboard graph request.
   Expected: status `403` with a JSON body, not `200` with HTML.

## Needs human review

`yes` — this changes access control directly, converting two fail-open paths into
denials. The August logs show ~257 requests that would newly be blocked, and
action buttons will disappear on any page whose slug is missing from the menu
table. A reviewer must exercise the affected admin routes with a non-main role
and confirm the intended users still have access, and that the exempted `cbs/*`
export and print routes are untouched.
