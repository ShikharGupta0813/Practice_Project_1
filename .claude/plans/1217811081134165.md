# PART 1 — In simple words

## What the system does today

Five separate, unrelated small bugs live in five different files. None of
them are connected — they are grouped in one task only because they were all
found in the same review pass.

1. **A "delete soundbox" button that doesn't delete anything.** In the
   soundbox admin screen, the button to remove a soundbox's serial number
   looks like it works (it says "success"), but the actual database delete
   was commented out at some point and replaced with a blank placeholder.
   The record is never actually removed.

2. **A crash when fetching a payment invoice link (in two copies of the same
   file).** When a customer's app asks for their SafeGold invoice link, the
   code that looks it up is missing one line — it builds a database question
   but never actually asks it, then immediately tries to read the answer.
   That crashes the request every time this path runs, in both the older and
   newer copies of this file (`apiv2` and `apiv6`).

3. **A crash in the YesBank overnight settlement job when there is nothing to
   settle.** When the automated nightly job looks for a bank and finds none
   for that date range, it tries to write a log entry about that — but the
   logging line has extra, wrong information stuffed into it that the
   logging function cannot accept, so instead of writing "nothing found" to
   the log, the whole job crashes.

4. **A leftover, broken line in the billing-receipt emailer.** When staff
   upload a signed billing receipt to email to a bank, the code builds a list
   of email addresses and then, on the very next line, immediately rebuilds
   that same list a different way — throwing away the first attempt. That
   first attempt is not just wasted, it is written in a way that crashes the
   whole page.

5. **Language files that can't be found on the live server.** A tool that
   loads translation files looks for them using a Windows-style file path
   (with backslashes). The live server does not run Windows, so this path
   never matches anything — the tool silently finds zero files every time it
   runs, rather than failing loudly.

## What is wrong with it

Three of these five (2, 3, 4) are not just wrong — they crash the page or job
outright when that code path runs, because they pass the wrong kind of value
to a PHP function that refuses to accept it. One (1) silently does nothing
instead of what the button promises, so a "deleted" record is still there.
One (5) silently fails to find any files, so a tool that is supposed to
process every language file processes none.

## What we are going to change

Each bug gets the smallest fix that makes it do what it was clearly meant to
do — restoring the delete call, adding the missing database line, removing
the bad extra arguments, deleting the dead line, and switching one backslash
path to a forward-slash path. No behaviour is added beyond what each piece of
code already intended.

## What could go wrong

Very little — each fix restores clearly-intended behaviour rather than
changing a decision. The one to watch is item 1: right now "delete" silently
does nothing, so any code relying on that button failing safe (never
actually removing rows) would start seeing rows actually disappear. That is
the intended fix, but worth a reviewer's eyes since it is the one change with
a real, if desired, behaviour difference.

| Word | What it means, simply |

| TypeError | A PHP crash that happens when a function is given the wrong kind of value (e.g. a list of things instead of a single word). |
| No-op | Code that runs but does nothing, despite looking like it does something. |
| Dead code | Code whose result is thrown away before it can matter. |

# PART 3 — The technical version

## Root cause (five independent items)

### 1. `application/modules/mobile_app/controllers/configuration/ConfigSoundboxMaster.php:2355` — delete no-op

Task title says line 1805; that line is inside an unrelated, already fully
commented-out block. The real, live bug is in `deleteSerialNo()`:

```php
2346:  public function deleteSerialNo()
...
2355:      $deleteStatus = ''; // $this->CommonModel->delete(DbTable::SOUNDBOX_MASTER, $condition);
2357:      if ($deleteStatus) {
```

`$deleteStatus` is hardcoded to an empty string, so `if ($deleteStatus)` is
always falsy and the response always reports `'Invalid user id'` even though
`echo json_encode($response)` still returns HTTP 200 — the endpoint always
"succeeds" from the caller's point of view while never deleting anything.
`DbTable::SOUNDBOX_MASTER` (`application/libraries/common/DbTable.php:191`)
is a real, live constant. The sibling method `deleteSerialNoBharatBank()`
three lines below (`:2378`) uses the exact same live pattern with a different
table, confirming this is the established working convention in this file.

### 2. `apiv2/InvestmentsSafeGold.php:2015-2019` and `apiv6/InvestmentsSafeGold.php:2015-2019` (identical) — fatal + query builder contamination

Task title says line 2045, inside `buy_gold_verify1_post()` — that function
is unrelated and has no bug. The real bug is 30 lines earlier, in
`fetch_invoice($tx_id)`:

```php
public function fetch_invoice($tx_id) {
    $this->db->where('tx_id', $tx_id);
    $this->db->from('tbl_safegold_invoice');
    return $query->num_rows();
}
```

`$this->db->where()`/`->from()` build up CodeIgniter query-builder state but
the query is never executed (`$this->db->get()` is never called) — this is
the "query builder contamination": the WHERE/FROM clauses stay attached to
`$this->db` and can leak into the *next* unrelated query run later on the
same object. `$query` is then referenced without ever being assigned, so
`$query->num_rows()` calls a method on `null` — an uncaught fatal `Error` in
PHP 7.4+/8 (not caught by the enclosing `catch (Exception $e)` at
`invoice_post()`'s `:931`, since `Error` does not extend `Exception`).

Confirmed reachable: `invoice_post()` (`:883`) calls
`$this->fetch_invoice($apiRequest['tx_id'] > 0)` at `:901` when the SafeGold
invoice-link API is hit. Three sibling private methods in the same file
(`get_customer_details()` `:1978`, `get_safegold_customer_id()` `:1987`,
`get_order_id_details()` `:1996`) show the correct, working pattern:
`$query = $this->db->get(); return $query->...;` — confirming `fetch_invoice()`
is simply missing that one line, identically in both file copies.

### 3. `mobile_app/controllers/YesBankSettlementWorkerSuper.php:74-85` — fatal TypeError

Task title says "TypeErrors" with no line. Confirmed one concrete site, in
`index()`, the "no seller found" branch:

```php
73:  if (empty($seller_received)) {
74:      file_put_contents(
75:          '/var/www/vhosts/.../yes-bank-settlement-super-' . date('Y-m-d') . '.log',
76:          json_encode(
77:              [ "Action" => "No Seller Found", ... ],
82:              "",              // <- $flags, must be int
83:              $this->log_file  // <- $depth, must be int
84:          ));
```

`json_encode(mixed $value, int $flags = 0, int $depth = 512)` — this call
passes `""` (a non-numeric string) as `$flags` and a log file PATH string as
`$depth`. PHP 8 throws `TypeError: json_encode(): Argument #2 ($flags) must
be of type int, string given` — uncaught (again inside a `catch (Exception
$e)` at `:131`, which does not catch `Error`). Every other `json_encode(...)`
call in this file (checked all of them) passes a single argument; this is the
one outlier, clearly a copy/paste mistake. Reached whenever the nightly
settlement job runs for a seller/date range with no matching seller row —
a normal, expected condition, not an edge case.

### 4. `mobile_app/controllers/communication/BillGenerationMaster.php:1504` — fatal TypeError, dead code

Task title says line 1502; that line is a harmless array append. The real
bug is two lines later, in `sendReceiptOnMail()`:

```php
1501:  $bankFinanceEmail = $this->CommonModel->select(DbTable::COMPANY_CONTACT, 'email as email_id', ...);
1502:  $bankFinanceEmail[] = ['email_id' => $bank_email_id];
1503:  $emails = array_column($bankFinanceEmail, 'email_id');
1504:  $toEmailList = explode(',', $emails);          // <- $emails is an array here
1505:  $toEmailList = array_map('trim', $emails);
```

`explode(string $separator, string $string, ...)` — `$emails` is an array
(from `array_column()` on `:1503`), so PHP 8 throws `TypeError: explode():
Argument #2 ($string) must be of type string, array given`, uncaught. Its
result is also immediately overwritten by `:1505` on the very next line even
when it doesn't crash, so line 1504 is dead code that only exists to fatal.

### 5. `mobile_app/controllers/apiv4/AppProfile.php:393` — Windows path separator

Line matches the task title exactly:

```php
393:    $directoryPath = FCPATH . 'assets\mobile_app\language-files'; // Update this path
396:    $files = glob($directoryPath . '/lng-*.json');
```

On a Linux production server, `\` inside `glob()`'s directory portion is a
literal backslash character, not a path separator, so `$directoryPath` never
matches the real `assets/mobile_app/language-files` directory — `glob()`
silently returns an empty array every time, and `insertTranslationsFromJson()`
always reports "No files found" (`:399`) without ever processing anything.
