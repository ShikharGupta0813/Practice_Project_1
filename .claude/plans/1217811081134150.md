# PART 1 — In simple words

## What the system does today

The bank sends WhatsApp messages to customers through an outside company called
Gupshup. Before a message can be sent, its template has to be registered with
Gupshup — a template being the fixed wording with blanks in it, like "Dear ___,
your balance is ___".

Staff create these templates on an admin screen. When they save, the system packs
the template's details into a single line of text and sends that line to Gupshup.

The line looks roughly like: `name=monthly_statement&category=UTILITY&language=en`.
Each detail is a name, an equals sign, its value, and an `&` between them.

## What is wrong with it

Some of the values are packed into that line exactly as typed, and some are not.

The message body, the header and the footer are handled properly — they are
converted first so that any awkward characters travel safely. But several other
values are dropped in raw: the category, the language, the template's name, the
list of example values, and the button definitions.

The problem is the `&` and `=` characters. Those are what separate one detail from
the next. If a value contains one, Gupshup reads it as the end of that value and
the start of a new detail. The rest of the value gets misread as a setting.

Most of the time this shows up as a template that Gupshup rejects, or one that
registers with the wrong wording. But it also means a member of staff can add
settings to the request that were never meant to be theirs to set, just by typing
an `&` in a template field.

The list of example values is the worst of the group, because it is machine-built
text that routinely contains punctuation — so this is likely misfiring already
rather than being a purely theoretical risk.

## What we are going to change

Convert the remaining values the same way the message body already is, so that any
character inside a value travels as part of that value and cannot be read as a
separator.

## What could go wrong

If a value is currently being mangled and something downstream has been built to
cope with the mangled version, fixing it changes what Gupshup receives. Templates
registered after the fix would be correct where previously they were subtly wrong.

The other thing to watch is not double-converting. The message, header and footer
are already converted earlier in the function. Converting them a second time would
turn a space into a literal `%20` in the customer's message.

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/communication/CommunicationWhatsapp.php:440`
— the task's line number is accurate. This is the `else` branch, taken when no
template image is attached; the `if` branch above builds an array and is not
affected.

```php
$post_field = "userid=" .$_ENV['WTSAPP_USERNAME']. "&password=" .$_ENV['WTSAPP_PASSWORD'].
    "&type=text&method=create_whatsapp_hsm&category=" . $_POST['template_category'] .
    "&language=".$template_language."&template_name=" . $template_id .
    "&allow_category_change=true&template=" . $message_gupshup .
    "&template_variable_examples=" . $variables_format .
    "&header=" . $header . "&footer=" . $footer;
```

**The task title overstates the scope — four of these are already encoded.** At
:404-407:

```php
$message         = rawurlencode($_POST['message']);
$header          = rawurlencode($_POST['header']);
$footer          = rawurlencode($_POST['footer']);
$message_gupshup = rawurlencode($final_template_gupshup);
```

So `$message_gupshup`, `$header` and `$footer` are safe. **Do not re-encode them.**

The genuinely unencoded values interpolated at :440 and just below:

| Value | Source | Risk |
|---|---|---|
| `$_POST['template_category']` | raw form input | staff-controlled, direct injection |
| `$template_language` | derived server-side | low, but unencoded |
| `$template_id` | template name | staff-influenced |
| `$variables_format` | `json_encode($columnArray)` at :402 | **highest** — JSON contains `{`, `}`, `"`, `,` routinely |
| `$dynamic_url_buttons` | JSON, appended at :443 | same as above |
| `json_encode($quick_reply_buttons)` | JSON, appended at :447 | same as above |

`$variables_format` is the one most likely to be misbehaving in production today,
since `json_encode` output always contains characters that need encoding.

## How it will be fixed

Wrap the six unencoded values in `rawurlencode()` at the point of interpolation.
Leave `$message_gupshup`, `$header` and `$footer` alone.

The tidier alternative is `http_build_query()` over an associative array, which
encodes everything correctly by construction:

```php
$post_field = http_build_query([
    'userid'   => $_ENV['WTSAPP_USERNAME'],
    'password' => $_ENV['WTSAPP_PASSWORD'],
    'type'     => 'text',
    'method'   => 'create_whatsapp_hsm',
    'category' => $_POST['template_category'],
    ...
]);
```

**But that requires un-encoding the three already-encoded values first**, or they
end up double-encoded. Given this is a live messaging path and the minimal fix is
low-risk, **the plan takes the `rawurlencode()` route** and notes
`http_build_query` as a follow-up. Match the surrounding style rather than
modernising mid-file, per the project conventions.
