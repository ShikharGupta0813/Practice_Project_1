# CRITICAL - cbs/controllers/BankManagement.php:7497, 7575, 11795, 12141, 12843, 12921 — six SELECT sites vulnerable to UNION-based extraction via branch_id/center_id

Asana: https://app.asana.com/0/0/1217811081134085/f  |  ID: 1217811081134085  |  Due: no due date

---
# PART 1 — In simple words

## What the system does today

A bank is organised into branches, and branches into centres. Each branch and centre
offers a particular set of products and services. When staff open one of the screens
that shows or edits those, the system asks the database "which products are switched
on for this bank, this branch and this centre?"

It builds that question by gluing the three identity numbers into a sentence and
sending the sentence to the database.

## What is wrong with it

The three numbers are glued in without being checked, in six separate places.

A database question is just a sentence, and the database answers whatever it is
asked. If one of those three values contains a fragment of database language instead
of a number, the fragment becomes part of the question.

What makes this worse than the delete-type flaw elsewhere in this batch is that
these are questions, and a question returns data. There is a well-known technique
for attaching a second question onto the end of the first so that the answers come
back in the same list — so instead of getting back a list of product numbers, the
attacker gets back whatever they asked for. Customer records, stored keys, staff
password hashes: anything in the database is reachable from any one of these six
lines.

The values arrive as part of the web address, so no form needs to be filled in — a
crafted link is enough.

The screens are behind a login, so this needs a signed-in account. But it lets any
signed-in account read the entire database regardless of what they are permitted to
see, which defeats the permission system entirely.

## What we are going to change

Stop gluing the numbers into the sentence. Hand the sentence and the three values to
the database separately, so they can only ever be read as numbers. Six places, the
same change in each.

## What could go wrong

Almost nothing functionally — for genuine numeric values the questions return exactly
what they return today.

The one thing to watch is that these six lines are not quite identical. Four ask
about services and two about products, and one of them uses a different table with
only two of the three values. Copying the fix carelessly from one to another could
point a question at the wrong table, which would show staff the wrong list of
products or services on a branch screen.

# PART 3 — The technical version

## Root cause

Six raw `SELECT` statements in
`application/modules/cbs/controllers/BankManagement.php`, all interpolating
`$id`, `$branch_id` and `$center_id` in numeric context with no quoting, cast or
binding. Example at :7497:

```php
$sql = "select DISTINCT product_id from tbl_cbs_center_products where is_active ='1' and bank_id =" . $id . " and branch_id =" . $branch_id . " and center_id = " . $center_id . " and product_id NOT IN ( SELECT DISTINCT product_id from tbl_cbs_center_products where is_active ='0')";

$center_products = $this->CommonModel->sql($sql);
```

Numeric context means there are no quotes to escape out of — appending
` UNION SELECT ...` to any of the three values is sufficient. The values reach these
methods as route parameters, so a crafted URL is the whole attack.

**Line numbers have drifted. Only the first still matches the task title:**

| Task title | Actual | Table | Values used |
|---|---|---|---|
| 7497 | **7497** ✅ | `tbl_cbs_center_products` | id, branch_id, center_id |
| 7575 | **7573** | `tbl_cbs_center_services` | id, branch_id, center_id |
| 11795 | **11889** | `tbl_cbs_center_services` | id, branch_id, center_id |
| 12141 | **12235** | `tbl_cbs_branch_services` | id, branch_id **only** |
| 12843 | **12937** | `tbl_cbs_center_products` | id, branch_id, center_id |
| 12921 | **13015** | `tbl_cbs_center_services` | id, branch_id, center_id |

Note **:12235 is the odd one out** — it queries `tbl_cbs_branch_services` and takes
only two values, not three. A copy-paste fix from any of the others would be wrong
there.

## How it will be fixed

Convert each to a bound query. `CommonModel->sql()` takes a prepared string, so
either extend it to accept bindings or use `$this->db->query($sql, $params)`
directly. **Step 1 of the plan settles which** — do not assume `CommonModel->sql()`
supports a second argument.

Target shape:

```php
$sql = "select DISTINCT product_id from tbl_cbs_center_products
        where is_active = '1' and bank_id = ? and branch_id = ? and center_id = ?
        and product_id NOT IN (SELECT DISTINCT product_id FROM tbl_cbs_center_products WHERE is_active = '0')";
$center_products = $this->db->query($sql, [(int) $id, (int) $branch_id, (int) $center_id])->result_array();
```

Casting as well as binding is belt and braces, but these are known-integer columns
and it makes the intent obvious to the next reader.

## Files and scope

Written against production (`onestackcbs`).

| File | Lines | What changes |
|---|---|---|
| `application/modules/cbs/controllers/BankManagement.php` | 7497, 7573, 11889, 12235, 12937, 13015 | Bind `bank_id`, `branch_id`, `center_id` in each of the six statements. |

Total: 1 file, roughly 30 lines changed.
**Medium** — the change is simple but the file is ~13,000 lines and the six sites
are spread across it, so each needs locating and testing individually.

**Evidence**

```
grep -n '$sql = "' application/modules/cbs/controllers/BankManagement.php
  -> 7497 7573 11889 12235 12937 13015     (6 raw SQL statements in the file, all six are these)

grep -n 'branch_id =" *\. *\$' application/modules/cbs/controllers/BankManagement.php
  -> same 6 lines
```

Both searches return the same six lines, and each was read in full to confirm the
table and the value list. **No other raw `$sql = "` exists in this file**, so the
six is the complete set — this is not a sample.

## Plan

1. Determine whether `CommonModel->sql()` accepts bindings:
   `grep -n "function sql" application/models/common/CommonModel.php` and read it.
   If it does not, use `$this->db->query($sql, $params)` at the call sites and
   leave `CommonModel` alone — do not change a shared model for six callers.
2. Fix :7497 first and test that screen before touching the others, to validate the
   chosen approach.
3. Fix :7573, :11889, :12937, :13015 — all three-value, but confirm each table name
   against the table above as you go.
4. Fix :12235 **separately and carefully** — two values, different table.
5. Confirm the result-handling after each query is unchanged (`->result_array()`
   vs whatever `CommonModel->sql()` returned). A shape change here would silently
   empty the product/service lists.
6. Commit.

## How to test

```bash
php -l application/modules/cbs/controllers/BankManagement.php
```

```bash
grep -c 'branch_id =" *\. *\$' application/modules/cbs/controllers/BankManagement.php
```
Expected: `0`.

Behavioural, signed in as cbs admin on staging. **Each of the six sites drives a
different screen — all six must be opened:**

1. Branch → centre → products screen. Expect the same product list as before the
   change. (:7497, :12937)
2. Branch → centre → services screen. Expect the same service list. (:7573,
   :11889, :13015)
3. Branch-level services screen. Expect the same list — this is the two-value
   query at :12235 and the most likely to be broken by a careless fix.
4. For a branch/centre with **no** configured products, confirm the screen still
   renders an empty list rather than erroring — the `NOT IN` subquery behaves
   differently with bound empties.
5. Injection check: request one of these screens with `center_id` set to
   `1 UNION SELECT 1` in the URL. Expect an empty or error result, and confirm
   nothing from another table is rendered.

Regression: confirm saving a change on the branch and centre product/service
screens still persists, since these queries feed the "currently enabled" state that
the save compares against.

## Needs human review

`yes` — six sites across a 13,000-line controller driving bank configuration
screens; a wrong table or a changed result shape would misconfigure branch products
and services without an obvious error.
