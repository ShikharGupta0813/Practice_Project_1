# PART 1 — In simple words

## What the system does today

In the mobile app, a customer can open their profile and change their name,
mobile number or email, and look at their transactions and support tickets. To
change a mobile number or email, the app sends a one-time code (OTP) to the new
number or address; the customer types it in and the change is saved.

Each time, the app tells the server *which customer* it is talking about by
sending a customer number in the request. The server also already knows who is
logged in, from the login token the app sends.

## What is wrong with it

The server believes the customer number in the request, not the login.

The original bug (the one in the title) saved a new number onto a completely
different customer. Priyanka fixed that part on 22 September. But the server
still prefers the number in the request. So a logged-in customer can put
**someone else's** customer number in the request and:

- change that person's mobile number to their own phone (the OTP goes to the
  attacker's own phone, so they can type it in). Login is by mobile OTP, so this
  means **taking over the other person's account**;
- change that person's name;
- read that person's transactions and support tickets.

## What we are going to change

The server will ignore the customer number in the request and always use the
customer who is logged in. A logged-in customer can then only see and change
their own details.

## What could go wrong

- If some version of the app sends a customer number different from the
  logged-in customer on purpose, it will now act on the logged-in customer
  instead. Nothing in the server code suggests that is a legitimate case:
  family ("child") logins are already refused by all of these screens.
- Records damaged by the old bug before 22 September are **not** repaired by
  this change. That is a separate data fix (query at the end).

| Word | What it means, simply |
|---|---|

| Login token | A pass the app gets at login and sends with every request; the server reads the customer from it. |

# PART 3 — The technical version

## Root cause

`DashboardDefaultState` (apiv2 and apiv6 identical; old `api/DashboardDefaultSatet`
the same) takes the customer to act on from the decrypted request body, not from
the JWT. The constructor already has the right value:

```php
$return_val = $this->jwt->authorizeToken();                                         // apiv2 :13
$this->customerId = isset($return_val['customer_id']) ? $return_val['customer_id'] : null;   // :14
```

The task's own bug (`'id' => $company_id`) was fixed by Priyanka in `affaa8a262`
(2026-09-22), which is on `onestackcbs`. The task's line 947 no longer matches;
that code is now :961-990. Her fix introduced the remaining problem, where the
request value wins over the token:

```php
$targetCustomerId = !empty($apiRequest['customer_id']) ? $apiRequest['customer_id'] : (isset($this->customerId) ? $this->customerId : 0);   // apiv2 :891, :964
```

Every method in the class that reads `$apiRequest['customer_id']` to choose a
customer (apiv2 and apiv6 line numbers are identical):

| Method | apiv2/apiv6 line | api/ line | Effect today |
|---|---|---|---|
| `getProfileDetails()` | 596 | 408 | read name, PAN, mobile of any customer (**no route**) |
| `updateName()` | 639 | 453 | rename any customer |
| `updateMobileNoEmail()` | 689, 774 | 504, 592 | send change OTP for any customer |
| `verifyOpt()` | 891, 964 | 702, 776 | write new mobile/email onto any customer |
| `update_resend_otp()` | 1078 | 881 | resend OTP for any customer |
| `myTransactions()` | 1167 | 966 | read any customer's transactions |
| `transactionDetails()` | 1224 | 1017 | read any customer's transaction |
| `getRecentTickets()` | 1273 | 1066 | read any customer's tickets |
| `getAllTickets()` | 1328 | 1120 | read any customer's tickets |

All of them run inside `if ($this->customerId)`, so a valid login is needed, but
nothing ties the request's id to it.

Child logins: the JWT for a child carries the parent's `customer_id` plus
`child_id` (`third_party/jwt/libraries/Jwt.php:69-77`). Every method above ends
with `if ($this->api_child_Id) { ... "No Access" }`, but that runs **after** the
work is done (e.g. `updateName()` :655-667 writes, then says "No Access"). So
children have no legitimate use of these endpoints.

## How it will be fixed

1. In each method in the table, take the customer from the token:
   - `$customer_id = $apiRequest['customer_id'];` becomes `$customer_id = $this->customerId;`
   - `"id" => $apiRequest['customer_id']` becomes `"id" => $this->customerId`
   - the two `$targetCustomerId = ...` lines in `verifyOpt()` become
     `$targetCustomerId = $this->customerId;`
2. In the three **write** methods (`updateName`, `updateMobileNoEmail`,
   `verifyOpt`), stop child logins from writing: change the gate
   `if ($this->customerId) {` to `if ($this->customerId && !$this->api_child_Id) {`.
   Otherwise a child's request would now write to the parent. The existing
   trailing "No Access" response is kept as is.
3. `api/DashboardDefaultSatet.php` (old copy, extends `MY_Controller`, no route on
   production): same edits. Its `updateMobileNoEmail()` gates on
   `if(isset($apiRequest['customer_id'])){` (:502); that becomes
   `if($this->customerId && !$this->api_child_Id){`.
4. Log lines that print `$apiRequest['customer_id']` (e.g. :700, :786, :919, :922)
   are left alone. They record what was sent, which is useful for spotting abuse.

Not changed (separate):
- Repairing customers overwritten before 2026-09-22 (read-only query at the end).
- The OTP lookup itself (`OTP_LOG` by otp + mobile + company), fixed by Priyanka.
