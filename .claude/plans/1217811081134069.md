# PART 1 — In simple words

## What the system does today

Staff upload reconciliation files — the spreadsheets used to check that the bank's
own records of money moved match what the payment networks say moved. When a member
of staff uploads one, the system files it into a folder built from three things
they chose on the form: which bank it belongs to, which category of report it is,
and the date.

So a file might be filed under "bank ABC / daily settlement / 2026-09-01". The
system then also copies it to cloud storage and records the upload in the database.

## What is wrong with it

The bank name and the report category are typed into the form and used to build the
folder path without being checked. Nobody confirms that "bank ABC" is a real bank
we know about, or that the category is one of the real categories.

Because those two values become part of the folder path, someone can put folder
navigation characters in them and steer the upload out of the reconciliation area
into somewhere else on the server.

The folder that gets created is also marked so that anything on the server can
write into it.

This is less severe than it first appears, and the task title overstates it in one
respect. **The file name is already handled properly** — the code strips it down to
a plain name and removes unusual characters before saving. So a stranger cannot
simply choose an arbitrary file name. And unlike some of the other tasks in this
batch, this screen **is** properly locked: you have to be signed in as staff to
reach it.

What remains is still worth fixing. A signed-in member of staff — or anyone who
gets hold of a staff session — can write files outside the intended area, and the
loose folder permission makes anything written there changeable afterwards.

## What we are going to change

Check the bank and the category against the real lists before using them to build
a path. Confirm the final destination is still inside the reconciliation area
before writing. Tighten the folder permission. And add a check on the file type, so
only genuine spreadsheet and document types are accepted.

## What could go wrong

If staff currently upload under bank or category names that do not exactly match
what is in the database — a spelling variation, an old code that was renamed —
those uploads will start being refused. That would look like a sudden breakage to
the reconciliation team.

The safest order is to log what would have been rejected first, look at a week of
real uploads, and only then start refusing. That is reflected in the plan.

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/mis/ReportController.php`,
`fingate_upload_udir()`.

**Line numbers have drifted.** The task says 1078-1120. The function actually
starts at **:1065** and runs to roughly **:1170**. The path construction is at
**:1097**.

```php
$type   = $this->input->post('type');
$folder = $this->input->post('folder');
$bank   = $this->input->post('bank');
$fromDate = $this->input->post('from_date');
...
$uploadPath = FCPATH . "uploads/rbi_reports_msl/{$bank}/{$folder}/{$formattedDate}/";

if (!is_dir($uploadPath)) {
    mkdir($uploadPath, 0777, true);
}
```

Confirmed defects:

1. **`$bank` and `$folder` interpolated raw into the path** (:1097). Both come
   from `$this->input->post()` with only an empty check at :1083. No allowlist, no
   `realpath()` containment. `../` in either escapes `uploads/rbi_reports_msl/`.
2. **`mkdir($uploadPath, 0777, true)`** (:1100) — world-writable, recursive.
3. **No extension allowlist.** `$fileExt` is computed at :1105 and again at :1110
   but never validated against anything before `move_uploaded_file()` at :1119.

**The task title is partly overstated — correct the record:**

- The **filename is already sanitised** at :1106:
  ```php
  $safeFilename = preg_replace('/[^a-zA-Z0-9-_\.]/', '_', basename($originalName));
  ```
  `basename()` plus a character filter. This is not a filename-injection hole.
- The controller **is authenticated**. Unlike task 37, this class calls its parent
  properly (`ReportController extends Admin_Controller`, `parent::__construct()`
  live at :12). So this requires a valid staff session — it is privilege abuse or
  session theft, not an anonymous internet attack.

Net: real, but **HIGH rather than CRITICAL** in practice. Worth saying in the PR.

`$bank` and `$folder` are also written into the S3 key at :1121 and stored in the
`RECON_UPLOADED_FILES` row at :1131-1155, so validating them fixes three
consumers, not one.

## How it will be fixed

- Validate `$bank` against the bank list already available via `CommonModel`
  (the same source the upload form populates its dropdown from).
- Validate `$folder` against the known reconciliation folder set.
- After building `$uploadPath`, assert with `realpath()` that it is still under
  `FCPATH . 'uploads/rbi_reports_msl/'` before `mkdir` or `move_uploaded_file`.
- Change `mkdir(..., 0777, true)` to `mkdir(..., 0755, true)`.
- Add an extension allowlist (`xlsx, xls, csv, pdf`) checked against `$fileExt`
  before `move_uploaded_file()`, returning the existing JSON error shape on
  rejection.
- Leave the existing filename sanitisation as is — it is correct.
