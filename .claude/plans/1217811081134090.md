# PART 1 — In simple words

## What the system does today

Every screen and every button in the admin area has its own web address. The
system reads the end of that address to decide which permission to check. An
ending of `-view` means "is this person allowed to look?". `-add` means "allowed
to create?", `-edit` means "allowed to change?" and `-delete` means "allowed to
remove?".

If an address has none of those endings, the system uses the whole middle part of
the address as a menu name. It then looks that menu up in the list of menus. If
the menu isn't in the list, the system **lets the request through**.

The first batch of this task (already in pull request #13247) fixed 20 addresses
that change data but were labelled "look". This is the second and last batch.

## What is wrong with it

There are 45 more addresses that change data but are not checked properly.

- **9 working actions carry the "look" label or a made-up label.** The biggest
  is "send SMS / WhatsApp to imported customers". Anyone who can merely *view* the
  SMS or WhatsApp screen can mass-message the bank's customers today. The others
  reset screen preferences, save module settings, and switch a vendor mapping on
  or off.
- **33 are old duplicate addresses that nothing uses any more.** Most were added
  automatically as aliases (a second name for the same thing) during an earlier
  clean-up. Every page now uses the properly labelled twin, so nothing calls the
  aliases. Because they carry no proper label, their menu name is never found, so
  they let *any* logged-in admin through. They are unlocked side doors nobody
  uses. One of them even points to code that doesn't exist.
- **3 (`admin/automated/...`) are a different, bigger problem.** The code behind
  them does not check that anyone is logged in at all. Changing their label would
  do nothing. That is being handled as a separate task.

## What we are going to change

- Give the 9 working actions the correct label ("add" or "edit"). Update every
  page and script that calls them to the new address, so nothing stops working.
- Switch off the 33 unused duplicates by commenting them out. This is how the
  codebase already marks 51 other unused routes, and it is easy to undo.
- Leave the 3 `automated` addresses alone.

## What could go wrong

- **People may lose access they have today.** Staff who could send bulk SMS with
  only "view" permission will need "add" permission afterwards. Shikhar is
  handling permission grants separately. The plan does not change anyone's
  permissions.
- **A missed caller would break a button.** If some page still used an old
  address, its button would stop working. Every caller has been searched for and
  listed below, and the test step re-checks for leftovers.
- **Anything outside the code that still used a switched-off address would get
  "page not found".** Examples are a bookmark or an external script. These are
  button actions (form posts), not pages people bookmark, so the risk is low.
- **The two "reset preferences" changes will have no effect yet.** The
  preferences screen has no entry in the menu list, so the system still lets
  those requests through. They only start being enforced when the separate
  "Block unauthorized access" task ships. That is fine: the labels will already
  be correct when it does.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Route | A rule that connects a web address to the piece of code that handles it. |
| Slug | The menu name inside the address, e.g. `sms` in `admin/sms-add/...`. |
| Action / suffix | The ending on the slug (`-view`, `-add`, `-edit`, `-delete`) that says which permission to check. |
| Alias | A second address pointing at the same code as another address. |
| Caller | A page or script that sends the browser to an address, e.g. when a button is pressed. |
| Fail open | When a check can't decide, it allows the request instead of refusing it. |
| Comment out | Switch a line off by marking it as a note, without deleting it. |

# PART 3 — The technical version

## Root cause

`application/core/MY_Controller.php:348-355` derives the permission from
`segment(2)` only:

```php
if (in_array($possibleAction, $validActions)) {
    $this->url_action = $possibleAction;
    array_pop($parts);
    $this->url_slug = implode('-', $parts);
} else {
    $this->url_slug   = $segment2;
    $this->url_action = 'view';
}
```

`application/libraries/PermissionService.php:152` then fails open when the slug
has no menu row:

```php
if (empty($menu)) {
    ...
    return true;
}
```

So there are two defects:
- **Explicit wrong suffix:** e.g. `admin/sms-view/cbs/import-customers-sms/(:any)`
  is checked against `display_action` of the `sms` menu.
- **No valid suffix:** e.g. `admin/save-product` derives slug `save-product`.
  There is no such menu row, so the request is allowed for any logged-in admin.
  `product_configuration-save` and `vendor_configuration-update` are the same
  case, because `save` and `update` are not recognised actions.

The production menu rows (queried by Shikhar, 2026-09-23) exist for `bank-list`
(89), `product_configuration` (65), `sms` (28), `vendor_configuration` (207) and
`whatsapp` (29), all active. **There is no row for `prefs`.**
