# PART 1 — In simple words

## What the system does today

There is an admin screen where a member of bank staff updates a customer's
contact details. On that screen they can also upload three documents: the
customer's signature, their photograph, and an address proof.

Before accepting those uploads, the program needs somewhere on the server's
disk to put them. So it checks whether a folder called `customer-kyc` exists,
and if it does not, it creates one.

When a program creates a folder it also has to say who is allowed to read from
it and write into it. Think of it as deciding, at the moment you install a
locker, who gets a key. That instruction is a short numeric code.

## What is wrong with it

The numeric code is being passed as text instead of as a number — the
difference between writing `0777` and writing `"0777"` with quote marks around
it. The language does not reject it. It quietly reads the text as a completely
different number, and the folder ends up created with the wrong set of keys:
effectively nobody can write into it, not even the program that just made it.

What this means for a real person: on a server where that folder does not
already exist, a staff member fills in a customer's contact details, attaches
the signature and photograph, presses save — and the uploads fail. The folder
in question is **not** shipped with the code, so on any freshly set up server it
genuinely does not exist and does get created wrongly.

On servers that have been running for a long time the folder was created at some
point in the past and is already there, so the faulty instruction never runs and
nothing looks broken. That is why this has gone unnoticed, and why the task is
marked LOW rather than urgent — it is a trap waiting for the next fresh
deployment, not something failing right now.

## What we are going to change

Remove the quote marks, so the permission code is passed as a number the way the
language expects. A change to one line. Nothing about how the screen works, what
it saves, or who may use it changes at all.

## What could go wrong

Very little. On any server where the folder already exists, this change has no
effect whatsoever — the line it fixes never runs. On a server where the folder
does not exist, the folder will now be created correctly instead of incorrectly,
which is the intended improvement.

One honest caveat: this fix does not make document uploads work end to end on a
brand new server. The code only ever creates the parent `customer-kyc` folder,
never the three sub-folders (`signature`, `photograph`, `address_proof`) that the
uploads actually go into. Those are missing too. We are deliberately **not**
changing that here, because it is outside what this task asks for and it changes
behaviour rather than correcting a typo. It is written down so nobody is
surprised, and it should become its own task.

# PART 3 — The technical version

## Root cause

`application/modules/cbs/controllers/CustomerAccountManagement.php:2035`, inside
`UpdateCustomerContactDetails()`:

```php
$folder = './internal-excel-files/customer-kyc';
if (!file_exists($folder)) {
    mkdir($folder, '0777', true);
}
```

`mkdir()`'s second parameter is `int $permissions`. `'0777'` is a numeric string,
so PHP 8 coerces rather than raising a TypeError — but it coerces to decimal
**777**, not octal `0777`. Decimal 777 is octal `01411`: the sticky bit plus mode
`0411` (owner `r--`, group `--x`, other `--x`). Before umask is even applied, the
directory is not writable by its owner.

Verified on `onestackcbs`:

- The literal is still `'0777'` at line 2035.
- `internal-excel-files/customer-kyc` is **not** present in the tree
  (`git ls-tree -r origin/onestackcbs` returns nothing under that path), so on a
  fresh deployment the `mkdir()` branch does execute.
- The only other `mkdir()` in this file, line 7121, already passes `0755`
  correctly and is not touched.

## How it will be fixed

Drop the quotes: `mkdir($folder, 0777, true);`.

Scope is held to the literal. No new guard on the `mkdir()` return value, no
creation of the `signature` / `photograph` / `address_proof` sub-directories, no
change to the surrounding upload configuration — all of those alter behaviour,
and this task is a correctness typo fix.
