# HIGH - Remove/secure the plaintext, unauthenticated soundbox command endpoint

Asana: https://app.asana.com/1/1139764983605995/task/1217811081134144  |  ID: 1217811081134144  |  Due: 2026-09-10

> Scope note: this plan reflects decisions taken with the task owner after a live
> test. The endpoint was found to be **firewalled** (external requests time out;
> only allowed hosts reach it), so the "anyone on the internet can trigger it"
> threat does not currently hold. The owner has chosen to: move the call to
> **HTTPS + a domain name** (hiding the raw IP) with certificate verification
> turned OFF (the `curl -k` equivalent, justified by the firewall and checks
> handled elsewhere), fix a real reliability bug, and stop a credential from
> being written to logs. A cryptographic signature was considered and
> **deliberately skipped** — see "What we are NOT doing".

# PART 1 — In simple words

## What the system does today
When a customer pays a shop by UPI, the shop's little speaker box announces the
amount out loud ("2 rupees received"). To make that happen, our system sends a
small message over the internet to a second machine we own (the "notification
server"). That machine passes it on to the speaker.

Right now our system sends that message using a **web address written as a bare
number** (an IP address, `43.205.84.158`) over an **unencrypted** connection
(plain `http`, no padlock). The message is sent with **no proof of who sent
it** — the receiving machine simply trusts whatever arrives.

## What is wrong with it
Three separate things:

1. **The connection has no padlock (plaintext).** The message travels
   unencrypted. On its own this is low risk here, because both machines are ours
   and sit on a protected network — but the reply that comes back currently
   contains a **password**, and sending a password in the clear is bad practice.

2. **That password is being written into our log files and our database** every
   single time a box speaks. Anyone who can read our logs or database can see
   it. Our own house rules say never write passwords into logs.

3. **If the notification server is slow, a real payment gets stuck waiting.**
   The current setting tells our system to "wait forever" for the speaker to
   answer. A slow speaker can therefore hold up an actual payment.

We checked whether an outsider could abuse the open endpoint: from outside the
network the request simply times out. So a stranger on the internet **cannot**
reach it today. The remaining problems are the three above — internal hygiene
and reliability, not an open door to the world.

## What we are going to change
- Send the message to a proper **web-address name** (a domain) instead of a bare
  number, over an encrypted `https` connection — this also hides the number.
- **Stop writing the password** into logs and the database.
- Change "wait forever" to "wait 5 seconds", so a slow speaker can never hold up
  a payment.
- Put the web address in one settings file instead of pasting it in seven
  places, so it can be changed in one spot later.

## What could go wrong
- This code sits **inside the live payment flow**. The changes are small and do
  not touch the money itself — only the "make the speaker talk" step — but it
  must be tested carefully because it runs on real transactions.
- If the new domain name is typed wrong or its certificate is misconfigured, the
  speakers could go quiet. We test with the built-in checker tool (which uses
  the exact same path) before trusting it on live payments.
- Changing "wait forever" to "wait 5 seconds" could, in theory, make a very slow
  speaker occasionally miss an announcement — but that is far better than
  holding up a payment, and real announcements are near-instant.

## What we are NOT doing
- **We are NOT adding a digital signature.** A signature would prove the message
  came from something that knows a shared secret. But every one of our own files
  would share that same secret, so it could not tell our payment code apart from
  any other script on the same server — and the firewall already blocks
  outsiders. Given that, a signature adds almost nothing here, so it is left out
  by choice.
- **We are NOT turning on strict certificate checking.** The owner has chosen
  the `-k` (skip-verification) behaviour for now, because access is already
  restricted by the firewall and identity is handled elsewhere. This can be
  switched on later by flipping two settings, with no other code change.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| IP address | A machine's location written as bare numbers, e.g. `43.205.84.158`. |
| Domain | A readable name for a machine, e.g. `notifications.onestack.in`. |
| HTTP / HTTPS | Sending data without / with a padlock (encryption). |
| Certificate | The ID card a server shows to prove the padlock is really theirs. |
| `-k` / verify off | "Use the padlock but don't check the ID card." |
| cURL | The tool our PHP uses to send a web request. |
| Timeout | How long to wait for a reply before giving up. |
| Firewall | A gate that only lets approved machines talk to a server. |
| MQTT | The messaging system the speakers use to receive announcements. |

# PART 3 — The technical version

## Root cause
The same soundbox-publish cURL block is copy-pasted across **7 call sites in 6
files**, each hardcoding a plaintext IP, an infinite timeout, and each logging
the raw response — which contains the broker password.

Confirmed by reading the code (line numbers are on the current working branch
`sg_cl_log_dirs_on_fresh_deploy`; they will differ slightly on `onestackcbs` —
the Asana title cites the older August lines, e.g. `Payment.php:3094`, which no
longer match):

**The 7 hardcoded-URL sites:**
```
grep -rn "43.205.84.158" application/ --include=*.php   (worktrees excluded)
```
- `application/modules/mobile_app/controllers/Payment.php:3121`
- `application/modules/mobile_app/controllers/Cron.php:7215`
- `application/modules/mobile_app/controllers/Cron.php:7380`
- `application/modules/mobile_app/controllers/HdfcCron.php:481`  ← NOT in the Asana title
- `application/modules/mobile_app/controllers/npci-upi/NpciCron.php:3081`
- `application/modules/mobile_app/controllers/npci-upi/NpciFinancialCron.php:2249`
- `application/modules/mobile_app/controllers/configuration/SoundboxChecker.php:364`

7 sites, 6 files, verified by eyeballing every match (no false positives). The
task title lists 5 files/6 sites and **omits HdfcCron.php** and the second
Cron.php site.

**Infinite timeout** — each block sets:
```php
CURLOPT_TIMEOUT => 0,   // Payment.php:3171, Cron.php:7487, HdfcCron.php:529,
                        // NpciCron.php:3142, NpciFinancialCron.php:2310,
                        // SoundboxChecker.php:439
```
`sendToSoundbox()` is called from ~9 points in Payment.php inside the live bank
callbacks (`yesbank_trans_callback`, `icici_subscriber_callback`,
`subscriber_callback`, `p2pm_yesbank_trans_callback`) and is **not** wrapped in
try/catch, so a hung publish blocks the payment thread.

**Credential leak** — the notification server's response body includes
`Execution.Command`, which is the literal `mosquitto_pub ... -P '<password>'`
string. The code logs the raw response and stores `Execution` verbatim:
```php
// raw $response written to logs (contains the password):
Payment.php:3182        "Response" => json_encode($response)
HdfcCron.php:540         "Response" => json_encode($response)
NpciCron.php:3156        $txt3 .= "Response  : " . $response
NpciFinancialCron.php:2324  $txt3 .= "Response  : " . $response
SoundboxChecker.php:453  $txt3 .= "Response  : " . $response

// Execution stored in DB (SOUNDBOX_PUB_MSG_LOG / checker table):
Payment.php:3195         'response' => json_encode($data['Execution'])
HdfcCron.php:553         'response' => json_encode($data['Execution'])
NpciCron.php:3172        'response' => json_encode($data['Execution'])
NpciFinancialCron.php:2340  'response' => json_encode($data['Execution'])
SoundboxChecker.php:486  'response' => json_encode($data['Execution'] ?? array())
```
This directly violates the CLAUDE.md rule "Never log secrets, tokens, or PII".

**Network exposure — verified reassuring.** Live test (this session): the same
POST from an external host times out (`HTTP 000`, connection dropped); from the
admin server it succeeds and the box speaks. So a firewall/security-group
already restricts the endpoint to allowed hosts. This is why the plan does not
add application-layer authentication.

## How it will be fixed
In-place edits to the 7 cURL blocks (no new shared abstraction — CLAUDE.md says
do not introduce new patterns mid-file; these are procedural controllers):

1. **URL from config.** Add two constants in `application/config/constants.php`
   using the existing `$_ENV` pattern, and set them in `.env`:
   ```php
   define('SOUNDBOX_NOTIFY_URL', $_ENV['SOUNDBOX_NOTIFY_URL']);
   ```
   ```
   SOUNDBOX_NOTIFY_URL=https://notifications.onestack.in/play-soundbox-string.php
   ```
   Replace each `$curl_url = 'http://43.205.84.158/play-soundbox-string.php';`
   with `$curl_url = SOUNDBOX_NOTIFY_URL;` (Cron.php:7380 uses `$url`; set it the
   same way).

2. **HTTPS + `-k` behaviour.** In each cURL option block add:
   ```php
   CURLOPT_SSL_VERIFYPEER => false,
   CURLOPT_SSL_VERIFYHOST => 0,
   ```
   (These are inert until the URL is https; the URL constant already is.)

3. **Timeout.** Change `CURLOPT_TIMEOUT => 0` to `CURLOPT_TIMEOUT => 5` in all 7
   blocks.

4. **Stop logging the password.** After each `$data = json_decode($response,
   true);`, strip the command before anything is logged or stored:
   ```php
   if (isset($data['Execution']['Command'])) { unset($data['Execution']['Command']); }
   ```
   Replace the raw-`$response` log lines (Payment:3182, HdfcCron:540,
   NpciCron:3156, NpciFinancial:2324, SoundboxChecker:453) to log the sanitised
   `json_encode($data)` instead of the raw `$response`. The DB `'response'`
   inserts already read `$data['Execution']`, so the same `unset` cleans them.
   Where the raw-response log happens *before* `json_decode`, move the decode up
   first (or decode a local copy for logging).

5. **Env parity.** Add `SOUNDBOX_NOTIFY_URL` to every environment's `.env` /
   env template that runs these controllers, so production, sandbox and public
   all resolve the constant. (Do not rely on the local `.env` as evidence of
   what production has — confirm with ops.)

Optional / not in this change: wrapping `sendToSoundbox()` calls in try/catch
(defence for the payment thread) — noted for review, not required to close the
task.
