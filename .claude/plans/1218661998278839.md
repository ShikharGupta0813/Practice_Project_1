Parent: Services Configuration for Production (1218501688848853)

# PART 1 — In simple words

## What the system does today
When a customer logs in to the app (or finishes verification), our server
sends the app three YES Bank keys for their bank:
- an encryption key,
- a reference prefix,
- a "production type".

The app uses these to register the customer as a seller with YES Bank (YPP).
Today those three keys are read from the **old** vendor settings tables.

## What is wrong with it
Nothing is broken. But OneStack is moving every outside service into the new
settings book. KYC has already moved. YPP Seller hasn't.

## What we are going to change
The three keys will be stored per bank in the new settings book and read from
there. The app will receive exactly the same four fields as today, with the
same names.

If a bank's keys aren't in the new book yet, the server reads them from the old
tables as it does now, so logins keep working while the data is moved bank by
bank.

## What could go wrong
- **This runs on every app login.** If a bank's keys are entered wrongly in the
  new book, that bank's app users get wrong keys and their YES Bank features
  fail. So enter them on rbank first and test there.
- Other YES Bank settings (partner key, web addresses, certificates) are **not**
  moved. They stay where they are, as they did for KYC.

# PART 3 — The technical version

## Root cause / current state (onestackcbs)
- The reader `getBankKeysYesbankKYC($company_id, $mode)` exists twice:
  - `application/models/common/CommonModel.php:4088`
  - `application/modules/mobile_app/models/common/CommonModel.php:3945`

  `common/CommonModel` is autoloaded (`config/autoload.php:131`), and the
  mobile_app copy may also be loaded, so both copies must stay identical.
- It reads the old tables: `tbl_module_group.module_group_key = 'YPP_SELLER'`,
  `tbl_module_master.module_name = 'YPP - SELLER'`, and
  `tbl_company_module_config` keys `ENCRYPTION_KEY`, `PARTNER_REF_PREFIX`,
  `PRODUCTION_TYPE` (`$mode` column = sandbox_value or production_value).
  It takes `partner_key` from `tbl_company_master.yesbank_partner_key`.
- Callers (the only ones): `apiv7/Profile.php:1161/1164` (verify-otp) and
  `1890/1893` (verify-customer). The result goes to the app as
  `yesbank_keys: {encryption_key, partner_key, partner_ref_prefix, production_type}`.
- Production new tables (checked 2026-09-29) have no YPP Seller row.

## How it will be fixed (Priyanka's KYC pattern)
1. **Constant** in `constants.php`:
   `define('YPP_SELLER_MODULE', 'ypp_seller_ypp_seller');`
   That's the slug generated for Module Group **"YPP Seller"** plus Sub Module
   **"YPP Seller"**.
2. **Both** `getBankKeysYesbankKYC()` copies:
   ```php
   $vendorModule = getVendorModuleConfig($company_id, YPP_SELLER_MODULE);
   if ($vendorModule['status'] && !empty($vendorModule['config'])) {
       $config = $vendorModule['config'];
       // partner_key still from company_master, exactly as today
       return array(
           'encryption_key'     => isset($config['ENCRYPTION_KEY']) ? $config['ENCRYPTION_KEY'] : null,
           'partner_key'        => <company_master.yesbank_partner_key>,
           'partner_ref_prefix' => isset($config['PARTNER_REF_PREFIX']) ? $config['PARTNER_REF_PREFIX'] : null,
           'production_type'    => isset($config['PRODUCTION_TYPE']) ? $config['PRODUCTION_TYPE'] : null,
       );
   }
   // else: the existing old-table query, unchanged (fallback)
   ```
   - `$mode` stays in the signature, and callers are unchanged. The new tables
     hold one value per key: **the production DB stores production values and
     the rbank DB stores rbank values** (user decision). So `$mode` only matters
     for the fallback.
   - Key names and order in the returned array match today's row exactly, and
     missing values are null, as the old `MAX(CASE…)` gives.

**Data setup** (admin screens; rbank first, then production):
