# PART 1 — In simple words

## What the system does today

Two kinds of people log in to the admin panel: OneStack staff, who look after
every bank, and bank staff, who should only ever see their own bank.

The admin panel has report screens (tables on a page) and "Export" buttons that
turn those tables into a spreadsheet file. Most of the report screens already
check who is asking: OneStack staff see all banks, bank staff see only their own.

## What is wrong with it

Four places skip that check:

1. **Transaction export** — a bank employee pressing "Export" gets every bank's
   orders, including customer names, not just their own bank's.
2. **Monthly bank report export** — the file includes whichever bank the request
   names, so a bank employee can ask for another bank's figures.
3. **Monthly bank report screen** — it checks who you are, and *then* swaps in
   whichever bank the request names. The check happens before the swap, so it
   protects nothing. It is like checking someone's ID at the door and then letting
   them write any name on their visitor badge.
4. **SMS report (screen and export)** — shows every bank's SMS history, including
   customers' mobile numbers, to anyone who can open the page.

Nothing tells us this has been misused. But one bank's staff could see another
bank's customers and business figures, and a bank would be right to treat that
as a serious breach.

## What we are going to change

Every one of these places will use the same rule the neighbouring screens already
use: OneStack staff see everything; bank staff see only their own bank; anyone
asking for another bank is refused. The SMS report becomes OneStack-only.

## What could go wrong

- If a bank's staff currently rely on the transaction export and it quietly gave
  them all banks, they will now get only their own rows. That is the intended
  behaviour.
- Bank staff lose access to the SMS report entirely. You confirmed it is a
  OneStack-only page.
- A OneStack login that has a bank attached to it will see only that bank's rows
  in the transaction export. That matches what the matching on-screen list already does.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Session | What the system remembers about you after you log in — who you are and which bank you belong to. |
| `company_id` | The number that identifies a bank. A bank employee's session carries their bank's number; OneStack staff's does not. |
| Export | The button that downloads a report as a spreadsheet (CSV) file. |
| Request / POST value | Information the web page sends to the server. Anyone can change it, so it must never be trusted to say which bank you belong to. |

## How it will be fixed

Apply the existing helper pair at each site, exactly as the neighbouring code does.
Deny responses match the neighbours: JSON zero-records for datatable endpoints,
and a plain `Unauthorized access` + `exit` for CSV exports, emitted **before** the
CSV headers.

Per your decisions: there are no partner-only logins, so no `partner_id` handling
is added anywhere. Existing `partner` request filters used by OneStack staff are
left as they are.
