# CRITICAL - Stop logging credit-bureau request bodies - PAN/DOB/mobile

Asana: https://app.asana.com/1/1139764983605995/task/1217811081134136  |  ID: 1217811081134136  |  Due: 2026-09-15

# PART 1 — In simple words

## What the system does today

When the bank wants a customer's credit report, the system sends that customer's
identity details to a credit bureau — TransUnion CIBIL or Equifax. To ask the
question, it has to send the things that identify the person: their PAN (the tax
number the bureau uses to look someone up), their date of birth, and their mobile
number.

As it does this, the system also writes notes about what it is doing into log
files on the server. Log files are a diary the software keeps for developers, so
that when something goes wrong they can look back and see what happened.

The problem is what goes into the diary. At seven points in these two files, the
code does not write a summary of the request — it writes **the whole request**,
including the customer's PAN, date of birth and mobile number, in plain readable
text.

## What is wrong with it

Those identity details end up sitting in ordinary files on the server, in the
clear, for every credit check the bank has ever run.

Concretely, for a real customer: they applied for something, the bank checked
their credit, and their PAN and date of birth are now written in a plain text
file on a web server. Anyone who can read files on that server — a developer, a
support engineer, a contractor, a backup, or an attacker who gets in through any
unrelated hole — can read the identity details of every customer ever checked.
The customer never agreed to that and has no way to know.

PAN plus date of birth plus mobile number is the exact combination used to
impersonate someone at a bank. It is the raw material for identity theft, not
merely "sensitive data".

It is also a compliance problem. This data is exactly what RBI and the credit
bureaus require to be protected, and the log files have none of the protections
the database has.

Nothing here is a crash or a visible fault. The system works. That is why it has
gone unnoticed — the damage is silent and it accumulates every single day the
code runs.

## What we are going to change

Stop writing the request body into the log files. The diary entries stay — the
system still records which credit-bureau call was made, when, for which customer
reference, whether it worked, and how big the request was. It simply no longer
copies the customer's PAN, date of birth and mobile number into the file.

## What could go wrong

The honest cost: a developer debugging a failed credit check will no longer be
able to read the exact request that was sent, straight from the log.

That is a real loss and worth being clear about. It is softened by two things.
First, both files already write the full request into a proper database audit
table, which stays exactly as it is — so the record still exists, in the place
that has access control around it. Second, the logs keep everything needed to
find that database row: the call name, the customer and company reference, the
timestamp and the record number.

The other risk is ordinary care: these edits are inside working credit-bureau
code, so a careless change could break a live integration. The changes only
remove entries from lists of things being written to a file. No decision, no
calculation and nothing sent to the bureau changes.

# PART 3 — The technical version

## Root cause

Two credit-bureau controllers write the decoded or raw request body into
day-stamped log files under `application/logs/`. Verified line by line on
`onestackcbs`.

### `application/modules/mobile_app/controllers/mis/EquifaxController.php`

| Lines | Sink | What leaks |
|---|---|---|
| 73-81 | global `writeLog()` -> `transunion-log-<date>` | `"Request Body" => json_encode($apiRequests)` — the entire decoded Equifax request |

```php
$apiRequests = json_decode(file_get_contents('php://input'), true);

writeLog(
[
    "Action" => "API Requested",
    "API name" => $apiName,
    "Request Body" => json_encode($apiRequests),   // <- PAN / DOB / mobile
],
    "",
    $this->log_file
);
```

Note `$this->log_file` is set to `'transunion-log-'` at line 54, so the Equifax
controller writes into a TransUnion-named log file. That is confusing but out of
scope here.

### `application/modules/mobile_app/controllers/mis/TransUnion.php`

All six go through the private `writeLog()` at line 17, which appends to
`application/logs/transunion-logs-<date>.log`, except the last, which is a bare
`fopen`/`fwrite` to `application/logs/transunion/hitAPI-log-<date>.php`.

| Lines | Key | What leaks |
|---|---|---|
| 149-153 | `raw_input_preview` | first 500 bytes of the raw POST body |
| 160-165 | `raw_input` | first 1000 bytes of the raw POST body (JSON-decode-error path) |
| 192-196 | `request_structure` | the **entire** decoded request array |
| 225-230 | `merged_request` | the entire decoded request array, after merge |
| 420-424 | `create_data` | contains `'request' => json_encode($requestBody)` |
| 426-432 | `requestBody` | `json_encode($requestBody)` written via `fwrite` |

The task named only line 148 — that is the `file_get_contents('php://input')`
assignment feeding 149-153. The remaining five write the same PII to the same
files.

### Deliberately NOT changed

Two sites persist the request body to database audit tables. These are the
intended system of record, they sit behind database access control, and removing
them would destroy the audit trail this fix relies on as the replacement:

- `EquifaxController.php:459-463` — insert into `tbl_equifax_api_req_resp`
  (`'request_json' => json_encode($requestBody)`).
- `TransUnion.php:412-418` — insert into `DbTable::TRANS_API_REQ_RESP`
  (`'request' => json_encode($requestBody)`).

If the intent is that the bureau request body should not be retained *anywhere*
in the clear, that is a larger change (schema, retention, encryption at rest) and
belongs in its own task. Flagging it, not doing it here.

## How it will be fixed

At each of the seven sites, drop the key carrying the request body and keep the
surrounding metadata. Where a site would be left with nothing useful, keep an
identifying, non-PII substitute:

- `raw_input_preview` / `raw_input` -> removed; `raw_input_length` already present
  at 151 and is kept, and is added at 164 so the error path retains a size.
- `request_structure` / `merged_request` -> removed; `request_keys` (line 194) and
  `first_key` (line 227) already log the *shape* without the values, and are kept.
- `create_data` -> replaced with `'api_name'` and `'inserted_id'`, both already
  logged at 421-422, so the log still points at the audit row.
- `requestBody :` line in the `fwrite` block -> removed; the `api_name` line above
  it is kept.
- Equifax `"Request Body"` -> removed; `"API name"` is kept.

No masking or partial redaction. Masked PAN is still PII, and a half-redacted
value invites someone to "improve" it back later. The values simply do not go to
the log.

1. Confirm only the two intended files changed:


2. Confirm both files still parse:


3. **The main check** — no request-body-bearing key may remain in any log call.
   This must return nothing:

```bash
grep -nE "raw_input_preview|'raw_input'|request_structure|merged_request|'create_data'|requestBody : |\"Request Body\"" application/modules/mobile_app/controllers/mis/TransUnion.php application/modules/mobile_app/controllers/mis/EquifaxController.php
```

Expect **zero lines**. Any hit is a site that was missed.

4. Confirm the database audit inserts survive — both must still be present:

```bash
grep -n "request_json\|'request' => json_encode" application/modules/mobile_app/controllers/mis/EquifaxController.php application/modules/mobile_app/controllers/mis/TransUnion.php
```

Expect exactly two hits: `EquifaxController.php:461` and `TransUnion.php:414`.

5. Confirm the log calls still exist and were reduced, not deleted — the count of
   `writeLog(` calls must be unchanged from production:

```bash
git show onestackcbs:application/modules/mobile_app/controllers/mis/TransUnion.php | grep -c "writeLog(" && grep -c "writeLog(" application/modules/mobile_app/controllers/mis/TransUnion.php
```

Both numbers must match. A drop means a whole log call was removed by mistake.

6. Prove the redaction works on realistic input, without touching production. Run
   the log-shaping in isolation against a representative bureau request body:

"ABSENT  " : "LEAKED  "), $n, PHP_EOL; } echo "log payload: $s", PHP_EOL;'

Expect `ABSENT` on all three and a payload carrying only name, length and keys.

7. Production confirmation, read-only, AFTER this is deployed. Run on the
   production host and check that new entries no longer carry PAN-shaped or
   DOB-shaped values:

```
grep -aciE '[A-Z]{5}[0-9]{4}[A-Z]' application/logs/transunion-logs-$(date +%F).log
```

```
grep -aciE 'raw_input|request_structure|merged_request|Request Body' application/logs/transunion-logs-$(date +%F).log
```

Both must return `0` for a day whose traffic ran entirely on the new code. A
non-zero first count means a PAN is still reaching the log from a site not
covered here; a non-zero second count means old code is still deployed.

Note: existing log files still contain historical PII. This change stops new
writes; it does not clean up what is already on disk. Purging or rotating the
existing `transunion-logs-*.log` and `application/logs/transunion/*` files is a
separate operational action and should be raised as its own task.
