# PART 1 — In simple words

## What the system does today

There is an internal admin tool called the "Mobile API Debugger". Staff use it
to test the bank's own mobile-app APIs (things like sending an OTP, checking
an account balance, and so on) without needing a phone. On the page, staff
pick a partner bank from a dropdown. The page then quietly asks the server for
that bank's real web address (its "endpoint" — think of it as the bank's
front-door address on the internet, always something like
`hdfcbank.api.onestack.in`), fills that address into a hidden box on the form,
and when staff click Submit, the browser sends that address back to the
server, which uses it to make the actual test call and show the result.

## What is wrong with it

The server never checks that the address it receives back is actually one of
the bank addresses it just handed out. It just believes whatever address is in
that box. Since the box is filled in by JavaScript running in the visitor's
own browser, anyone who is logged in (this tool only requires being logged in
— it does not require an admin role) can bypass the dropdown entirely and
submit any web address they like directly to the server — including private
company servers, cloud infrastructure addresses, or a server they control
themselves.

The server will then reach out to whatever address was given, send it a
request that includes real request bodies (in some cases containing OTPs,
tokens, or attempted account numbers), and hand the response straight back to
whoever asked. On top of that, the server has been told not to bother checking
whether the address it's talking to has a valid, trustworthy security
certificate (`SSL_VERIFYHOST`/`SSL_VERIFYPEER` are both switched off), so it
will happily talk to a fake or self-signed server too.

In security terms this is called Server-Side Request Forgery (SSRF) — tricking
a trusted server into making requests to places it should never reach on your
behalf. It can be used to probe internal systems the outside world normally
cannot see, or to have the bank's own server relay live authentication traffic
to an attacker-controlled address.

## What we are going to change

The server will stop trusting the raw web address sent by the browser. Instead
it will check the address against the small, fixed list of address patterns
the bank's own APIs are always built from (`*.api.onestack.in` and
`*.api.rbank.in`, matching how the "give me this bank's address" lookup
already builds addresses on the same page). Anything that does not match that
pattern is rejected before any outgoing request is made. We will also turn the
certificate checks back on, since every genuine address in that pattern is a
real, certificate-bearing OneStack/RBank server.

## What could go wrong

If some legitimate partner bank uses a hostname that does not follow the
`*.api.onestack.in` / `*.api.rbank.in` pattern, this tool would start
rejecting it. From reading the code that builds the "give me this address"
lookup, every bank's address is always built from exactly that pattern, so
this should not happen — but it can only be confirmed for certain by someone
who knows every partner bank's actual URL. Turning certificate checking back
on could also surface a failure if any of these servers is currently running
with an expired or self-signed certificate; today that would be silently
hidden because checking is off.

| Word | What it means, simply |
|---|---|
| Endpoint | The web address (like a phone number, but for computers) that a request is sent to. |
| SSRF (Server-Side Request Forgery) | Tricking a server into fetching or sending data to an address of the attacker's choosing, instead of the address it was meant to talk to. |
| SSL/TLS certificate verification | The check a computer does to confirm the server it's talking to is really who it claims to be, and not an impostor. |
| Allow-list | A short list of the only things that are permitted; anything not on the list is refused. |

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/technology/MobileDebugger.php`:

- `buildMobileApiRequest()` at line 112-126 takes `$endpoint` directly from
  `$this->input->post('endpoint')` with no validation, and concatenates it
  into `$requestData['url']` for every one of the ~30 `switch` cases (e.g.
  line 130: `$requestData['url'] = $endpoint . '/api/v3/one-time-token';`).
- `callMobileApi()` at line 1580-1625 passes that URL straight to
  `curl_setopt_array()` as `CURLOPT_URL` (line 1589) and, critically, sets:
  ```php
  CURLOPT_SSL_VERIFYHOST => 0,
  CURLOPT_SSL_VERIFYPEER => 0,
  ```
  (lines 1596-1597) — so an attacker-supplied host with a self-signed or
  absent certificate is accepted without complaint.
- `triggerMobileApi()` (line 76-110) is gated only by the constructor's
  session check (`$this->session->userdata('identity') != null`, line 17) —
  it does **not** call `checkSubChildControllerAccess(...)` the way `index()`
  does at line 31. So any logged-in user, not just an admin with the
  `mobile_debugger` permission, can reach this endpoint.

Confirmed the legitimate address pattern by reading the code that populates
the hidden `endpoint` field client-side:
- `assets/custom/js/mobile_debugger.js:18-43` (`get_mobile_api_endpoint`) calls
  `admin/mobile_debugger-view/cbs/get-mobile-api-endpoint` server-side, and
  only writes the *returned* value into `input[name="endpoint"]` (line 26).
- That route (`application/config/routes.php:1290`) maps to
  `Debugger::getMobileApiEndpoint()`
  (`application/modules/mobile_app/controllers/Debugger.php:1389-1435`), which
  builds the address itself, from a DB-verified active company row, always as:
  ```php
  $mobileApiEndpoint = "https://" . $bankName . ".api.onestack.in"; // Live
  // or
  $mobileApiEndpoint = "https://" . $bankName . ".api.rbank.in";    // Sandbox
  ```
  (Debugger.php:1408-1414).
- The same two suffixes (`.api.onestack.in`, `.api.rbank.in`) are the only
  ones used for this class of partner-bank API host elsewhere in the codebase
  (`Home.php:41,49,51`; `BankManagement.php:18054`; `Hdfc_Common.php:101`).

So the legitimate value of `endpoint` is never a free-form URL — it is always
`https://<sanitized-bank-name>.api.onestack.in` or
`https://<sanitized-bank-name>.api.rbank.in`. `MobileDebugger.php` currently
has no equivalent check and will build a request to literally anything typed
or POSTed into that field.

**Out of scope, noted only:** the missing `checkSubChildControllerAccess`

flagging it here so it isn't lost.

## How it will be fixed

1. Add a private method `isAllowedMobileApiEndpoint(string $endpoint): bool`
   to `MobileDebugger.php` that:
   - Parses the URL with `parse_url()`.
   - Rejects if scheme is not exactly `https`.
   - Rejects if a `user`/`pass`/`port` component is present (blocks
     `https://good.api.onestack.in@evil.com` and similar tricks).
   - Rejects if `host` is empty or is an IP literal
     (`filter_var($host, FILTER_VALIDATE_IP)`).
   - Accepts only if `host` matches
     `/^[a-z0-9-]+\.api\.(onestack|rbank)\.in$/i`.
2. In `triggerMobileApi()` (line ~78), immediately after reading
   `$this->input->post('endpoint')`, validate it with that method before doing
   anything else. On failure, return the existing-style JSON error response
   (`success: false`, an `error-panel` html message) and stop — do not call
   `buildMobileApiRequest()`/`callMobileApi()`.
3. In `callMobileApi()` (lines 1596-1597), change:
   ```php
   CURLOPT_SSL_VERIFYHOST => 0,
   CURLOPT_SSL_VERIFYPEER => 0,
   ```
   to:
   ```php
   CURLOPT_SSL_VERIFYHOST => 2,
   CURLOPT_SSL_VERIFYPEER => true,
   ```

This closes the SSRF (the host is now always one of the two known suffixes)
and the SSL bypass, without touching the request-building logic for any of
the ~30 API cases, and without changing the front-end — the legitimate flow
already only ever produces URLs that pass the new check.
