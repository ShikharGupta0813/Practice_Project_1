# PART 1 — In simple words

## What the system does today

The system keeps diaries. Every time something notable happens — a payment
arrives, a bank file is imported, a QR code is rebuilt — it writes a line into a
text file so staff can look back later and see what happened. Those diary files
are grouped into folders by subject, the way you might keep separate folders for
bank statements, receipts and letters.

There is a catch. The folders themselves are not shipped with the software.
When the system is installed fresh onto a new server, only the top-level filing
cabinet exists — every subject folder inside it is missing. They only appear
once something has written to them.

## What is wrong with it

Most of the code opens a diary file by pointing straight at it and saying
"write here". If the folder is missing, that fails. On older versions of PHP
(the language this is written in) the failure was quiet — the diary line was
simply lost. On the newer version, the same failure stops the request dead with
an error.

That matters because these writes sit in the middle of real work. A crash there
does not just lose a diary line; it abandons the job that was running. On a
brand-new server the very first payment or import that reaches one of these
lines would stop, and it would keep stopping until somebody created the folder
by hand.

**Most of this is already fixed.** The work already committed on this branch
rewrote 180 files to go through a helper that creates the folder before writing.
This task is the sweep-up: 39 places the earlier pass missed, because they were
written in a slightly different style that the earlier search did not match.

Six of them write into a **subject folder** that can genuinely be missing — five
in the QR-code regeneration feature (the part that rebuilds a merchant's payment
QR), one in a scheduled job that checks GST numbers. These are the ones that can
actually crash today.

The other 33 write into the **top level** of the filing cabinet rather than a
subject folder. Those are safe right now, because this branch makes sure the
top-level folder always ships. But that safety rests entirely on one line in a
settings file. If anybody ever removes that line, all 33 break at once. So they
are being converted too, and that dependency goes away.

One of the 39 is a different problem. It opens a diary file, then never writes
anything to it and never closes it. It has never produced a single line of
output in its life. Each time the job runs it leaves a file handle open — the
equivalent of pulling open a filing-cabinet drawer, writing nothing, and walking
away leaving it open. Enough of those and the server runs out of drawers.

## What we are going to change

Thirty-eight of them get switched over to the same folder-creating helper the
rest of the code now uses. The diary files keep their exact names and their
exact contents — they just stop failing when a folder is absent. The one that
never wrote anything is deleted, along with the unused text it was building.

## What could go wrong

Seven of the changes are inside a file that is loaded on **every single request**
in the application. A mistake there would not affect one page, it would affect
all of them. The changes are small and mechanical, but they need a careful read
rather than a glance.

The real risk across all 38 is quieter: if a converted line ends up pointing at
a slightly different filename, the diary silently splits into two files and
nobody notices until someone goes looking for a record that seems to have
vanished. The check for this compares every log filename before and after the
change and requires them to be identical.

Deleting the last one means giving up on a diary entry somebody once intended to
write. Since it has never actually written anything, nothing that exists today
is lost — but if that logging is genuinely wanted, it should be added back
deliberately rather than left half-built.

|---|---|

| File handle | The open connection to a file. Every one opened should be closed |

| Fresh deploy | Installing the software onto a brand-new server, where nothing has run yet |

# PART 3 — The technical version

## Root cause

`.gitignore:31` on production is `/application/logs/**` with no exception, so
**no file under `application/logs/` is tracked at all** (`git ls-tree -r
origin/onestackcbs -- application/logs` returns 0 files). On a fresh deploy
neither the log subdirectories nor `application/logs/` itself exist.

Call sites that open a log file with a bare `fopen()` therefore get `FALSE`, and
the following `fwrite()` receives `FALSE` where a resource is required — a fatal
`TypeError` on PHP 8.

The branch already addresses this in two ways:

1. `.gitignore` was content-scoped and `application/logs/.htaccess` is now
   tracked (`git ls-files application/logs` → 1 file), so **`application/logs/`
   itself is guaranteed to exist** after this branch ships.
2. `application/helpers/common_helper.php:1805` adds `writeLogRaw()`, which
   `mkdir($logDir, 0755, true)` before writing, and `logFilePath()` for the few
   sites that genuinely need a handle. 180 files were converted.

The helper accepts either form of path:

```php
if (strpos($relativePath, 'application/logs') !== FALSE) {
    $filePath = $relativePath;
} else {
    $filePath = "./application/logs/" . ltrim($relativePath, '/');
}
```

**What the earlier pass missed.** The conversion matched the literal
`"./application/logs/` prefix. Five sites in `CommonFunctions.php` build their
path as `FCPATH . "application/logs/..."` instead, so they were skipped:

`application/libraries/common/CommonFunctions.php:2853`
```php
$txt1 = "";
$myfile = fopen(FCPATH . "application/logs/regenerateQr/regenerate-qr-log-" . date('Y-m-d') . ".php", "a");
$txt1 = "\nLog Date and Time: " . date('d-m-Y H:i:s') . "\n";
...
fwrite($myfile, $txt1);
fclose($myfile);
```

A sixth site was missed because the call is split across three lines:

`application/modules/mobile_app/controllers/Cron.php:14225`
```php
$myfile = fopen(
    "./application/logs/testing/temp-gst_auth_data-log-" . date('Y-m-d') . ".php",
    "a"
);
```

This one is **an orphan handle, not a log write**. Within
`process_authbridge_fetch_gst()` (`Cron.php:14165`) there is no `fwrite($myfile,
...)` and no `fclose($myfile)` anywhere — verified by grepping `txt1|myfile`
across the whole function body, which returns only the `fopen` and the `$txt1 .=`
accumulations at `:14230`, `:14231`, `:14232` and `:14258`. `$txt1` is built and
discarded. The handle leaks on every run.

## How it will be fixed

1. Convert the five `CommonFunctions.php` sites to `writeLogRaw()`, passing the
   `FCPATH . "application/logs/..."` string through unchanged — the helper's
   `strpos(..., 'application/logs')` branch handles it, so log filenames and
   contents are byte-identical to today. Drop the now-unused `$myfile`,
   `fwrite()` and `fclose()` lines.
2. Delete the orphan `fopen` at `Cron.php:14225` together with the dead `$txt1`
   accumulations at `:14224`, `:14230-14232` and `:14258`. No replacement — this
   code has never written to disk, so converting it would *start* producing a
   log file that has never existed, which is a behaviour change, not a fix.

## Plan

1. `git checkout sg_cl_log_dirs_on_fresh_deploy` (already the current branch;
   confirm working tree is clean). Do **not** cut a new branch.
2. Convert the 38 sites. For each one the shape is identical:
   - delete the `$<handle> = fopen(<path expr>, "a");` statement, single-line or
     split across lines;
   - leave the `$<text>` accumulation exactly as it is, so the log content is
     byte-identical;
   - replace the `fwrite($<handle>, $<text>);` / `fclose($<handle>);` pair with
     one `writeLogRaw($<text>, <path expr>);`, passing the path expression
     through **unchanged** so filenames do not move;
   - match the file's own indentation (tabs in `CommonFunctions.php`, spaces
     elsewhere).
   Match on the **exact handle variable**, and only accept a site where the
   `fwrite`/`fclose` pair uses that same variable. Work bottom-up within each
   file so earlier line numbers stay valid.
3. In `application/modules/mobile_app/controllers/Cron.php`, delete lines
   `14224` (`$txt1 = "";`), the `fopen(` call at `14225-14228`, the three
   `$txt1 .=` lines at `14230-14232`, and the `$txt1 .=` at `14258`. Leave every
   other statement in `process_authbridge_fetch_gst()` untouched. This one is
   deleted, not converted — see Root cause.
4. Leave `application/helpers/common_helper bkp 07_11_2022.php` untouched.
5. Run the verification gate and the checks under "How to test".
6. Commit on the same branch, message trailered
   `Asana: 1217811081134143` plus the standard `Co-Authored-By`.
7. Push. PR #13081 updates itself — **do not open a second dev PR**. Comment the

**Not verifiable locally.** Whether the log directories end up writable by the
PHP user on production depends on deploy ownership, and is already flagged as
the blocking item on PR #13081. This task does not change that position either
way. Before merge, run on production:
```bash
ls -ld /var/www/html/application/logs
stat -c '%U:%G %a' /var/www/html/application/logs
ps -o user= -C php-fpm | sort -u
```
If the owner of `application/logs` is not the PHP user and the mode is not
group-writable, `mkdir()` inside `writeLogRaw()` will fail and these writes stay
broken — the code fix is correct but insufficient, and the deploy needs to
create the directory as the PHP user.
