# PART 1 — In simple words

## What the system does today

The admin console has a "bank onboarding form". It holds a bank's details: its
name, its settlement bank account, the contact people, and the keys OneStack
uses to talk to the bank's core banking system.

The form has a GST number box. When someone types a GST number and moves on,
the page asks the server for the bank that owns that GST number. The server
sends back everything it has saved about that bank, and the page fills in the
rest of the form automatically.

The server only checks that the person is logged in to the console. It does not
check whether that GST number belongs to *their own* bank.

## What is wrong with it

GST numbers are public; anyone can look one up. So a bank employee who is
logged in can type another bank's GST number and see that bank's secret API
keys, its settlement account number and IFSC, and its staff names, emails and
mobile numbers.

It is like a filing cabinet where you only need to read the label on someone
else's drawer to open it. Nothing tells us this has been misused, but anyone
with a bank-staff login could do it today.

## What we are going to change

Before answering, the server will check who is asking:
- **OneStack staff** (no bank attached to their login) can still look up any
  bank, exactly as today.
- **Bank staff** get an answer only when the GST number is their own bank's.
  For any other GST number they get the same "not found" reply as for a GST
  number that does not exist.

Nothing else changes. When a bank user types their own GST number, the form
still fills in all the fields, keys included. The same fix goes into a second,
identical copy of this code.

## What could go wrong

- If a bank's GST number is saved slightly differently in two places (extra
  spaces, lower case), that bank's own staff would stop getting the autofill.
  The check ignores spaces and upper/lower case to avoid this. A genuinely
  different number would still block it; they could still type the details by
  hand.
- If a bank has no GST number saved in its company record, its staff lose the
  autofill. That is the safe way round.
- OneStack staff are not affected at all.

# PART 3 — The technical version

## Root cause

The task's line number has moved: the method starts at
`Bank_register_controller.php:909`, not `:933`. The lookup is keyed on the
posted GST number alone:

```php
// application/modules/mobile_app/controllers/Bank_register_controller.php:913-919
$company_gstn = $this->input->post('company_gstn');
$select = '...,ac_number,ac_type,ifsc_code,...,cbs_url,cbs_bank_identifier,cbs_apikey,cbs_publickey,...';
$condition = array(
  'gst_number' => $company_gstn,
);
$partnerInfo = $this->encrypt_model->select(DbTable::BANK, $select, $condition);
```

`DbTable::BANK` = `tbl_bank_onboarding` (`DbTable.php:80`). The full row is
echoed as JSON (`:931-977`).

Who can reach it:
- The class `extends Admin_Controller` (`:7`), so a logged-in admin is required.
  The task title's "anyone" is overstated.
- The route is `$route['fetch-bank-detail']` (`routes.php:79`). It is not under
  `admin/`, so `Auth_Controller` skips `PermissionService`
  (`MY_Controller.php:345-367`, the `else` branch).
- No check links the GST number to the session's bank. Bank users carry
  `company_id` in their session, and OneStack users do not
  (`index()` at `:27-36` already scopes by it).

Same code in an identical copy:
`application/modules/mobile_app/controllers/bank_onboarding_form/Bank_register_controller.php:475`,
with the post at `:481`. It reads via `$this->CommonModel->select(...)`
rather than `encrypt_model`, and no route points to it.

A bank row links to its company by GST: `tbl_bank_onboarding.gst_number =
tbl_company_master.company_gstn` (`dashboard_helper.php:341-348`).

The only caller is `views/public/form2.php:757-816` (and the legacy
`application/views/public/form2.php:748`). The blur handler on `#company_gstn`
fills the form, including `#cbs_url`, `#cbs_apikey` and `#cbs_publickey`, so
the response shape must stay the same.

## How it will be fixed

Right after `$company_gstn` is read, add an inline tenant check. Per the tenant
rule, no helper is used:

```php
$sessionCompanyID = $this->session->userdata('company_id');
if (!empty($sessionCompanyID)) {
	$ownCompany = $this->CommonModel->select(DbTable::COMPANY_MASTER, 'company_gstn', array('id' => $sessionCompanyID));
	if (empty($ownCompany) || empty($ownCompany[0]['company_gstn']) || strtoupper(trim($ownCompany[0]['company_gstn'])) !== strtoupper(trim($company_gstn))) {
		$formData['msg'] = 'Invalid user id';
		echo json_encode($formData);exit;
	}
}
```

- On a mismatch it returns exactly the existing not-found response (`:980`,
  `:985`). A bank user cannot tell "exists but not yours" from "does not exist".
- OneStack users (no `company_id`) keep the current behaviour.
- `CommonModel` is already loaded in both constructors (`:16` and the copy's
  `:16`). `CommonModel->select(table, fields, condition)` is the same call
  shape used on `tbl_company_master` in `cbs/Agreements.php:21`.
- `company_gstn` is read unencrypted everywhere else (`dashboard_helper.php:341`,
  `Agreements.php:21`), so plain `CommonModel` is correct.
- Select list, response fields and JS are unchanged. Per the user's decision,
  the keys stay in the response.
