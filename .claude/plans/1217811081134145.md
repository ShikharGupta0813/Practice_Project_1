# PART 1 — In simple words

## What the system does today

A soundbox is the small speaker that sits next to the till in a shop. When a
customer pays, it says out loud "payment received, two hundred rupees". The
shopkeeper does not have to look at a phone. They hear it, and they trust it.

While this feature was being built, a developer made a test page: a form where
you type in a shop and an amount, press a button, and the speaker announces a
payment. That way you could test the speaker without making a real payment
every time. A sensible thing to have on a workbench.

That test page was left on the live website, with no login on it. Anyone who
knew the web address could make any shop's speaker announce a payment that
never happened. That is what this task was written about.

**That page is already gone.** Somebody on the team deleted it a while back and
it is no longer in the live code. So the danger the task describes is closed.

What is still there is the file that sat behind it. The page is gone, but the
file was never deleted, and it has seven other web addresses still working on
it. None of them ask for a login either. And they are not about soundboxes at
all — over time somebody used this leftover file as a convenient place to park
other bits of work.

Four of those seven do a one-time cleanup job on the database. The team decided
that customers' PAN and Aadhaar numbers should be scrambled, so that anyone who
got hold of a copy of the database would see gibberish instead of real identity
numbers. New customers are scrambled automatically, but the hundreds of
thousands of records already stored in readable form had to be converted one
batch at a time. Somebody wired that conversion job to a web address so they
could refresh a page to convert the next hundred records. Quick, and it works.

The other three are throwaway developer checks: scramble a test word twice and
see whether the results differ, unscramble one fixed sample and see whether it
comes back right, and look up one specific real customer to check that lookups
still work once the numbers are scrambled.

## What is wrong with it

Nothing here is broken. That is what makes it easy to miss. The code does what
it was written to do.

The problem is where it lives. A job that rewrites customer identity records
should only be runnable by somebody with access to the server. Instead it is a
web address on the open internet with no login in front of it.

And while it converts records, it prints them to the page — the real PAN, the
real Aadhaar, before and after. The developer added that so they could watch the
job and check it was doing the right thing. On their own machine that is fine.
On a live public address it means that loading the page hands those identity
numbers to whoever loaded it, and converts another batch of records as a side
effect.

Concretely, for a real person: a customer of one of these banks has their PAN
and Aadhaar number sitting behind a web address that needs no password. One of
the seven has a real customer's PAN typed directly into the file, so that
person's whole record is printed to anyone who opens it. Another was abandoned
half-finished — it converts nothing at all, it only reads identity numbers and
prints them. That one has no purpose left; it is only a leak.

Nobody uses any of this. No part of the product links to it, and no other code
calls it. It is leftover, and it was simply never cleaned up.

## What we are going to change

Delete the file, and delete the nine lines in the routing list that point at it.
Nothing else in the system refers to it, so nothing else has to change. After
this, those seven web addresses stop existing.

## What could go wrong

The main risk is the cleanup job. If it has not finished — if there are still
customer records waiting to be converted — then deleting this takes away the
tool somebody was using to finish it. It would not break anything that is
running, but the remaining records would stay unconverted until the job is
rebuilt somewhere sensible.

There is a read-only check for this in the test section below. It should be run
before the change is merged. The user has decided to proceed with deletion.

Beyond that the risk is low. Deleting code that nothing calls cannot change how
anything else behaves. The one thing to be careful about is deleting only the
web addresses and not the file itself, which would look like a fix and change
nothing at all — the reason for that is explained in the technical part.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Controller | The piece of code that answers one group of web addresses. Address comes in, controller runs, page goes out. |
| Route | A line in a list that maps a short web address to the controller code that answers it. |
| Commented out | Code left in the file but switched off. Usually a sign of unfinished or abandoned work. |
| PAN / Aadhaar | Indian identity numbers. PAN is for tax, Aadhaar is the national ID. Both are sensitive personal data. |

| HMVC | The way this project organises code into modules. It matters here because it lets a web address reach a controller file even when no route is written for it. |

# PART 3 — The technical version

## Root cause

**The view named in the task title no longer exists on production.**

```
git cat-file -e onestackcbs:application/modules/mobile_app/views/frontend/test_soundbox.php
fatal: path '...' does not exist in 'onestackcbs'
```

Deleted by commit `ab5166657d` ("B1 — Delete test_soundbox.php and
test_mqtt_public.php"), which `git branch --contains` confirms is on
`onestackcbs`. The literal deliverable in the title is already done.

What remains is `application/modules/mobile_app/controllers/Testing_soundbox.php`
(274 lines on `onestackcbs`; identical in the working tree — `git diff onestackcbs`
on that path is empty).

**It has no authentication.** `Testing_soundbox.php:3`:

```php
class Testing_soundbox extends MY_Controller {
```

`MY_Controller` (`application/core/MY_Controller.php:5`) is the unauthenticated
base. The class that enforces login is `Auth_Controller`
(`MY_Controller.php:318`), whose constructor calls `ion_auth->logged_in()` at
line 323 and `permissionservice->checkPermission` at line 368. This controller
extends neither, and the file contains no session check, no `checkPermission`
call and no login guard across its 274 lines.

**Seven public methods, all reachable.** `application/config/routes.php:1724-1731`
declares seven routes; `routes.php:1721-1722` holds two more, commented out.

| Method | Line | Behaviour |
|---|---|---|
| `update_customer_details` | 34 | 100 rows of `tbl_customers` (`encrypt_status = 0`), encrypts PAN + Aadhaar via `encrypt_model->update`, **writes**, `print_r`s each record before and after (lines 77-81) |
| `update_bank_details` | 87 | Same for 20 rows of `tbl_company_master` (`bank_pan`). **Writes**, prints (119-123) |
| `update_bank_contact_details` | 129 | Same for `tbl_cbs_bank_contact_detail` (PAN + Aadhaar of named bank staff), limit 2. **Writes**, prints (171-175) |
| `update_bank_onboarding_details` | 181 | Reads `tbl_bank_onboarding` (bank PAN, person PAN, Aadhaar), limit 2. Write loop commented out at 209-230; `print_r($result)` at 232 is live. **Read and print only** |
| `encrypt_data` | 235 | Encrypts the literal `'testing'` twice, echoes both. No customer data |
| `decrypt_data` | 246 | Decrypts a **hardcoded** ciphertext (line 250) via `decrypt_api_request()`, prints it. Input is not caller-supplied, so this is not a decryption oracle |
| `testing_select_query` | 266 | `select('*')` on `DbTable::CUSTOMERS` for hardcoded PAN `BWVPD3180Q` / id `252091`, decrypt flag TRUE, prints the full row |

The four `update_*` methods are a PAN/Aadhaar encryption migration. The writes
go through `EncryptedCommonModel::update`
(`application/models/common/EncryptedCommonModel.php:197-221`), which masks,
encrypts per `application/config/column_rules.php:5`, and sets
`encrypt_status = 1`.

Worth flagging for whoever reviews: `column_rules.php` has rules for `pan_no`
and `aadhar_no` but **none** for `plain_text_pan_no` / `plain_text_aadhar_no`,
so those columns are written unencrypted by design. That is a pre-existing
decision, out of scope here, and unchanged by this task.

**Deleting only the routes would close nothing.** `MY_Router`
(`application/core/MY_Router.php:6`) extends `MX_Router`, whose `locate()`
(`application/third_party/MX/Router.php:110`) resolves a URL by testing for
`<module>/controllers/<Controller>.php` on disk, independently of the route
table. With the routes removed but the file present, all seven methods stay
reachable at `/mobile_app/testing_soundbox/<method>`. The file itself must go.

**Line numbers in the task title:** the title names no line numbers, only the
view path, which is stale. Every line number cited above was read from
`onestackcbs` and is current.

## How it will be fixed

Delete `application/modules/mobile_app/controllers/Testing_soundbox.php`
outright, and remove the `testing_soundbox` block from
`application/config/routes.php` (lines 1721-1732, covering the seven live
routes, the two commented ones, and the blank lines inside the block).

No replacement, no deprecation shim, no auth wrapper. Nothing in the repository
calls this code, so there is nothing to migrate.

**Explicitly rejected: switching the base class to `Auth_Controller`.** It would
add the `logged_in() OR is_admin()` gate at `MY_Controller.php:323`, which does
run for every request — but the permission check below it does not. At
`MY_Controller.php:341-371` the slug is only derived when
`$this->uri->segment(1) === 'admin'`; otherwise the `else` branch sets
`url_slug` and `url_action` to `''`, writes a `"Skipping URL"` log line, and
calls `checkPermission` with those empty values anyway. Neither
`testing_soundbox/...` nor `mobile_app/testing_soundbox/...` starts with
`admin`, so both land in that branch and pass. The result would be that any
logged-in admin could still print 100 customers' PAN and Aadhaar and trigger
writes to customer records. That is the known fail-open issue, and this
controller is a live instance of it. A fix that appears to close the hole while
leaving it open is worse than leaving it visible.
