# PART 1 — In simple words

## What the system does today

Customer accounts can be loaded into the system in bulk from a spreadsheet. Each
upload becomes a job that sits in a queue waiting to be processed. Staff can look
at the queue and remove a job they no longer want — a duplicate upload, or one with
a mistake in it.

When staff click remove, the screen sends the system the identity number of the job
to delete. The system builds a database instruction by gluing that number onto the
end of a sentence, and sends the whole sentence to the database.

## What is wrong with it

The system glues the number on without checking that it is a number.

A database instruction is just a sentence, and the database does whatever the
sentence says. If instead of a number someone sends a fragment of database
language, that fragment becomes part of the sentence and the database obeys it too.

The everyday comparison: it is like a form letter where the system fills in a blank
with whatever the sender typed, then treats the whole letter as an order to be
carried out. Type your name in the blank and it works normally. Type your name
followed by "and empty the safe" and the letter now says that too.

Because the sentence here is a delete instruction, a crafted value could delete far
more than the one job it was meant to. Depending on the database's settings it can
also be used to read data it should not, by attaching a question onto the end.

The screen is behind a login, so this needs a signed-in staff account — but the
whole point of the permission system is that a junior member of staff should not be
able to reach beyond what they are allowed to touch, and this lets them.

## What we are going to change

Stop gluing the value into the sentence. Instead, hand the sentence and the value to
the database separately, so the database treats the value as a plain number and
never as an instruction. This is the standard way to do it and the rest of the
system already does it in most places.

## What could go wrong

Very little. The change does not alter what the instruction does when it is given a
genuine number — the same job is deleted. The only visible difference would be if
something is currently relying on passing a non-numeric value, which would be a bug
in its own right.

The one thing to be careful of is that this same faulty line exists in **four**
places, and fixing one leaves the other three open. They must all go together.

| SQL | The language used to ask a database to do something. |

# PART 3 — The technical version

## Root cause

`application/modules/cbs/controllers/CbsCustomerAccountImport.php:219`
— **the task says :220; the actual line is :219.**

```php
$is_in_queue = $this->CbsCustomerAccountImport_model->check_CustomerAccountImportQueueProcess($_POST['id']);
if (empty($is_in_queue)) {

    $sql = "Delete from tbl_cbs_cron_import_data where queue_id = " . $_POST['id'];
    $qry_result = $this->db->query($sql);
```

`$_POST['id']` is concatenated into a raw `DELETE` with no cast, no escaping and
no binding. Numeric context, so no quotes to break out of — a value of
`1 OR 1=1` deletes the whole table.

Note the surrounding code reads `$_POST` directly rather than through
`$this->input->post()`, which is the CI3 convention used elsewhere in this
codebase. Worth correcting in the same edit for consistency, but the binding is
the security fix.

Two lines further down the same `$_POST['id']` is used safely via the query
builder:

```php
$condition = array('id' => $_POST['id']);
$affected_row = $this->CbsCustomerAccountImport_model->delete_CustomerAccountImport($condition);
```

— which is exactly the pattern the raw query should have used.

## How it will be fixed

Bind the parameter:

```php
$id = (int) $this->input->post('id');
$sql = "Delete from tbl_cbs_cron_import_data where queue_id = ?";
$qry_result = $this->db->query($sql, [$id]);
```

`(int)` alone would be sufficient for this numeric column, but binding is the
convention to establish across all four copies, and it stays correct if the column
type ever changes.
