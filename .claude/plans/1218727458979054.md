# PART 1 - In simple words

## What the system does today
Both consoles (production at admin.onestack.in, sandbox at rbank.in) have a button in the sidebar: "Log in to Sandbox" or "Log in to Production". Pressing it opens the other console in a new tab and sends along the operator's email address.

On the production side this does little: the other console just shows its normal login page (or the dashboard if you are already logged in there).

On the sandbox side (rbank.in) it is very different. The address the button uses, `rbank.in/single-login`, takes the email and logs that person in with NO password. This was confirmed by testing it: rbank.in does not ask for a password.

## What is wrong with it
Think of a door that opens for anyone who says a staff member's name. Anyone who knows an operator's email address can send it to `rbank.in/single-login` and be logged in as that operator, including a main super-admin. They do not need to press the button at all; they can send the request directly. Because the sandbox is linked to production, a break-in on the sandbox could become a way towards production.

## What we are going to change
Switch off the password-free door. The `single-login` address and the code behind it are commented out (not deleted, so it is easy to bring back). The live-mode button is pointed at the normal rbank.in login page, the same way the production button already works. Operators log in on each console with their own password.

## What could go wrong
- Anyone who used the one-click "Log in to Sandbox" shortcut now has to type their password on rbank.in. That is intended.
- If some mobile app or outside system secretly calls `rbank.in/single-login`, it will stop working. Nothing in this code base does (see Evidence), but the mobile app builds could not be checked.
- The fix must reach rbank.in (the sandbox). Fixing only production does nothing for the real hole.

# PART 3 - The technical version

## Root cause
Written against `onestackcbs`; all line numbers verified there.

`application/config/routes.php:57`
```php
$route['single-login'] = 'auth/singleLogin';
```
`application/controllers/Auth.php:32-37` - public, no auth, reads email only:
```php
public function singleLogin(){
    $user_email = $_POST['user_email'];
    ...
    $this->db->where('us.email', $user_email);
```
`Auth.php:81` calls `$this->ion_auth->singleLogin($user_email, false)`; `Ion_auth_model.php:1014-1100` looks the user up by email, checks only `active` and role status, then `set_session($user)` + `update_last_login()`. No password, token, signature, expiry or origin check. A matching email yields a full session; redirect to `admin`.

`application/views/admin/_templates/main_sidebar.php:33-49` - live mode posts a hidden `user_email` to `https://rbank.in/single-login`; sandbox mode posts to `https://admin.onestack.in` (root = `Auth::index`, which ignores POST, so that direction only opens the login page).

Confirmed live: user ran a POST to rbank.in/single-login with their own email and was logged in without a password.

## How it will be fixed
Comment out (do not delete) the route and `Auth::singleLogin()`. Change the live-mode button URL from `https://rbank.in/single-login` to `https://rbank.in`, which is exactly how the production button already behaves. Keep the form and hidden field as they are, to match the existing production button.

Not changed: `Ion_auth_model::singleLogin()` (`Ion_auth_model.php:1014`) - `Auth::completeLogin()` at `Auth.php:1355` uses it for the normal login flow. Not changed: `main_sidebar - onestackcbs.php` - dead file, not loaded anywhere (its `m action=` markup is broken); left alone as agreed to keep the change small.

## How to test
- `php -l application/controllers/Auth.php` and `php -l application/config/routes.php` -> no syntax errors.
- `grep -n "single-login" application/config/routes.php application/views/admin/_templates/main_sidebar.php` -> only commented-out or no hits; `grep -n "function singleLogin" application/controllers/Auth.php` -> only inside the comment.
- Normal login still works: open `/auth/login`, log in with a test account; `Auth::completeLogin` must still reach `admin`.
- After deploying to rbank.in, run the read-only check from your own machine with your own email and confirm there is no login:
  `curl -s -i -X POST https://rbank.in/single-login -d "user_email=YOUR_OWN_EMAIL" | head -20`
  Expect a 404 (route gone), and NO `Location: .../admin` plus a new session cookie.
- On production, press "Log in to Sandbox": rbank.in opens on the normal login page.
- Optional production read-only check: grep the web server access logs for `POST /single-login` to see who used it and whether anything unexpected called it (anything other than operators' browsers means check before deploying).
