# PART 1 — In simple words

## What the system does today

The bank has well over a hundred report pages for the Reserve Bank of India, plus
some reconciliation and board-meeting pages. At the top of each page is the same
line: "insert whatever file this label points at".

When a report is opened from the main RBI report screen, the code sets that label
to one fixed file. That file adds a few hidden fields (which bank, which report) that
the page uses when it is saved.

When some of the same pages are opened from *other* screens (reconciliation reports,
board resolutions, the balance sheet and ledger pages), nobody sets the label. The
page tries to insert "nothing", fails quietly, and carries on without those hidden
fields. Some of those pages are written to expect exactly that.

## What is wrong with it

Nothing can be attacked today — the label is always either the one fixed file or
empty. The problem is that "insert whatever the label says" is only as safe as the
label. If someone later wires the label to something a user can type, 137 pages
would all start running whatever file an attacker names. Nothing in the code makes
that danger obvious, and scanning tools cannot see what the label will hold.

A comparison: every door in the building opens with "whatever key is in this
envelope". Today the envelope always holds the right key, but anyone could swap it.

## What we are going to change

Each page will stop reading a file name from the label. Instead it names the one
fixed file directly, and only inserts it when the code has switched the label on —
exactly as today. Pages that insert the file today still do; pages that don't still
don't. The label becomes an on/off switch, not a file name.

The code that automatically generates new report pages is **not** changed in this
round (it is being fixed separately). New report pages it creates will still use the
old line until that is done.

## What could go wrong

- **Volume.** 136 edits across 135 files. A scripted replacement that goes wrong
  could break one report page. The check is that every file changes by exactly one
  line.
- **Some file names contain spaces and symbols** (`&`, brackets). A careless script
  could skip them or break on them.
- **New report pages will still come out with the old line** until the generator is
  fixed in a follow-up. Existing pages are unaffected by that.

| Word | What it means, simply |
|---|---|
| include / `include_once` | A PHP instruction: "paste in and run this other file here". |
| View | A PHP file that draws a web page. |
| Controller | The code that prepares data and picks which view to draw. |
| `APPPATH` | A built-in constant holding the full path of the `application/` folder. |
| Local file inclusion (LFI) | An attack where someone makes the server run a file of their choosing. |

# PART 3 — The technical version

## Root cause

**One live assignment, a hardcoded literal** —
`application/modules/mobile_app/controllers/mis/ReportMaster.php:1242` (inside
`getRBIReportUrl()`):

```php
$this->data['rbiReportIncludePath'] = 'application/modules/cbs/views/includes/rbi-report-update-ids.php';

$this->template->admin_render('cbs/reports/rbi-report/'. $url, $this->data, true);
```

`:1139` is the same line, commented out. No other assignment exists.

**137 include sites**, in 135 view files plus the generator template:

```php
// e.g. application/modules/cbs/views/board-resolution-mom.php:10
<?php include_once($rbiReportIncludePath);  ?>
```

**The generator writes the pattern into new views** —
`application/modules/mobile_app/controllers/mis/RbiReportAutomationController.php:320-336`
`generateHeader()` returns a template string containing
`include_once ($rbiReportIncludePath);`, which `:805` `file_put_contents()`s into a
new view. Any fix that skips this line regresses on the next generated report.

**Views that are rendered WITHOUT the variable today** (the reason the 2026-09-07
plan was wrong — it would have injected the hidden inputs into these pages):

| View(s) | Rendered by | Sets the variable? |
|---|---|---|
| `cbs/views/reports/reconciliation/all-reports/*` (14 files) | `mobile_app/controllers/mis/ReportController.php:1659` | no |
| `cbs/views/board-resolution-mom.php` | `cbs/controllers/BoardResolution.php:60` | no |
| `cbs/views/reports/rbi-report/Others/*` (9 files) | `cbs/controllers/TransactionManagement.php:1726, 1764, 1793, 2024, 2081, 2340, 2701` | no |

On those renders `include_once(null)` emits a warning, hidden by
`error_reporting(E_ERROR)` (known-patterns), and includes nothing. At least one
page depends on that: `reconciliation/all-reports/debit-reversal-confirmation-report.php:204`
— *"Only validate bank_id and report_id if the elements exist"*, and `:227` only
adds `bank_id` to its AJAX payload if the element exists. Injecting the block
unconditionally would add `#bank_id` / `#report_id` and change that request.

**Included file**: `application/modules/cbs/views/includes/rbi-report-update-ids.php`
— emits five hidden inputs from `$getReportData`, `$bank_id`, `$bank_category_id`,
`$report_type`, `$report_id`.

**Task line numbers:** the task gives a count (135), not lines. Verified count is 137
sites.

## Known gap (out of scope by user decision)

`RbiReportAutomationController.php:331` keeps emitting `include_once ($rbiReportIncludePath);`
into generated views. Any view generated after this change reintroduces one unguarded
site. Follow-up: apply the same one-line change to that template string once task 7
(`1217811081134068`, dev PR #13371, same file) has landed.

## How it will be fixed

Keep the controller assignment at `ReportMaster.php:1242` unchanged. Its value is now
used only as an on/off flag, which is exactly what it is today (set = include,
unset = nothing).

Replace every site with a guarded include of a fixed path:

```php
if (!empty($rbiReportIncludePath)) { include_once(APPPATH . 'modules/cbs/views/includes/rbi-report-update-ids.php'); }
```

- Behaviour is identical on every render path: set → same file included; unset →
  nothing included (and the hidden warning goes away).
- The file path no longer comes from a variable, so the path cannot be swapped even
  if the assignment is ever changed.
- `APPPATH . 'modules/...'` resolves to the same file as today's CWD-relative
  `'application/modules/...'` (`index.php` chdirs to FCPATH; known-patterns
  "Relative log paths").

(Deferred) In the generator (`RbiReportAutomationController.php:331`) the replacement sits inside
a single-quoted PHP string, so use double quotes for the inner literal:

```php
                if (!empty($rbiReportIncludePath)) { include_once(APPPATH . "modules/cbs/views/includes/rbi-report-update-ids.php"); }
```

Not doing: `realpath()` whitelisting (the path is now a constant, so there is nothing
to whitelist); `$this->load->view()` (changes the include mechanism for no gain);
touching the commented line at `:1139`.
