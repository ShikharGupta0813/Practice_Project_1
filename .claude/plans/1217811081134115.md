# PART 1 — In simple words

## What the system does today
The console home page shows charts: how many customers registered, how many
made a transaction, how many logged in to the app, transaction counts, and so
on. When the page asks the server for a chart, it also sends "which bank" to
show, taken from a dropdown on the page.

There are two kinds of console login that matter here:
- **Bank users**: their login is tied to one bank.
- **OneStack users** (OneStack staff and the main superadmin): their login is
  tied to no bank, so they can look at any bank.

For 11 of the 14 charts, the server always applies a bank user's own bank as
well as whatever the dropdown says. Think of a filing clerk who only ever opens
your own drawer: you can ask for "just this folder", but you can never get into
someone else's drawer.

## What is wrong with it
Three charts skip that rule and trust the dropdown alone:
- new registered customers
- transacting customers
- customers who logged in to the app

So a member of staff at Bank A can change the request (easy to do from the
browser) and see Bank B's customer numbers. If they send an empty bank, they
see totals across every bank on the platform.

What leaks is only **counts** (for example "412 new customers this month"), not
names or account details. But it is still one bank seeing another bank's
business figures, which banks would not accept.

## What we are going to change
One simple rule for these three charts:
- **Bank user** (their login has a bank): they only ever see their own bank,
  whatever the dropdown says.
- **OneStack user** (their login has no bank): no change. They can see any bank
  and pick one from the dropdown.

Partners are deliberately left out of this change. Partner filtering on these
charts stays exactly as it is today.

## What could go wrong
- **Two bank-group logins have no bank set.** The code cannot tell them apart
  from OneStack users, so they will still see every bank, as they already do on
  the other eleven charts. That is a data problem with those two logins, not
  something this change fixes.
- **A mistake in the edit could zero out a chart for everyone.** The test steps
  below compare the numbers before and after, for a OneStack user and a bank
  user.

# PART 3 — The technical version

## Root cause
The task title says 14 endpoints. Reading the code, **3 are affected**. The other
11 already AND the session filter with the POST filter, so the POST values can
only narrow the result.

The existing pattern in the same file (`DashboardChartsController.php:532-551`,
`getBarChartTransactionCount`):

```php
$companyID = $this->session->userdata('company_id');
...
if(!empty($companyID)){ $this->db->where('ord.company_id', $companyID); }
...
if(!empty($bank)){      $this->db->where('ord.company_id', $bank); }
```

The same shape is at `:563-584`, `:933-955`, `:970-991` and `:1310-1328`.

The three helpers that apply **only** the POST values:

- `getRegisterCustomerCount` (`:1075-1090`). Called from
  `drawNewRegisterCustCountChart` (`:1010-1012`, `:1050-1052`) with
  `$bank = $_POST['bank']`:
  ```php
  if(!empty($companyID)){
      $this->db->where('comp.id', $companyID);
  }
  ```
- `getTransactingRegCustCount` (`:1188-1229`). Two queries (orders, then UPI),
  filtered by `ord.company_id` / `upi.company_id` from the argument only.
  Called from `drawTxnCustCountChart` (`:1092-1094`, `:1163-1165`).
- `getAppLoginCustomerCount` (`:1639-1657`). Filtered by `cust.company_id` from
  the argument only. Called from `drawAppLoginCustCountChart` (`:1575-1577`,
  `:1613-1615`).

Here the `$companyID` parameter is the POST value, not the session. There is no
session read anywhere in these helpers.

Routes: `routes.php:1804`, `:1805`, `:1810`. The JS caller is
`assets/custom/js/charts/google-charts.js:522`, `:661`, `:2870`. It POSTs
`{partner, bank}`.

## How it will be fixed
Rule: if the session has a `company_id` (bank user), force the query to that
bank. If it has none (OneStack or main superadmin), leave the query as it is
today.

In each of the three helpers, read `company_id` from the session and add it as
a `where` clause **in addition to** the existing POST filters. This is the same
`if(!empty(...))` session filter the neighbouring helpers use. Only the bank
part of that pattern is copied: **no session `partner_id` filter is added**
(Shikhar, 2026-09-24: scope is bank user vs OneStack user only). Each session
filter uses the same column as the POST bank filter already in that function.

Signatures do not change, callers do not change, and the JS does not change.
