# PART 1 — In simple words

## What the system does today
Every bank has two lists of people:

- **User List** (User Management) is the list of people who can log in.
- **Bank Staff** (a section on the Bank Details page) is the bank's staff directory.

They are kept in two separate places. Think of an office with a **login register**
and a separate **staff directory**. The Bank Staff screen shows only the directory.

## What the owner wants (agreed 2026-09-30)
1. Add someone in the **User List**: they must also appear in **Bank Staff**.
2. Add someone in **Bank Staff** *with* a Role Group and Role Name: they must also
   appear in the **User List**. Without a role they stay in Bank Staff only.
3. Edit an existing **Bank Staff** person and give them a Role Group and Role Name
   later: they must then appear in the **User List**.

Deletes and existing records are out of scope.

## What is wrong with it
Only rule 1 is broken. Rules 2 and 3 already work.

**Rule 1:** adding from the User List does write a Bank Staff entry, but leaves it
switched to "inactive". The Bank Staff screen only shows active entries, so the person
never appears there. This is what was reported: *"users from user list are not
reflecting under this bank staff."*

**Rules 2 and 3:** the Bank Staff save screen already creates the login whenever a Role
Group and Role Name are filled in, whether the person is new or is being edited.

## What we are going to change
When a user is added from the User List, their Bank Staff entry will be saved as active.
That's a one-line change.

## What could go wrong
Very little. It's one value on one insert, and every other screen that adds Bank Staff
already sets it the same way.

One existing limitation stays as it is (not part of this task): if someone is given a
role in Bank Staff but a login with the same email already exists and has a *different
mobile number*, the login can't be created and the screen says "Something went wrong".

# PART 3 — The technical version

## Root cause
**Rule 1: broken.** `application/modules/mobile_app/controllers/Users.php:1002-1016`
(`addUsers()`, route `admin/users_list-add`, `routes.php:1714`):
```php
if($this->input->post('role_grp_id') != ONESTACK_SUPERADMIN){
    $additional_data = array(
        ...
        'flag' => 'bank',
        'created_on' => date('Y-m-d H:i:s'),
        'created_by' => $UserId
    );
    $this->CommonModel->create(DbTable::COMPANY_CONTACT, $additional_data);
```
There's no `status` key. Production DDL (supplied by the owner): `status enum('0','1')
NOT NULL` with no default. In non-strict mode MySQL stores `'0'`. In strict mode the
insert fails, and the return value is not checked. Either way the row is invisible,
because the Bank Staff list filters on `cc.status = '1'`
(`cbs/models/pagination/CommonContact_model.php:45`, value set in
`BankManagement::getAllContactUserList`). Other contact inserts set it, for example
`BankManagement.php:4447` `'status' => '1',` and `CbsCron.php:903`.

**Rules 2 and 3: already implemented.** `BankManagement::addUpdateCompanyContact`
(route `admin/bank-list-add/cbs/add-update-company-contact`, `cbs-routes.php:72`):
- `:4393` add branch / `:4480` edit branch both fall through to `:4571`
  "New user creation", which sits **outside** the add/edit `if`.
- `:4574` `if (!empty($roleGroup) && !empty($subRole))` → look up `tbl_users` by
  `email` + `phone` → if none, `ion_auth->register(...)` at `:4641` with
  `company_id`, `role_grp_id`, `sub_role_id`, branch/center/atm and the flags. If a
  user exists and is active, its role is updated at `:4698`.
- `:4707` with no role: "Company contact saved, but user not created" (rule 2 without a
  role, as intended).
- Edit form: `bank-contact-kyc.php:1321-1322` loads the role fields blank when no active
  user exists, so a role can be added later, which triggers the `:4574` path.

Known limitation, unchanged: the `:4575` lookup matches `email` **and** `phone`, while
`tbl_users.email` must be unique. A login with the same email but a different phone
makes `register()` fail at `:4654` ("Something went wrong") after the contact is saved.

## How it will be fixed
Add `'status' => '1',` to the `COMPANY_CONTACT` array in `Users::addUsers()`, after
`'flag' => 'bank',`.

**Added at execution (2026-09-30), same insert:** the contact's `company_id` fell back
to `$companyID`, which `Users.php:969-971/994` had already overwritten with the OneStack
email-sender company. A bank login's form has no Bank dropdown (`users_add_form.php:123`),
so the contact landed under OneStack instead of the bank, while the user row (`:940`)
correctly used the session bank. Fix: fall back to the session `company_id` first, then
`$companyID`. OneStack logins are unchanged (verified by simulation).
