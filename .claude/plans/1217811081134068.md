# PART 1 — In simple words

## What the system does today

The bank has to send many reports to the RBI (the Reserve Bank). Each report has
a fixed layout, and those layouts were drawn up as Excel files.

A developer built a small helper page that turns one of those Excel layouts into
a web page. That web page then becomes the screen where staff fill in that
report. It works like a photocopier that turns a paper form into a web form.

You tell the helper which Excel files to convert, for example
`A13-SCBs/Cards-Statistics.xlsx`. It reads that file from a "templates" drawer on
the server and writes the finished page into an "output" drawer. The folder name
you gave it decides which sub-folder of the drawer is used.

Nothing else in the system calls this helper. A person has to call it
deliberately.

## What is wrong with it

1. **No one checks who is using it.** The helper is supposed to sit behind the
   admin login. The one line that switches that check on has been turned off
   (commented out). Anyone on the internet who knows the address can use it.
   It is a staff-only photocopier room with the lock taken off the door.

2. **The caller decides where the copy goes, and nothing checks it.** Folder
   names can contain `../`, which means "go up one folder". By adding enough of
   them, a caller can step out of the output drawer and into any part of the
   server. The helper will:
   - create new folders anywhere on the server, even when the conversion then
     fails, and
   - write a new file next to any Excel file that already exists anywhere on the
     server.

   The file it writes is a `.php` file. That is a type of file the server runs as
   a program rather than just showing it. That is on purpose, because the output
   is meant to become a report screen. But it means a caller who can also get
   their own Excel file onto the server some other way could plant a program and
   have the server run it. That is the worst kind of break-in.

Production runs PHP 7.4. On that version, the half-broken logging lines in this
helper do **not** stop it, so everything above really happens on production
today if someone calls it. We have not yet confirmed whether anyone has.

## What we are going to change

- **Put the lock back.** Only a signed-in admin can use the helper.
- **Check every file name before using it.** Only plain letters, numbers and a
  few safe symbols are allowed. `../` is refused, and the file must be an Excel
  file that really exists inside the templates drawer. Anything else is skipped
  and noted in the helper's own log.
- **Create folders only after the name has passed the check.** Folders are also
  only ever created inside the output drawer.
- **Remove four broken logging lines.** They refer to a log file that is no
  longer opened.
- **Make the converter step private,** so it can no longer be reached directly
  from a web address.

The output stays a `.php` report screen, exactly as today.

## What could go wrong

- **A script that calls it without logging in will stop working.** Nothing in
  the code calls it, but a developer might have a script or bookmark that does.
  After the fix, that caller is sent to the login page instead.
- **Unusual folder or file names would be refused.** A template whose name
  contains a character outside the allowed set (for example `&`, `'`, `#` or
  `$`) would be skipped. All the template names in the repository today pass.
  The only exception is `~$PSA-Return.xlsx`, which is an Excel "file is open"
  lock file, not a real template.
- **Some admins can still use it.** Any signed-in admin can run it, not only the
  people meant to. Checking the finer per-screen permission is a separate task
  (Asana 1217811081134060).

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Controller | The piece of code behind one web address on the server. |
| Constructor / `parent::__construct()` | Code that runs first, every time, before anything else. The parent's constructor is where the "are you signed in and an admin?" check lives. Commenting it out removes the check. |
| `.php` file | A file the web server runs as a program, rather than just showing it. |
| Path traversal (`../`) | Using "go up one folder" in a file name to escape the folder you were meant to stay in. |
| `realpath()` | Asks the server "where does this path really end up?", after following every `../` and shortcut. We use it to prove a file is inside the right folder. |
| Allowlist | A list of what is allowed. Anything not on it is refused. |
| RCE | Remote code execution: a stranger getting the server to run their program. |

# PART 3 — The technical version

## Root cause

This was verified against `origin/onestackcbs`. That file is identical to the
current branch (825 lines).

**1. The authentication chain never runs**, `RbiReportAutomationController.php:12-16`:

```php
class RbiReportAutomationController extends Admin_Controller
{
    public function __construct()
    {
        // parent::__construct();
```

`Admin_Controller::__construct()` (`application/core/MY_Controller.php:94-107`)
and `Auth_Controller::__construct()` (`:325-337`) are what enforce
`ion_auth->logged_in() && is_admin()`. On failure they redirect to `auth/login`,
or echo a script redirect for AJAX requests. Neither runs here.

`PermissionService` would not apply even with the parent restored. The URI
starts with `mobile_app`, not `admin`, so the check at `MY_Controller.php:347`
is skipped. That is the known hole, covered by Asana 1217811081134060.

The task's line `:16` still matches.

**2. The caller controls the input and output paths**, in `RbiReportAutomation()`
at `:750-822`. The task says 754-830, but the method now spans 750-822.

```php
752  $post = json_decode(file_get_contents('php://input'), true);
755  if (isset($post['files'])) { $filePaths = $post['files']; }
769  $fileNames = explode(',', $filePaths);
774  $folderName = dirname($fileName);
779  $outputDirectory = FCPATH . "assets/rbiReportTemplate/htmlToExcel/$folderName";
791  if (!is_dir($outputDirectory)) {
792      mkdir($outputDirectory, 0755, true);
797  $reportContent = $this->processExcel($fileNameOnly, $folderName);
802  $exampleFile = $outputDirectory . "/$fileNameOnly.php";
805  file_put_contents($exampleFile, $reportContent);
```

- `$folderName` goes into the path unchecked. `processExcel()` then reads
  `excelToHtml/$folder_name/$file_name` (`:34`) with that same folder.
- `excelToHtml/../X` and `htmlToExcel/../X` resolve to the same place. So one
  `../` payload moves both the input and the output. The effect is that the
  output `.php` lands next to any `.xlsx` that exists anywhere on disk.
- `mkdir(..., true)` at `:792` runs **before** the input is loaded. Arbitrary
  directory creation happens even when the load then throws.
- The written content is built from the spreadsheet's sheet names and cells.
  `generateHeader()` (`:320-338`) emits `<?php include_once ($rbiReportIncludePath); ?>`,
  so `.php` output is intended: it is a view template like those in
  `application/modules/cbs/views/reports/rbi-report/`. An attacker controls the
  content only if they can place their own `.xlsx` on the server.
  Sanitising spreadsheet content is **out of scope**.

**3. Dangling `fwrite`/`fclose` on an undefined handle**, `:788-789` and `:813-814`:

```php
788  fwrite($myfile, $txt1);
789  fclose($myfile);
```

- These used to reuse the handle from a `fopen` at the "Generation has been
  started" log. Commit `a0a563a0a3` (fopen to `writeLogRaw`, Asana
  1217811081134142) replaced that `fopen` and left these four lines behind.
- On production's PHP 7.4.33 (confirmed by the user, `php -v`) they only raise
  warnings, which are hidden by `error_reporting(E_ERROR)` (known-patterns). The
  write at `:805` therefore still happens.
- On PHP 8 they would be a fatal `TypeError`.
- The only thing lost by removing them is a duplicate log entry that no longer
  works anyway.

**4. `$filePaths` is undefined when `files` is missing** (`:755-767`). This is a
notice only; execution falls through to `die("No files provided.")`.

**5. `processExcel()` is `public` (`:32`),** so it can be reached by URL. It is
read-only and its return value is discarded, but it is the input half of the
same defect.

## How it will be fixed

All changes are in one file. Neighbouring style stays the same: tabs and
spaces as in the file, `writeLogRaw` for logging, `die()` for the existing
"no files" path.

1. **Constructor:** uncomment `parent::__construct();`. Leave the other
   commented lines alone.
2. **New private method `resolveReportPath($fileName)`.** It returns the cleaned
   relative path, or `false`:
   - `trim()` the entry and reject it if it is empty.
   - Reject it unless it matches `#^[A-Za-z0-9 _.()\-]+(/[A-Za-z0-9 _.()\-]+)*$#`.
     This rules out a leading `/`, `\`, `:`, NUL and every other special
     character.
   - Reject it if any `/`-separated part is `.` or `..`.
   - Reject it unless it ends in `.xlsx`, case-insensitive. Real templates
     include `.XLSX`.
   - Reject it unless `realpath(FCPATH . 'assets/rbiReportTemplate/excelToHtml/' . $fileName)`
     exists and starts with `realpath(<excelToHtml base>) . DIRECTORY_SEPARATOR`.
3. **In `RbiReportAutomation()`:**
   - Initialise `$filePaths = null;`.
   - Require `is_string($filePaths)`; otherwise go to the existing
     `die("No files provided.")`.
   - At the top of the loop, call `resolveReportPath()`. On `false`, write a
     `writeLogRaw` line to the same RbiReport log saying the entry was
     rejected, then `continue`. Do not log the raw entry; log only its length,
     so no attacker-supplied text reaches the log.
   - After `mkdir`, confirm `realpath($outputDirectory)` is inside
     `realpath(FCPATH . 'assets/rbiReportTemplate/htmlToExcel')`. Otherwise log
     and `continue`. This needs `htmlToExcel/` to exist, so create the base with
     the same `mkdir(..., 0755, true)` first.
   - Everything after that is unchanged: `dirname`/`basename`, the
     `processExcel()` call, `basename($fileName, '.xlsx')`, the `.php` output
     name and `file_put_contents`. Keeping the case-sensitive `'.xlsx'` suffix
     means a `.XLSX` template still produces `Name.XLSX.php`, exactly as today.
   - Delete `:788-789` and `:813-814`.
4. Change `public function processExcel` to `private function processExcel`.
   Its only caller is `:797`, inside this class.

Not changed: the `generate*()` helpers (pure string builders, no I/O), logging
`$post` at `:762`, sanitising spreadsheet content, and PermissionService
coverage of `mobile_app/*` URIs.
