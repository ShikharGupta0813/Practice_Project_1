# PART 1 — In simple words

## What the system does today

Every time the system does something worth remembering it writes a line into a
diary file — "OTP checked for this customer at 14:32", "payment sent to the
bank, this came back". Nobody reads these for pleasure. You read them when
something has gone wrong and you need to know what happened at 3pm last Tuesday.
For a bank it is also how you answer a customer disputing a payment, and how you
answer a regulator.

The diaries are split by topic into separate folders — one for OTP, one for
each bank, one for each payment network. There are 97 of them. A filing room
with 97 labelled drawers.

When code is copied onto a server, it comes from the team's shared store. A
rules file says what must never go into that store, and log files are top of
that list — they are enormous, they change every second, and they contain real
customer activity. **That rule is correct and this task does not change it.**

## What is wrong with it

The rule is written too broadly. Instead of "do not store the diary pages" it
says "do not store the filing room". So the empty drawers are left out too.

Set up a fresh server and the code arrives without the filing room. No drawers.
The system then tries to write into a drawer that is not there, the write fails,
and **nothing notices** — the failure is never checked, so no error appears
anywhere. The line simply vanishes.

Everything looks healthy. The site runs, payments go through. Weeks later
somebody goes to check the trail for a disputed payment and finds nothing. Not
an error — nothing. It was never written, and nobody was told.

One detail makes this much harder to spot. There is a piece of code that creates
the **top-level** folder if it is missing, so the general logs work fine. All 97
of the topic drawers underneath it are never created. So the part you would
casually check looks correct, while the parts you would actually need in an
investigation — the bank and payment-network trails — are the ones going
missing.

## What we are going to change

Correct the rule so it blocks the diary pages but keeps the empty drawers, and
put one small placeholder file into each of the 97 folders so they travel with
the code. A freshly built server then arrives with the whole filing room already
in place, and every log line has somewhere to go.

## What could go wrong

The change touches no running code, no customer data and no money. It adds
folders and edits a rules file. The honest risks:

**Real logs must keep being excluded.** If the new rule were written wrongly,
live logs containing customer activity could start being committed into the
shared store — worse than the problem being fixed. The exact rule was therefore
tested against real git in a throwaway repository before being written down, and
that test is repeated in the test section.

**Existing logs on the live server must not be disturbed.** The change only adds
placeholder files and never removes or overwrites a log.

**The folders must be writable once they arrive.** If the deployment process
creates them owned by a different user than the one the website runs as, they
would exist but not accept writes — the same silent failure in a new costume.
This is the one thing that cannot be checked from here, so it is a required
pre-merge step in the test section.

The change is wide but shallow: 98 tiny identical files with no logic in them.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| Log | A diary file the system writes as it works, used to investigate problems later. |
| `.gitignore` | The rules file listing what must not go into the shared code store. |
| Deploy | Copying the code onto a real server so customers use it. |
| `index.html` | A blank placeholder page. Used here for two reasons: a folder cannot travel with the code unless it holds at least one file, and it stops a visitor seeing a list of the folder's contents. |
| Negation / exception | A rule line starting with `!`, meaning "except this — keep it after all". |
| Ownership | Which user account owns a folder. A folder owned by one user may not be writable by another, even though it plainly exists. |

# PART 3 — The technical version

## Root cause

**The line named in the task title is not the cause.** `.gitignore:31-33` is
correct as written:

```
31:/application/logs/*
32:!application/logs/index.html
33:!application/logs/.htaccess
```

The blocker is 51 lines later, at **`.gitignore:82`**:

```
82:/application/logs
```

No trailing `/*`, so this excludes the **directory**. Git cannot re-include
anything beneath an excluded directory, which makes the negations at lines 32-33
inert. Git names the responsible line itself:

```
git check-ignore -v application/logs/index.html
-> .gitignore:82:/application/logs	application/logs/index.html
```

Result on production:

```
git ls-tree -r --name-only onestackcbs -- application/logs/
-> (no output)
```

Nothing is tracked under `application/logs/` — not even the two files lines
32-33 exist to preserve, neither of which is present on disk. A fresh clone or
deployment gets no `application/logs` directory at all.

**Why this has stayed invisible.** `writeLog()` at
`application/helpers/common_helper.php:1776` does contain a `mkdir`, but it
guards the wrong path:

```php
$folderPath = "./application/logs/";
if (!file_exists($folderPath)) {
    mkdir($folderPath, 0777, true);
}
if($folderName != ""){
    $folderName = $folderName . "/";
}
$filePath = $folderPath . $folderName . $logFileName . "-" . date('Y-m-d') . ".log";
file_put_contents($filePath, $txt, FILE_APPEND);
```

It creates the **parent**, then writes into `./application/logs/<folderName>/`
which it never checks. So the top-level directory self-heals on any fresh server
— flat logs work, everything looks fine — while all 97 subdirectories silently
do not. `file_put_contents` returns `false` and the value is discarded, so no
failure surfaces.

`AppLog` has no directory handling at all. Verified: `mkdir`, `is_dir` and
`file_exists` appear nowhere in `application/libraries/AppLog.php`. It builds
its path at `AppLog.php:79-82` and writes at `AppLog.php:41`, discarding the
result. It writes flat (`application/config/applog.php:8` — "Logs directory (NO
subfolders)"), so it needs only the root, which it gets as a side effect of some
earlier `writeLog()` call having created it.

**Why a code-only fix is insufficient — the decisive evidence.** Most logging
does not go through either helper. Counting `fopen` / `file_put_contents` /
`write_file` calls whose literal path targets a log **subdirectory**, excluding
commented lines and `bkp` files:

```
835  direct write sites into a log subdirectory
132  distinct files containing them
 40  distinct subdirectories
111  of those 132 files contain no mkdir anywhere
```

Concentrated exactly where an investigation would look: `logs/npci/` (250
sites), `logs/kcc/` (108), `logs/testing/` (97), `logs/yesbank/` (80),
`logs/cbs/` (54), `logs/transaction/`, `logs/upi/`, `logs/transunion/`.

Representative, `application/libraries/common/CommonFunctions.php:908`:

```php
$myfile = fopen("./application/logs/firebase-dynamic-link/firebase-dynamic-link-api-log-" . date('Y-m-d') . ".php", "a");
```

No `mkdir`, no check. Fixing `writeLog` and `AppLog` would not affect this line
or the other 834.

**Deploy mechanism.** `appspec.yml:3-7` has AWS CodeDeploy copy the whole
repository to `/var/www/vhosts/onestack-app-prod`:

```yaml
files:
  - source: /
    destination: /var/www/vhosts/onestack-app-prod
    overwrite: true
file_exists_behavior: OVERWRITE
```

So anything committed is deployed — which is what makes this fix work. The
`BeforeInstall` hook that would run `scripts/prepare_deploy` is commented out
(`appspec.yml:8-11`), so that script never runs today.

**Other log rules in the file, checked and deliberately untouched:**

- `.gitignore:2-3` — `*/logs/log-*.php` and `!*/logs/index.html`. Generic and
  complementary; line 3 already intends to preserve `index.html`. No conflict.
- `.gitignore:196` — `/cbs_api/application/logs/*`. Targets a directory absent
  from this repository (`git ls-tree onestackcbs` has no `cbs_api` entry). No
  interaction.

**Task title line number:** `.gitignore:31` is real and still at line 31, but is
not the cause. The cause is line 82, which the task does not mention.

## How it will be fixed

Replace `.gitignore:31-33` with a recursive block and delete line 82:

```
/application/logs/**
!application/logs/**/
!application/logs/**/index.html
!application/logs/**/.htaccess
```

Line 1 excludes everything under `application/logs` at any depth. Line 2
re-includes the directories so git will descend into them. Lines 3-4 re-include
the keeper files at any depth. Four lines cover all 97 directories and any added
later — no per-directory rules, nothing to maintain.

Then add `application/logs/index.html` plus one `index.html` in each of the 97
subdirectories — 98 files, each the standard CodeIgniter 403 page already used
296 times in this repository (copy `application/config/index.html` verbatim):

```html
<!DOCTYPE html>
<html>
<head>
	<title>403 Forbidden</title>
</head>
<body>

<p>Directory access is forbidden.</p>

</body>
</html>
```

`index.html` rather than `.gitkeep`: identical file count, matches the existing
convention, and additionally suppresses directory listings. No `.htaccess` is
created — no directory in this repository uses an `.htaccess` deny-file, so
inventing one would introduce a new pattern. The negation for it is kept so one
added later is preserved.

**Both halves are required.** Verified against real git in a throwaway
repository:

```
TEST A: recursive block present AND /application/logs still present
  git add -A ; git ls-files  ->  .gitignore only        (no index.html tracked)

TEST B: recursive block present, /application/logs REMOVED
  git add -A ; git ls-files  ->  .gitignore
                                 application/logs/index.html
                                 application/logs/otp/index.html
  git check-ignore -v application/logs/otp/otp.log
                             ->  .gitignore:1:/application/logs/**   (still ignored, correct)
```

## Rejected alternatives

**Fix `writeLog()` and `AppLog` to create their own directories.** The smallest
possible change (2 files, ~6 lines) and the user's own preferred approach, but
it does **not** fix the bug: 835 write sites across 132 files bypass both
helpers entirely, including all 250 `logs/npci/` sites. Rejected on the
"do not compromise the fix" instruction. It remains a good follow-up for
future-proofing — it would cover directories nobody remembers to commit — but it
is not this task and is deliberately excluded to keep the change minimal.

**Create the directories at deploy time** (the task title's "or" branch):
enable the `BeforeInstall` hook in `appspec.yml` and add a shell script. Two
files, no runtime cost, and it would allow an explicit `chown`. Rejected
because it cannot be verified before merge — the hook is currently disabled,
`scripts/prepare_deploy` references a different and probably stale directory
(`onestack-app` rather than `onestack-app-prod`), and a faulty `BeforeInstall`
hook fails the deployment itself. Trading a silent logging bug for a possible
deploy failure is a bad trade on a banking system that cannot be rehearsed from
here.

**A CodeIgniter `pre_system` hook that creates all 97 directories.** Two files
and self-healing. Rejected: `enable_hooks` is `TRUE` but
`application/config/hooks.php` defines no hook at all, so this would be the
project's first, and it would run on every request in exchange for solving a
once-per-deployment problem.

**Editing the 835 call sites.** Not seriously considered; vastly larger and
riskier than the chosen fix.

## How to test

**Step 0 — GATE, production, read-only. Answer before opening the PR.** The fix
only works if the deployed folders are writable by the web server user:

```bash
ls -ld /var/www/vhosts/onestack-app-prod/application/logs
ls -ld /var/www/vhosts/onestack-app-prod/application/logs/* | head
ps -eo user,comm | grep -E "apache|httpd|php-fpm|nginx" | sort -u
```

Compare the owner of the log directories with the user the web server runs as.
If they match, proceed. If the directories would arrive owned by `root` while
the web server runs as `apache`/`www-data`, this plan is **incomplete** — it
would replace "folder missing" with "folder unwritable", which fails identically
and silently, and additionally stops `writeLog`'s existing `mkdir` from
rescuing the root folder. In that case stop and add a deploy-time `chown` step
before merging. Record the result in the PR body either way.

**Step 1 — the ignore rules are correct:**

```
grep -n "application/logs" .gitignore
```

Expect the four-line recursive block and **no** bare `/application/logs` line. A
surviving bare line makes the entire change inert.

**Step 2 — real log files are still ignored.** Safety-critical; a failure here
would start committing customer activity:

```bash
mkdir -p application/logs/otp application/logs/npci/query/imps
printf 'x\n' > application/logs/log-test-delete-me.php
printf 'x\n' > application/logs/otp/otp-test-delete-me.log

git check-ignore -v application/logs/npci/query/imps/imps-test-delete-me.log
rm -f application/logs/log-test-delete-me.php application/logs/otp/otp-test-delete-me.log application/logs/npci/query/imps/imps-test-delete-me.log
```

All three must print a matching rule (exit 0). Any "not ignored" is a FAIL —
stop before committing.
