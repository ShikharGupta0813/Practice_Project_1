Asana: https://app.asana.com/1/1139764983605995/task/1217811081134078  |  ID: 1217811081134078  |  Due: 2026-10-16

User decisions (2026-09-30): add the signature check whether or not SafeGold is
live; when the check fails, still save the record, marked `failed`.

Scope widened after AI review (2026-09-30), applied under the "fix real problems
this change introduces" rule. Before this change, a replayed genuine callback
only added "failed" rows. Once genuine callbacks record "success", a replay would
add duplicate **success** payment rows. So: once an order is recorded as paid,
later callbacks for it write nothing to the payment tables. The check runs under
a row lock (`SELECT ... FOR UPDATE`) inside the existing transaction, so two
simultaneous callbacks cannot both write. Ignored callbacks go to
`application/logs/safegold/save-payment-ignored<date>.php`, so the attempt
still leaves a trail, and the response follows the request's own signature
result ("Payment Success" only if that request is itself validly signed).
Callbacks for orders not yet paid are recorded exactly as the decision above says.

# PART 1 — In simple words

## What the system does today

In the app, a customer can buy digital gold. They pay through Razorpay, an
outside payment company. When the payment finishes, the payment screen sends our
server a short message: "this order, this payment, it worked" — or "it failed".

Razorpay signs every "it worked" message with a secret code that only Razorpay
and we know, a bit like a wax seal on a letter. Checking the seal is how you know
the letter really came from Razorpay.

Our server writes the message into two record books: the gold-order book and the
main payments book.

## What is wrong with it

Our server never looks at the seal. It files the seal away and then decides
"paid" or "not paid" only by whether the message has a line called "status".

So anyone can send our server a made-up "it worked" message with a status line,
and the order is written down as **paid**, even though no money moved. The
payments book then shows a payment that never happened, which can mislead
anyone reconciling money or reading reports.

It is also wrong the other way: a *real* Razorpay "it worked" message does not
carry a "status" line, so real payments are currently written down as
**failed**.

Nothing in the code hands over gold based on this record, so no gold is given
away for free today. The damage is false (and missing) payment records.

## What we are going to change

Before writing anything down, the server will check Razorpay's seal. Only a
message with a genuine seal is recorded as a successful payment. Anything else
(no seal, a wrong seal, or Razorpay's own "failed" message) is still recorded,
but as **failed**, so there is a trail of every attempt.

## What could go wrong

- Real successful payments will start being recorded as **success** where today
  they are recorded as failed. That is the correct result, but anyone who
  relied on the old (wrong) value will see a change.
- If the secret code stored in our system does not match the Razorpay account
  that took the payment, every payment will be recorded as failed. The secret
  that creates the order is the same one that will check it, so this should not
  happen.
- SafeGold looks unfinished in production (a test-mode Razorpay key, a fixed ₹1
  amount, and no web address set up for this message). This fix makes the
  endpoint safe; it does not make SafeGold ready for launch.

# PART 3 — The technical version

## Root cause

`application/modules/mobile_app/controllers/apiv2/InvestmentsSafeGold.php`,
`save_payment_post()` at **469-535** on `onestackcbs` (the task's 475-531 range
is inside it and still accurate). Success is decided by the presence of a field,
and the signature is only stored:

```php
'razorpay_signature' => isset($_POST['razorpay_signature']) ? $_POST['razorpay_signature'] : '',   // :497
'payment_status' => isset($_POST['status']) ? 'success' : 'failed',                                  // :501
...
'payment_status' =>isset($_POST['status']) ? 'success' : 'failed',                                   // :513
```

The result is written in one transaction to `tbl_payment_transactions` (insert,
:519) and `tbl_safegold_transaction` (update by `razorpay_order_id`, :521-522).

`apiv6/InvestmentsSafeGold.php` is byte-for-byte identical in this method
(checked with `diff` of the two `save_payment_post` bodies: identical).

Supporting facts:

- The caller is Razorpay Checkout inside `application/views/pages/razorpay_view.php:11-30`.
  It posts Razorpay's `handler` response (`razorpay_payment_id`,
  `razorpay_order_id`, `razorpay_signature`, **no `status`**) or the
  `payment.failed` response (`error[...]`). So genuine successes are
  recorded `failed` today.
- The secret is in `application/third_party/safegold/libraries/Safegold.php:19-20`
  (`rzp_test_…` key, hardcoded secret), and the same library creates the order
  with it at :30-35. The controller already loads this library
  (`InvestmentsSafeGold.php:23`, `$this->safegold`).
- The Razorpay SDK (`razorpay/razorpay 2.*`, `composer.json:9`) has
  `Utility::verifyPaymentSignature()`
  (`vendor/razorpay/razorpay/src/Utility.php:9-45`). It computes
  `HMAC-SHA256(order_id|payment_id, Api::getSecret())` and throws
  `Razorpay\Api\Errors\SignatureVerificationError` on mismatch.
  `Api::getSecret()` is static and is set by `new Api($key, $secret)`.
- Reachability: `razorpay_view.php:26` posts to `api/v2/safegold/save-payment`,
  but no route file on `onestackcbs` defines it (grep below). The method can still
  be reached through the HMVC module path, and `Mobile_Controller`
  (`libraries/common/Mobile_Controller.php:30-34`) only checks the session when an
  `Authorization` header is sent, so it takes unauthenticated requests. Consistent
  with the REST known issue in CLAUDE.md, which this task does not change.

## How it will be fixed

1. **Library** (`Safegold.php`): add one method next to the existing Razorpay
   helpers, in the same style:

   ```php
   public function verify_payment_signature($attributes) {
       $api = new Api($this->razorpay_api_key, $this->razorpay_api_secret);
       try {
           $api->utility->verifyPaymentSignature($attributes);
           return true;
       } catch (\Razorpay\Api\Errors\SignatureVerificationError $e) {
           return false;
       }
   }
   ```

   The secret stays where it is. Moving it is out of scope (consistency rule).

2. **Controller** (apiv2 and apiv6, identical edits): after the order lookups
   succeed and before `$data` is built, decide the status from the signature:

   ```php
   $signature_valid = false;
   if (!isset($_POST['error']) && !empty($_POST['razorpay_signature'])) {
       $signature_valid = $this->safegold->verify_payment_signature([
           'razorpay_order_id'   => $razorpay_order_id,
           'razorpay_payment_id' => $razorpay_payment_id,
           'razorpay_signature'  => $_POST['razorpay_signature'],
       ]);
   }
   $payment_status = $signature_valid ? 'success' : 'failed';
   $msg = $signature_valid ? 'Payment Success' : 'Payment Failed';
   ```

   Replace both `isset($_POST['status']) ? 'success' : 'failed'` (:501, :513)
   with `$payment_status`. Keep everything else as it is: the raw response
   stays in `razorpay_response`, `razorpay_status`/`payment_gateway_status` still
   copy `$_POST['status']`, and both rows are still written. A failed check is
   recorded as `failed` (user decision), not refused.

   Remove the two early `$msg =` assignments at :475 and :479 (now set below), so
   the message cannot say "Success" while the status says `failed`.

Not changed (separate issues, noted here so they are not lost):
- Hardcoded Razorpay key/secret and SafeGold access token in `Safegold.php`.
- Idempotency after payment is handled in this task (see the note at the top).
- No route for `api/v2/safegold/save-payment`, the ₹1 hardcoded amount
  (`InvestmentsSafeGold.php:47`), and "Test Transaction" in the view.
