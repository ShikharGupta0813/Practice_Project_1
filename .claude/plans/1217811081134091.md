# PART 1 — In simple words

## What the system does today

Every admin page and button has a web address, and the permission guard decides
who may use it from the page name inside that address. Behind each address sits
one piece of server code (a "method") that does the work.

Often **several** addresses lead to the same piece of code. For example, the
code that looks up a state from a PIN code is reachable through 10 different page
names, because many screens need it.

## What is wrong with it

The guard checks the page name in the address, not the code behind it. If the
same code can be reached through ten page names, a user who is allowed on **any
one** of those ten pages can use it.

For a harmless lookup (state from PIN code), that doesn't matter. For code that
**changes** data, such as changing a customer's status or sending an email to
every customer, it means someone given one small, unrelated page can do
something their role was never meant to allow.

There are 121 such pieces of code. Nobody yet knows which ones are harmless.

## What we are going to change

Nothing in the code, in this task. We go through all 121, sort each into
"harmless lookup", "sensitive read" or "changes data", and for every risky one
write down which single page name *should* be the way in and what the fix is. The
result is a report plus a short list of fix tasks.

## What could go wrong

- Nothing breaks: no code changes.
- If the audit runs before task 2's route clean-up reaches production, part of
  the list will describe routes that are about to disappear. That is why it
  waits.

# PART 3 — The technical version

## Root cause

`PermissionService::checkPermission()` derives permission from the URL's slug
(`MY_Controller.php:347-372`, `PermissionService.php:119-171`), not from the
target `controller/method`. So a method with routes under N slugs is reachable by
anyone holding any one of the N menu permissions.

Count re-verified on production (2026-09-30): merging the four route files in
load order (`routes.php`, `cbs-routes.php`, `production/routes.php`,
`production/cbs-routes.php`), keeping only uncommented `$route[...] = '...'`
lines, taking `admin/*` keys, stripping `-(view|add|edit|delete)` from segment 2,
and grouping by lowercased target without `/$N` arguments gives
**3,669 routes → 1,909 admin targets → 121 targets with more than 2 distinct slugs.**
This matches the task title exactly. With `(a|b)` regex groups expanded into their
alternatives, the real figure is **160** (script below).

Sample of the top of the list:

| Slugs | Target | First look |
|---|---|---|
| 12 | `bank_onboarding_form/partnermaster/getpartnerbankslist` | read, list of partner banks |
| 10 | `bank_onboarding_form/companymaster/getstatebypincode` | harmless lookup |
| 10 | `bank_onboarding_form/companymaster/getcitybystateid` | harmless lookup |
| 6 | `customers/customermaster/sendincompleteprofilemailertoall` | **writes / sends mail to all** |
| 6 | `communication/smstemplates/getsmstemplatelist` | read |
| 5 | `customers/customermaster/changecustomerstatus` | **writes customer status** |

Some "slugs" are regex groups such as `(bank-list-view|clientTicket-view|...)`.
Each alternative must be expanded before counting distinct slugs.

## How it will be done

1. **Wait for the gate:** PR #13445 (task 2, currently OPEN to `onestackcbs-dev`)
   and its production PR are merged to `onestackcbs`. Check with:
   `gh pr list --head sg_cl_no_suffix_admin_routes --state all --json number,baseRefName,state`.
2. **Regenerate the list** from `origin/onestackcbs` with the script under "How
   to test". Use the expanded count and report it. Today it's 160; it should drop after task 2.
3. **Classify each target** by reading the method body (not the name):
   - **A: harmless lookup.** Read-only reference data, e.g. states, cities,
     pincode, template lists. No action.
   - **B: sensitive read.** Returns customer, transaction, bank or credential
     data. Check whether the method scopes by session bank itself.
   - **C: changes data.** Any insert, update or delete, file write, mail/SMS
     send, or external API call with side effects.
4. **For every B and C:** decide which slug(s) are legitimately related (the
   screens that really call it, found by grepping views/JS for the route key)
   and which are unrelated leftovers. Recommend one of: remove the unrelated
   route aliases; give the method its own slug + action and a menu/access row;
   or add an explicit in-method permission check.
5. **Write the report** to `.claude/plans/1217811081134091_audit.md`:
   - summary counts per class;
   - one table row per target: target, slugs (expanded), class, the screens that
     call it, verdict, recommended fix;
   - "Follow-up fixes": the C-class and unscoped B-class items grouped into fix
     tasks (same file = same task), each with files and a size estimate.
6. Hand the report to the user. Creating follow-up Asana tasks is the user's call.

Out of scope: changing any route or code; targets with 1-2 slugs; non-`admin/`
routes (those are covered by task 44's `no-action` path).
