# PART 1 — In simple words

## What the system does today
There are two copies of the banking console. One is the practice copy
("rbank.in", also called sandbox), where new things are tried. The other is the
real one ("admin.onestack.in", production), used with real customers' data.
Each copy has its own database (the filing cabinet where all its records are
kept) and its own set of logins to open that cabinet.

## What is wrong with it
Nothing is proven wrong. The question is whether the two copies are really
walled off from each other. If the practice copy holds a key to the real
cabinet, then anyone who breaks into the practice copy (which is the weaker,
less guarded one) gets into the real records too.

What we found so far, in plain terms:
- The two copies use **different databases** (different names), and your
  checks on cookies, keys and admin logins came back clean.
- BUT the practice copy has **a second, deliberate door into the real
  database**. Its settings file defines a connection called
  `production_migration_database`, and a program (`DataTransferCron`) uses it to
  copy data between practice and real. So the answer to "do they share a
  backend?" is not a plain "no": there is a built-in link, and what matters now
  is how much that link is allowed to do.
- Neither settings file shows the real passwords or addresses. Both read them
  from hidden environment settings. So the settings files alone cannot prove
  the two are separate; the hidden values have to be compared.

## What we are going to change
Nothing in the program. We run a short list of read-only checks on both
servers, write down the answers, and post the result on the Asana task. If the
link into the real database is more powerful than it needs to be, that becomes
a separate follow-up task.

## What could go wrong
Nothing, as long as only the read-only checks are run and no password is
pasted anywhere. The risk is the opposite: pasting passwords into chat, Asana
or screenshots. Compare short fingerprints instead (see "How to test").

# PART 3 — The technical version

## Root cause
Not a bug. The task asks for a verification, and the repo shows both what is
known and what is not:

1. **Both `database.php` files take credentials from `$_ENV`**, so the files
   do not show which host or database each environment really uses.
   - production `database.php` (from the server): `'hostname' => $_ENV['DEFAULT_DB_HOSTNAME']`, same for `username`, `password`, `database`.
   - rbank `database.php` (from the server): same `$_ENV[...]` keys.
   - The earlier statement "each file only holds its own credentials" is
     therefore **not provable from the files**. It has to be checked on the
     env values.
2. **rbank has a connection group that targets production.**
   - rbank `database.php`: `$db['production_migration_database']` with `MIGRATION_DB_HOSTNAME/USERNAME/PASSWORD` and `'database' => $_ENV['PRODUCTION_MASTER_DB_DATABASE']`.
   - This group does **not exist** in the production file.
3. **A tracked controller uses it for writes.**
   - `application/modules/cbs/controllers/DataTransferCron.php:12`: `$this->pdb = DatabaseFactory::getInstance('production_migration_database');`
   - `:20-21`: for `$destination == 'production'` the code sets `$destinationDb = $this->pdb`.
   - `:831`: `$this->pdb->insert(CbsDbTable::CBS_VOUCHER_ENTRIES, $refData);` (production inserts), `:781` begins a transaction on `$this->pdb`.
   - Route status: `application/config/cbs-routes.php:1383-1384` are commented `UNUSED-ROUTE`, so it is not reachable over HTTP. It still runs from the command line through `index.php` (CI CLI), i.e. cron.
4. **Two other sandbox-to-production paths exist and were NOT inspected**:
   `application/config/routes.php:1373-1382` `move-to-sandbox/*` and
   `*-move-to-production/*` → `mobile_app/api/MoveToSandbox` and `MoveToProduction`.
   Whether those use the DB link or HTTP calls: **not verified**.
5. **Passwords sit in commented-out blocks in both server `database.php` files**
   (observed in the pasted copies; none of this is in the tracked repo —
   `git grep` for those strings in tracked files returned nothing). One of the
   old production passwords is **identical** to the old sandbox user's password
   in the production file's comment, so the two environments once used the
   same password for different users. Values are deliberately not repeated here.
6. rbank `database.php` also has a hard-coded Oracle block (`$db['oracle']`
   with an IP host and a trivial username/password). Out of scope; noted for
   a separate task.

## How it will be fixed
No code. Determine, with read-only checks, whether the migration link gives
rbank write access to the production master DB, and whether any secret,
network path or login is shared. Record the finding. Remediation, if any
(restrict the migration user to least privilege, firewall the link, rotate
credentials, delete the commented passwords) becomes separate tasks.

## Plan
1. Locate the env file on each server (read-only):
   `ls -la /var/www/vhosts/rbank.in/ /var/www/vhosts/onecbs-prod/ | grep -i env`
2. On each server, list the hostnames and database names only (never
   usernames/passwords) and compare them. Any equal host+database pair across
   the two servers means a shared backend.
3. Compare username and password **fingerprints** between the two servers.
4. Test network reach from each server to the other's DB host.
5. On the production DB, list the grants of the migration user.
6. Record the answers in the table under "How to test"; post the result and the
   conclusion on the Asana task. Raise follow-ups for anything non-isolated.

## How to test
Run on the servers, read-only. Replace `ENVFILE` with the path from step 1.
Never paste values from `*_PASSWORD` lines anywhere.

Host and database names (safe to share), run on BOTH servers:

```bash
grep -E '^(DEFAULT|SLAVE|LOGGER|ONECBS|REPORTING|RECON|MIGRATION|PRODUCTION_MASTER)_DB_(HOSTNAME|DATABASE)=' ENVFILE
```

Salted fingerprints of usernames and passwords, run on BOTH servers; compare the
short codes by eye. Do not post the codes in Asana:

```bash
while IFS='=' read -r k v; do printf '%s %s\n' "$k" "$(printf 'cmp14:%s' "$v" | sha256sum | cut -c1-10)"; done < <(grep -E '_DB_(USERNAME|PASSWORD)=' ENVFILE)
```

Network reach, from the rbank server to the production DB host (value of
`DEFAULT_DB_HOSTNAME` on the production server), then the reverse:

```bash
nc -vz -w 3 PROD_DB_HOST 3306
```

Production DB, read-only. Run in phpMyAdmin on production, using the user
value of `MIGRATION_DB_USERNAME` from the rbank env:

```sql
SELECT user, host FROM mysql.user ORDER BY user;
SHOW GRANTS FOR 'MIGRATION_USER'@'%';
```

How to read the results:

| Check | Result | Meaning |
|---|---|---|
| Host+database pair equal on both | yes | Shared backend. Finding, high priority |
| Host+database differ, but `MIGRATION_*` host is the production DB | yes | rbank has a link into production. Read the grants next |
| Fingerprint equal on any username/password | yes | Shared credential. Rotate one side |
| `nc` succeeds from rbank to production DB host | succeeds | Not network-isolated. Needs firewall/security-group rule |
| `nc` times out | times out | Isolated at network level (the link, if any, goes through another path) |
| Grants show `INSERT/UPDATE/DELETE` or `ALL` on the master DB | yes | rbank can change production data. Follow-up: least privilege |
| Grants show only `SELECT` | yes | Link is read only. Lower risk |
| `mysql.user` lists the migration user with host `%` | yes | Can connect from anywhere. Follow-up: restrict host |

Already reported by you, recorded here, not re-run: cookie/session scope,
encryption key, API keys and admin logins checked and fine.

Nothing is changed in the repo, so there is nothing else to regression-test.
