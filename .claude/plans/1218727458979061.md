# PART 1 — In simple words

## What the system does today
Some admin screens borrow a ready-made helper file (a table-display tool called DataTables) from another company's server (`cdn.datatables.net`). Every time one of those screens opens, the browser downloads the file live and runs it, trusting it is the right one.

## What is wrong with it
If that outside server were ever hacked, or someone tampered with the file on its way to the browser, bad code would run inside the bank's admin console, where staff are logged in and see customer data. Nothing checks that the file is the genuine one. It is like using a sealed parcel from a courier without checking the seal.

Nothing bad has happened that we know of. This is a safety gap, not a breakage.

## What we are going to change
There are 3 borrowed files on two admin screens. We treat the two screens differently, following what the rest of the admin already does (other pages keep a copy on our own server and add a fingerprint to it):

- **Locker Availability screen:** it borrows a second copy of the table helper, but the admin already loads its own copy from our server on every page. So we simply remove the borrowed copy. No outside file, nothing to fingerprint.
- **Share Certificate screen:** it borrows 2 older files that we do not keep a copy of. Switching them could change how the screen behaves, so we keep borrowing them and add a "fingerprint" (called SRI) to each. The fingerprint is a short code worked out from the correct file. The browser works out the same code for what it downloaded, and if the two don't match it refuses to run the file.

Three other borrowed files (Razorpay payments, Google Analytics, the Haptik chatbot) are deliberately left alone: their owners change them without notice, so a fingerprint would soon be wrong and break payments, tracking or the chatbot.

## What could go wrong
- Locker screen: if that screen secretly needed its own borrowed copy, its table would stop working. We think it does not, because the admin page already loads the same tool, but it must be tested in the browser. If it fails we put the line back and add a fingerprint instead.
- Share Certificate screen: if we copy a fingerprint wrongly, the browser refuses the file and the table/buttons stop working. We prevent this by working out the fingerprint from the real file and testing the screen.
- If the outside server doesn't allow this kind of check, the file is blocked. We test for that before we commit.

# PART 2 — The words used here

| Word | What it means, simply |
|---|---|
| SRI (Subresource Integrity) | A fingerprint stored in our page for an outside file. The browser refuses the file if its fingerprint differs. |
| CDN | A company's server that hosts shared files so many websites can borrow them. |
| `integrity` attribute | The HTML field that holds the fingerprint, written like `sha384-...`. |
| `crossorigin` attribute | A setting the browser needs so it is allowed to check a file from another site. |
| DataTables | A helper that draws searchable, sortable tables on screen. |

# PART 3 — The technical version

## Root cause
Three admin views load third-party JS from a CDN with no `integrity` attribute (verified on `origin/onestackcbs`):

```
application/modules/cbs/views/service-managment/locker-availability.php:78
    <script src="https://cdn.datatables.net/1.13.5/js/jquery.dataTables.min.js"></script>
application/modules/cbs/views/product-managment/share-certificate.php:3
   <script type="text/javascript"  src=" https://cdn.datatables.net/1.10.13/js/jquery.dataTables.min.js"></script>
application/modules/cbs/views/product-managment/share-certificate.php:4
    <script type="text/javascript"  src=" https://cdn.datatables.net/buttons/1.2.4/js/dataTables.buttons.min.js"></script>
```

All three URLs are version-pinned, so the files never change and SRI is safe. (Task count "0/4" does not map 1:1 to the code; the fourth hit is probably Razorpay, which cannot be hashed. Not verified.)

Not hashable (served unversioned and updated by the vendor, so a hash would break them), left unchanged:
- `application/views/pages/razorpay_view.php:2` — `checkout.razorpay.com/v1/checkout.js` (SafeGold payment page, `third_party/safegold/libraries/Safegold.php:57`)
- `googletagmanager.com/gtag/js` — `sideload.php`, `deregister_device.php`, `apk_poster_download.php` (public pages)
- `toolassets.haptikapi.com/.../loader.js` — `chatbot.php` (public pages)

Existing convention (consistency rule): ~17 live tags in `application/` already carry `integrity="sha512-/sha384-..." crossorigin="anonymous"`, ALL pointing at self-hosted files via `base_url('assets/custom/plugins/...')` (e.g. `modules/cbs/views/common-button.php:23` html2canvas, `product-managment/terms-condition.php:14` Bootstrap CSS, `mobile_app/views/npci-upi/complaint/header.php:10` Popper). No CDN tag is hashed anywhere. So the neighbouring pattern is "self-host, then hash".

Why the two pages differ:
- `locker-availability.php:78` loads DataTables 1.13.5 from the CDN, but the admin shell already loads local DataTables 1.13.6 at `application/views/admin/_templates/header.php:171` (`assets/custom/plugins/datatables/jquery.dataTables.min.js`, banner "DataTables 1.13.6"). The page calls `appendAjaxDataTable(...)` (`assets/custom/js/custom.js:80`) at line 113, which uses the global DataTables, so the CDN tag is a redundant second copy. The view has its own `<html>/<body>` wrapper but is a fragment (no `<head>` assets); how it is injected is not verified (no static reference to `locker-availability` found; loaded dynamically).
- `share-certificate.php:3-4` loads DataTables **1.10.13** and Buttons **1.2.4** from the CDN over the local 1.13.6. No local copy of those versions exists (local is 1.13.6; `dataTables.buttons.min.js` exists locally but its version is not verified). Replacing them could change that page's behaviour (works-by-accident risk), so they keep their CDN source and get SRI.

## How it will be fixed
- `locker-availability.php`: delete line 78 (the redundant CDN DataTables tag). Fallback if the browser test shows the table broken: restore the line and give it `integrity` + `crossorigin` instead.
- `share-certificate.php`: add `integrity="sha384-<hash>"` and `crossorigin="anonymous"` to lines 3 and 4. Hashes are computed from the exact bytes served at the pinned URLs at implementation time. Leave the src URLs and their leading space as is (browsers trim it; not part of this task).

## Plan
1. Branch from `onestackcbs` (`sg_cl_sri_datatables_cdn`) per workflow.
2. Compute SHA-384 of the TWO share-certificate files from their pinned URLs. Needs a download of 2 public files, which needs the user's OK at the time (user was asked and asked for an explanation; re-confirm). Command (piped, nothing saved to disk):
   `curl -sS https://cdn.datatables.net/1.10.13/js/jquery.dataTables.min.js | openssl dgst -sha384 -binary | openssl base64 -A` (repeat for `https://cdn.datatables.net/buttons/1.2.4/js/dataTables.buttons.min.js`).
3. Confirm the CDN answers with CORS: `curl -sI https://cdn.datatables.net/1.10.13/js/jquery.dataTables.min.js | grep -i access-control-allow-origin` must show `*`. If not, stop and ask.
4. Edit `share-certificate.php` lines 3-4, adding `integrity="sha384-..." crossorigin="anonymous"`.
5. Delete `locker-availability.php:78`.
6. Run `.claude/bin/verify.ps1`, commit with `Asana: 1218727458979061` trailer, run the local review, push, open the DEV PR.
